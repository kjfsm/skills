# コードベース全体をレビューする

判定の軸は1つ: **これを直さないと、現実的な操作や次に来る現実的な変更で、誰にどんな不具合・手間が起きるか。** 基準の本体 — 探す対象、確度の付け方、表の列 — は `codebase-reviewer` が持つ。

**件数は目的にしない。** バグは積極的に探すが、それ以外は問いを通ったものだけが載る。少ない一覧は失敗ではない。

近いものとの違い: 差分のレビューは `two-axis-review` と組み込みの `/code-review`、セキュリティだけの監査は `security-audit`、テストの見直しは `prune-tests`、モジュールの深さを軸にした構造の候補探しは `/mattpocock-skills:improve-codebase-architecture` である。ここは差分を持たず、既にあるプロダクションコードの全部を読む。

ここは **一覧で止まる。** 直すのは別の作業で、多数をまとめて直すなら `fix-on-integration-branch` スキルが一覧を受け取る。

## 手順1 — 追いつき、読む対象と材料を集める

`git fetch` し、`origin/<既定ブランチ>` に追いついてから始める。そのコミットの SHA を **基点** として控える。

作業用のディレクトリを1つ切り(`mktemp -d`)、以降のファイルはすべてそこに置く。**ファイルに置くのは、この作業のコンテキストが途中で圧縮されても判定が残るようにするため**である。

- **対象** — `git ls-files` から、テスト、生成物、取り込んだ外部のコード、ロックファイル、アセットを除いたものを `files.txt` に1行1パスで書く。ユーザーが範囲を指定していれば、その範囲だけにする。何を除いたかは `excluded.txt` にパターンと理由で残す — 一覧の最後に「読んでいないもの」として出す
- **文書** — 記録された設計判断と規約(ADR、`CONTEXT.md`、`AGENTS.md`、`.claude/rules/`、`docs/agents/`)のパスを `docs.txt` に書く
- **次に来る変更** — open のイシューの題と、直近の変更履歴(`git log --oneline` の数十件)を `changes.txt` に書く。イシュートラッカーに届かなければ履歴だけにして、そう書く

完了: `files.txt` が範囲内のプロダクションコードを漏れなく含み、除いたものが `excluded.txt` にあり、`docs.txt` と `changes.txt` が探した結果(空を含む)になっている。

## 手順2 — 領域に切って読ませる

**`codebase-reviewer` サブエージェントを、領域ごとに並列で起動する。** 判定の問い・探す対象・確度・表の列・報告の形はそちらが1部だけ持つ — **ここには写さない。** 呼び出しのたびに貼り直す本文は、貼り忘れた日に黙って消える。

自分で読んで判定しない。数万行を1つのコンテキストに入れると、後半ほど判定が雑になる。

- **切り方** — **一緒に読まないと経路が辿れないものを同じ領域に寄せる**(実行される場所と責務の境界で切る: 状態を持つサーバー側、HTTP と認証、共有ロジック、画面、のように)。ディレクトリの大きさを揃えるために、呼ぶ側と呼ばれる側を別の領域に割らない。1体あたり 8,000 行前後(`wc -l` で数える)。領域同士はファイルを重ねない
- **渡すもの** — その領域のファイル一覧、書き出し先(`area-<n>.tsv`)、`docs.txt` と `changes.txt` のパス
- 全体が1体に収まる量でも1体に渡す。毎回同じ経路を通すためである

**読み手が全員返るまで、作業ツリーを動かさない。** 途中で既定ブランチに追いつくと、読み手の手元で行番号がずれ、返ってくる `file:line` が指す先が変わる。

完了: 全員の報告で「読んだ数 = 渡した数」であり、領域のファイル一覧を合わせたものが `files.txt` と一致する。読めなかったファイルと、報告の「領域の外」で名指しされた箇所は、もう1体に渡す。

## 手順3 — 追いつき直し、消えた指摘を落とす

全員が返ってから `git fetch` する。既定ブランチが基点から進んでいたら追いつき、`git diff --name-only <基点>..origin/<既定ブランチ>` に出たファイルを指す行を1件ずつ開き直す。直っていれば落とし、行番号がずれていれば書き直す。

完了: 表のすべての行の `file:line` が、今の作業ツリーで指摘どおりの箇所を指している。

## 手順4 — 束ねて、裏を取る

全領域の表を `all.tsv` に束ねる。

- **重複を畳む** — 同じ原因を2つの領域が別々に挙げていたら1行にする。独立に2体が挙げたことは、その指摘を先に裏取りする理由になる。それだけで `確認済み` にはしない
- **裏を取る** — `バグ` の全行と、差分の大きさが `大` の全行は、自分でコードを開いて経路を辿り直す。辿れたら `確認済み`、読み手の言う経路が通らなければ落とす、読むだけでは決まらなければ `推定` のまま決着のつけ方を残す。ここで判定を足すのは確度だけで、区分と問いは読み手のものを使う
- **ID を振る** — 区分ごとに連番: `B1…`(バグ)、`K1…`(改善)、`I1…`(イマイチ)、`S1…`(簡素化)、`D1…`(食い違い)。以降の会話と、直す段の割り当ては ID で指す。振ったあとは詰め直さない

完了: `バグ` と `大` のすべての行について、自分で辿った結果が確度に反映されている。

## 手順5 — `推定` を、実行して決める

決着のつけ方が `実行` の行を、1件ずつ確かめる。プラットフォームやライブラリの上限に依る指摘は、読むだけでは確定しない。

1. `git status` がクリーンであることを確かめる。依存が入っていなければ、lock ファイルどおりに入れる — 切ったばかりの worktree には無い
2. そのリポジトリに既にあるテストの層のうち、指摘の入力を入口から入れられる層に、**一時テスト** を1本書く。期待は「正しい挙動」で書く — 指摘が本当なら赤になる
3. そのテストだけを走らせる。赤なら `確認済み`、緑なら落とす(列 3 の主張が違っていた)。走らせる途中で別の不具合が出たら、新しい行として足す
4. 一時テストを作業用のディレクトリの `probes/` へ移し、`git status` がクリーンに戻ったことを確かめる。**リポジトリには残さない** — ここは一覧で止まる作業で、赤いテストをコミットする場所ではない。移したテストは、直す側が赤いテストの元として使う

**プロダクションコードは書き換えない。本番にも触らない。** 決着のつけ方が `本番データ` の行は、確かめずに一覧の別枠へ回し、数える対象を読み取りだけの問い合わせの形で添える — 実行するかはユーザーが決める。

完了: `実行` の行が0件か、残ったそれぞれに確かめられなかった理由がある。

## 手順6 — 一覧を出して止まる

一覧を `findings.md` として作業用のディレクトリに書き、同じものをこの順で応答に出す。

1. **バグ** — `確認済み` を先に、その中は起きることの重い順。1件ごとに ID、`file:line`、起きること(入力 → 経路 → 結果)、直し方の案、差分の大きさ、確度。実行して確かめたものにはその印と、`probes/` のファイル名
2. **改善 → イマイチ → 簡素化** — 同じ列で、区分ごとに
3. **実行で確かめていないもの** — `推定` のまま残った行と、確かめられなかった理由
4. **本番のデータで決まるもの** — 何の件数が分かれば判定が変わるかと、その問い合わせ
5. **記録された設計判断を覆す提案** — 名指しした記録と理由。上の区分と重ねて載せず、ここにだけ置く
6. **コードと食い違う記述** — `D` の全件。コードがしていることと記述が言っていることを並べ、どちらに合わせるかは書かない
7. **読んでいないもの** — `excluded.txt` の中身

末尾に区分ごと・確度ごとの件数と、`findings.md` と `probes/` のパスを1行ずつ。

**ここで止まる。直さない。** どれを直すかはユーザーが ID で決める。数件ならこのセッションでそのまま直してよい。多数をまとめて直すなら、`fix-on-integration-branch` スキルに `findings.md` と `probes/` を渡す。設計から決め直す必要がある項目は、イシューにしてから進める。
