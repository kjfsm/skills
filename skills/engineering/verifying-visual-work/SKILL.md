# Verifying Visual Work

見た目の仕事は、**目で判定できる**という思い込みで壊れる。壊れ方は決まっている — 最初の1画面だけを見て「動いた」と結論し、指摘されてから値をいじってはスクリーンショットを見比べ、ある破綻を別の破綻と交換し続ける。

このスキルはそれを止める4つの規律である。バグの診断そのものは `/diagnosing-bugs` が扱う。ここが扱うのは**作っている最中と、作った直後**。

## 1. 実装する前に「これは既知の技法か」を判定する

名前の付いた技法（CSS の視差、スクロール駆動アニメーション、モーフィング、遠近法の合成、仮想スクロール、フォーカストラップ…）は、**解かれている問題**である。落とし穴もセットで文書化されている。

記憶から書き起こす前に、参照を1つ読む。数分で、構造と「なぜその構造なのか」の両方が手に入る。

判定は1問: **この技法に名前が付いているか。** 付いているなら検索する。付いていない（本当に自分の問題）なら、次の規律へ進む。

自前で書き起こしてよいのは、参照を読んだうえで**合わないと分かったとき**だけである。

## 2. 不変量を式で書き、その式をアサートする

座標・寸法・タイミングが絡む問題は、**目で判定してはならない**。スクリーンショットは「何かおかしい」しか教えず、「何がどれだけずれているか」を教えない。値をいじって見比べるループは、そこから始まって収束しない。

手順:

1. その表現が満たすべき関係を**式で書く**。「稜線は画面下端に来る」「深い層はスクロールの 1/S しか動かない」「粒子 i はどの形でも同じ配列位置を担当する」
2. その式を**実行時に測れる形**にする。`getBoundingClientRect()` の差分、要素数、バイト数、`elementFromPoint()` で取れる要素
3. **期待値と実測値を並べて出す**。目で見るのはその表ではなく、一致しているかどうかだけ

```js
// 例: スクロール 400px に対する各層の移動量が 400/S に一致するか
for (const [name, S] of Object.entries({ far: 1.5, mid: 1.28, near: 1.1 })) {
  console.log(name, "実測", before[name] - after[name], "期待", Math.round(400 / S));
}
```

式が書けないなら、その表現をまだ理解していない。理解していないものは調整では直らない。

## 3. 複数の状態で見る。最初の1画面は「状態」ではない

スクロールで動くもの、操作で変わるもの、時間で変わるものは、**最初の1画面を見ても何も検証していない**。

最低限:

- スクロール連動なら 0 / 33 / 67 / 100%
- 操作で変わるなら操作の前後（ドラッグ、トグル、ホバー、キー入力）
- 状態を持つなら各状態（読み込み中・空・エラー・満杯）
- 固定要素があるなら、それが本文に重なる位置

「動く」と書いてよいのは、動いた**後**を見たときだけである。

## 4. 修正が2回外れたら、手を止める

3回目を同じやり方で試してはいけない。2回外れたということは、**直し方ではなく理解が間違っている**。

止まったら、次のどれかへ切り替える:

- 規律1へ戻る（参照を読む）
- 機構を切り出す。本番の画面ではなく、色の帯を3本置くだけの最小のページで調べる。本文・ナビ・配色・他の要素が混ざった画面では、原因の切り分けができない
- 作るものを変える。その表現でなければ達成できない目的か、を問い直す。失敗モードを自分が理解している別の技法で同じ話ができるなら、それは後退ではなく設計判断である
- 相手に状況を渡す。何が分かっていて何が分かっていないかを、試行の回数とともに伝える

**回数を数えておくこと。** 数えていないと、9回目まで同じループを回っていたことに後から気づく。

## 実際に起きたこと

CSS の遠近法による視差を記憶から書き、最初の1画面だけを見て「動く」と PR に書いた。指摘を受けてから9回、値を変えてはスクリーンショットを見比べた。地面を足せば地中に潜り、詰めれば稜線が消え、構造を変えれば空だけが残った。

投影の式を書き下した時点で原因は即座に出た。`perspective-origin: 0 0` の下ではシーン座標 y の点は画面上の `y / S` に出る。どの層も稜線を `y = 100dvh` に置いていたので、遠い層ほど `100/S` — 画面の上へ寄っていた。正しくは `y = 100dvh × S` に置く。

式を実測と突き合わせたら1回で収束した:

| 層   | S    | 実測移動 | 期待 `400/S` |
| ---- | ---- | -------- | ------------ |
| far  | 1.5  | 267px    | 267px        |
| mid  | 1.28 | 313px    | 313px        |
| near | 1.1  | 364px    | 364px        |

同じセッションで、コードの設計判断（メタデータをどこに置くか）は最小の実験を作って2つの条件を実測し、証拠で決めていた。**手法は持っていたのに、見た目の問題には適用しなかった。** 「設計は計測、見た目は目視」という無意識の線引きが、この失敗の本体である。座標が絡めば、見た目も計測対象である。
