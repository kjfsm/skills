# エージェントブリーフの書き方

テンプレートは **形** の見本である。書く言語はリポジトリの既存文書に合わせる — 見本が英語であることは、英語で書く理由にならない。

エージェントブリーフとは、GitHub のイシューや PR が `ready-for-agent` に移るときに投稿される、構造化されたコメントである。これは AFK エージェントが作業のよりどころとする、権威あるスペックである。元の本文や議論はあくまでコンテキストであり、エージェントブリーフこそが契約である。

このブリーフは **エージェントが何をすべきか** を述べるものであり、それは両方の対象に及ぶ: イシューの場合はゼロから変更を構築すること、PR の場合は _既存の差分に対して_ 何が残っているか — 仕上げる、ギャップを埋める、レビュー指摘に対応する、ということである。原則はどちらでも同じであり、下記の PR の例がその違いを示している。

## 原則

### 精密さより長持ちすること

そのイシューは何日も、何週間も `ready-for-agent` のまま置かれるかもしれない。その間にコードベースは変わる。ファイルが改名され、移動され、リファクタリングされても、このブリーフが役立ち続けるように書く。

- **すべきこと**: インターフェース、型、振る舞いの契約を記述する
- **すべきこと**: エージェントが探すべき、あるいは変更すべき具体的な型、関数のシグネチャ、設定の形を名指しする
- **してはいけないこと**: ファイルパスを参照する — すぐに古くなる
- **してはいけないこと**: 行番号を参照する
- **してはいけないこと**: 現在の実装構造がそのまま残ると仮定する

### 振る舞いを記述する、手順を記述しない

システムが **何を** すべきかを記述し、**どう** 実装するかは記述しない。エージェントは新たな気持ちでコードベースを探索し、自分自身の実装上の決定を下す。

- **良い例:** 「`SkillConfig` 型は `CronExpression` 型の任意の `schedule` フィールドを受け付けるべきである」
- **悪い例:** 「src/types/skill.ts を開き、42行目に schedule フィールドを追加する」
- **良い例:** 「ユーザーが引数なしで `/triage` を実行すると、対応が必要なイシューの要約が表示されるべきである」
- **悪い例:** 「メインのハンドラ関数に switch 文を追加する」

### 完全な受け入れ基準

エージェントは、いつ完了したかを知る必要がある。すべてのエージェントブリーフには、具体的でテスト可能な受け入れ基準がなければならない。各基準は独立して検証可能であるべきである。

- **良い例:** 「`gh issue list --label needs-triage` を実行すると、初期分類を経たイシューが返る」
- **悪い例:** 「トリアージが正しく動作すること」

### 明示的なスコープの境界

何がスコープ外かを述べる。これにより、エージェントが過剰に作り込んだり、隣接する機能について勝手な想定をしたりするのを防ぐ。

## テンプレート

```markdown
## Agent Brief

**Category:** bug / enhancement
**Summary:** 何が起きる必要があるかの1行の説明

**Current behavior:**
今どうなっているかを記述する。バグの場合はこれが壊れた振る舞いである。
拡張の場合はこれが、その機能が積み上がる現状である。

**Desired behavior:**
エージェントの作業が完了した後にどうなるべきかを記述する。
エッジケースやエラー条件について具体的に書く。

**Key interfaces:**

- `TypeName` — 何をなぜ変える必要があるか
- `functionName()` の戻り値の型 — 現在何を返し、何を返すべきか
- 設定の形 — 必要な新しい設定オプションがあれば

**Acceptance criteria:**

- [ ] 具体的でテスト可能な基準 1
- [ ] 具体的でテスト可能な基準 2
- [ ] 具体的でテスト可能な基準 3

**Out of scope:**

- このイシューで変更・対応すべきで **ない** もの
- 関連しているように見えるが別物である隣接機能
```

## 例

### 良いエージェントブリーフ(バグ)

```markdown
## Agent Brief

**Category:** bug
**Summary:** スキルの description の切り詰めが単語の途中で切れ、壊れた出力を生む

**Current behavior:**
スキルの description が1024文字を超えると、単語の境界に関わらず正確に
1024文字で切り詰められる。これにより、単語の途中で終わる description が
生じる(例:「Use when the user wants to confi」)。

**Desired behavior:**
切り詰めは1024文字より前の最後の単語境界で行われ、切り詰められたことを
示すために「...」を付け加えるべきである。

**Key interfaces:**

- `SkillMetadata` 型の `description` フィールド — 型自体の変更は不要だが、
  それを埋めるバリデーション/処理ロジックが単語境界を尊重する必要がある
- SKILL.md の frontmatter を読んで description を抽出するあらゆる関数

**Acceptance criteria:**

- [ ] 1024文字未満の description は変わらない
- [ ] 1024文字を超える description は、1024文字より前の最後の単語境界で
      切り詰められる
- [ ] 切り詰められた description は「...」で終わる
- [ ] 「...」を含めた合計の長さが1024文字を超えない

**Out of scope:**

- 1024文字という制限自体を変えること
- 複数行にわたる description のサポート
```

### 良いエージェントブリーフ(拡張)

```markdown
## Agent Brief

**Category:** enhancement
**Summary:** 却下された機能要望を追跡するための `.out-of-scope/` ディレクトリのサポートを追加する

**Current behavior:**
機能要望が却下されると、そのイシューは `wontfix` ラベルとコメントを付けて
クローズされる。その決定や理由の永続的な記録は存在しない。今後似たような
要望が来ても、メンテナーは過去の議論を思い出すか検索する必要がある。

**Desired behavior:**
却下された機能要望は、`.out-of-scope/<concept>.md` ファイルに、決定、理由、
その機能を要望したすべてのイシューへのリンクとともに記録されるべきである。
新しいイシューをトリアージする際は、これらのファイルとの一致を確認する
べきである。

**Key interfaces:**

- `.out-of-scope/` 内の Markdown ファイル形式 — 各ファイルは
  `# Concept Name` の見出し、`**Decision:**` の行、`**Reason:**` の行、
  イシューへのリンクを含む `**Prior requests:**` のリストを持つべきである
- トリアージのワークフローは、早い段階で `.out-of-scope/*.md` の全ファイルを
  読み、入ってきたイシューを概念の類似性で照合するべきである

**Acceptance criteria:**

- [ ] 機能を wontfix としてクローズすると `.out-of-scope/` にファイルが
      作成・更新される
- [ ] そのファイルには決定、理由、クローズされたイシューへのリンクが
      含まれる
- [ ] 一致する `.out-of-scope/` ファイルがすでに存在する場合、新しいイシューは
      重複を作らずその「Prior requests」リストに追加される
- [ ] トリアージ中、既存の `.out-of-scope/` ファイルが確認され、新しい
      イシューが過去の却下と一致する場合に表面化される

**Out of scope:**

- 自動的な照合(人間が一致を確認する)
- 過去に却下された機能の再オープン
- バグ報告(拡張の却下のみが `.out-of-scope/` に行く)
```

### 良いエージェントブリーフ(PR)

PR の場合、「Current behavior」は差分の現状を記述し、ブリーフはゼロから構築するのではなく、それを仕上げるか直すようエージェントに求める。

```markdown
## Agent Brief

**Category:** enhancement
**Summary:** `triage list` のコントリビューターによる `--json` 出力フラグを仕上げる

**Current behavior:**
この PR はイシューのリストを JSON にシリアライズする `--json` フラグを
追加する。ハッピーパスは動作し、差分はプロジェクトのコマンド構造と一致
している。2つのギャップが残っている: エラーはまだ人間向けのテキストとして
出力されており(JSON ではない)、新しいフラグにテストのカバレッジがない。

**Desired behavior:**
`--json` を付けると、エラーを含むすべての出力が stdout 上の整形された
JSON になり、コマンドの終了コードは変わらない。フラグがない場合の既存の
人間向け出力はそのままである。

**Key interfaces:**

- コマンドのエラー経路は、プレーンテキストのエラーの代わりに `--json` の
  下で `{ "error": string }` を出力するべきである
- PR がすでに追加した既存のシリアライザを再利用する。2つ目を導入しない

**Acceptance criteria:**

- [ ] `triage list --json` は成功・エラーどちらのケースでも有効な JSON を
      出力する
- [ ] 終了コードは非 JSON のコマンドと一致する
- [ ] `--json` の成功時の出力とエラーケース1つをテストがカバーする
- [ ] デフォルト(非 JSON)の出力はバイト単位で変わらない

**Out of scope:**

- 他のコマンドに `--json` を追加すること
- PR がすでに定義した成功時のペイロードの JSON の形を変えること
```

### 悪いエージェントブリーフ

```markdown
## Agent Brief

**Summary:** トリアージのバグを直す

**What to do:**
トリアージ周りが壊れている。メインのファイルを見て直して。
150行目あたりの関数に問題がある。

**Files to change:**

- src/triage/handler.ts (line 150)
- src/types.ts (line 42)
```

これが悪い理由:

- カテゴリがない
- 説明が曖昧(「トリアージ周りが壊れている」)
- すぐに古くなるファイルパスと行番号を参照している
- 受け入れ基準がない
- スコープの境界がない
- 現在の振る舞いと望む振る舞いの記述がない
