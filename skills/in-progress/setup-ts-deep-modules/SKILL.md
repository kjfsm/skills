# Setup TS Deep Modules

このリポジトリのすべてのパッケージを**深いモジュール**にする: 小さなインターフェースの裏に多くの振る舞いを隠す。パッケージの公開面はその**エントリーポイント** — パッケージのルートにあるファイル — であり、サブフォルダの中身はすべて隠される。このスキルは [dependency-cruiser](https://github.com/sverweij/dependency-cruiser) と、エントリーポイントだけが唯一の入り口になるようにするルールをインストールし、そのルールが実際に機能することを証明する。

用語(深いモジュール、インターフェース、シーム、深さ)については `/codebase-design` スキルを実行し、その語彙を一貫して使うこと。

## 強制される構造

```
src/packages/
  <name>/
    index.ts        ← an entry point (public). Import this from outside.
    client.ts       ← another entry point. Packages may expose SEVERAL.
    lib/            ← implementation: hidden from outside, free to import each other.
    tests/          ← co-located tests + fixtures (a subfolder, so private).
```

公開面はパッケージの**ルートファイル**である — 唯一指定された `index.ts` ではない。慣例として実装は `lib/` に、テストは `tests/` に置かれ、すべてのパッケージが同じ二分割の構造を持つ。ただしルール自体は一般的なものである: *どの*サブフォルダの中身も*すべて*非公開なので、フォルダを追加するたびに設定を拡張する必要は一切ない。

4つのルール、すべて `error`:

1. **エントリーポイント境界** — パッケージ外のコード(アプリコードや他のパッケージ)は、そのパッケージのエントリーポイント(ルートファイル)だけをインポートでき、サブフォルダの中身は一切インポートできない。
2. **パッケージ内の自由** — パッケージ自身のファイルは互いに自由にインポートし合える。
3. **テストはエントリーポイント経由** — `<pkg>/tests/` 配下のファイルは、任意のパッケージのエントリーポイントと自分自身の `tests/` フィクスチャをインポートできるが、どのパッケージのサブフォルダ内部(自分自身のものであっても)もインポートできない。パッケージ横断の統合テストは問題ないが、深いインポートは不可。
4. **循環禁止** — 依存の循環を禁止する。

**バレルではなくエントリーポイント。** 公開面は*すべての*ルートファイルであるため、パッケージは1つの巨大な `index.ts` にすべてを流し込む代わりに、複数の小さなエントリーポイント(`index.ts`、`client.ts`、`server.ts`)を公開できる。サブツリー全体を再エクスポートするバレルファイルは推奨されない — エントリーポイントは小さく保ち、実装はサブフォルダに隠す。

レイヤリング(どのパッケージがどのパッケージに依存できるか)は*別の*関心事であり、このリポジトリで埋めるべきコメント付きのスタブとして設定に残してある。

## 手順

### 1. 環境を検出する

- **パッケージマネージャー** — `pnpm-lock.yaml` → pnpm、`yarn.lock` → yarn、`bun.lockb` → bun、それ以外は npm。以下のすべてのコマンドでこれを使う(`pnpm`/`yarn`/`npm run`/`bunx`)。
- **パッケージのルート** — `src/` が存在すれば `src/packages`、なければ `packages`。リポジトリがすでに異なる明確な慣例を持っている場合はユーザーに確認する。
- **既存の設定** — `.dependency-cruiser.*` ファイルの有無を確認する。既に存在する場合は上書き**しない**: 4つのルールとオプションをマージし、何を追加したかをユーザーに伝える。

**完了の条件:** パッケージマネージャー、パッケージのルート、既存設定の有無がすべて判明していること。

### 2. dependency-cruiser をインストールする

検出したパッケージマネージャーで `dependency-cruiser` を devDependency としてインストールする。

**完了の条件:** `dependency-cruiser` が `devDependencies` に入っていること。

### 3. 設定を書く

[`dependency-cruiser.config.cjs`](./dependency-cruiser.config.cjs) をリポジトリのルートに `.dependency-cruiser.cjs` としてコピーする。`PACKAGES_ROOT` をステップ1で検出したルートに設定する。ルールはパスの深さに基づいており拡張子に依存しないため、他に調整は不要である。

**完了の条件:** `.dependency-cruiser.cjs` が正しい `PACKAGES_ROOT` とともに存在し、4つの禁止ルールが含まれていること。

### 4. チェックに組み込む

- `lint:boundaries` スクリプトを追加する: `depcruise <packages-root>`(または `depcruise src`)。
- すでに typecheck を実行しているリポジトリの統括チェックコマンド(例: `check` / `ci` / `validate` スクリプト)に組み込む。`tsconfig` に触れたり、パスエイリアスを追加したりしては**いけない**。
- 統括スクリプトが存在しない場合は `lint:boundaries` を追加し、CI に含めるようユーザーに伝える。

**完了の条件:** `lint:boundaries` が存在し、typecheck と同じコマンドの一部として実行されること。

### 5. サンプルパッケージを組み立てる

コピー用テンプレートとして、コミットされる `<packages-root>/example/` を作成する:

- `index.ts` — エントリーポイント。内部ファイルに処理を委譲する1つの関数をエクスポートする(パッケージが単なる素通しではなく、見た目にも*深い*ことがわかるように)。
- `lib/impl.ts` — **サブフォルダ**内の内部ファイルで、`index.ts` からインポートされ、外部からは到達不能。
- `tests/example.test.ts` — **`../index`(エントリーポイント)だけを**インポートし、公開関数に対してアサーションする。

これはコピーするか削除してよいスターターテンプレートであることをユーザーに伝える。

**完了の条件:** サンプルパッケージが存在し、その振る舞いをルートのエントリーポイント経由で公開し、`impl` をサブフォルダに隠していること。

### 6. ルールが実際に効くことを証明する

これがスキル全体の完了基準である — 違反時に失敗しない設定は無価値である。

1. `lint:boundaries` を実行する。クリーンなサンプルに対しては**成功**しなければならない。
2. `tests/example.test.ts` に一時的に深いインポートを追加する(例: `import { thing } from "../lib/impl"`)。再度 `lint:boundaries` を実行する — `tests-through-entrypoints` で**失敗**しなければならない。
3. 深いインポートを元に戻す。もう一度実行する — **成功**しなければならない。

**完了の条件:** 成功、深いインポートでの失敗、再度の成功、という一連の流れを確認していること。ステップ2で失敗しない場合、ルールが正しく組み込まれていない — 完了とする前に修正すること。

### 7. 規約をドキュメント化する

**パッケージフォルダ内**(`<packages-root>/README.md`)に、それが統括するパッケージの隣に `README.md` を書く。内容は: `src/packages/<name>/` のレイアウト(ルートにエントリーポイント、実装は `lib/`、テストは `tests/`)、「パッケージのエントリーポイント(ルートファイル)を通じてのみインポートする」こと、そして `lint:boundaries` の実行方法。**バレルファイルは明示的に非推奨とする** — サブツリー全体を1つの index で再エクスポートする代わりに、複数の小さなエントリーポイントを公開する。コピー用スニペットと、4つのルールをそれぞれ1段落にまとめた内容に留める。

その後、リポジトリのエージェント向け指示ファイル — 存在すれば `CLAUDE.md`、なければ `AGENTS.md`(どちらも存在しなければ `AGENTS.md` を作成)— から、そこへの**コンテキストポインタ**を追加する。1行で十分である。例: `Packages are deep modules — see [src/packages/README.md](./src/packages/README.md) before adding or importing one.` これによって、エージェントが境界ルールにつまずくのではなく、それを発見できるようになる。

**完了の条件:** `<packages-root>/README.md` が存在し、バレルを非推奨としており、リポジトリの `CLAUDE.md`/`AGENTS.md` からそこへリンクされていること。

## 補足

- 設定の `$1` バックリファレンス(dependency-cruiser のグループマッチング)は、パッケージが自分自身の内部には到達でき、外部からはできないようにする仕組みである — これをパッケージごとの個別ルールに平坦化してはならない。
- 公開か非公開かは**深さ**によって決まる: パッケージのルートファイルはエントリーポイントであり、サブフォルダ内のものはすべて非公開である。慣例的なサブフォルダは `lib/`(実装)と `tests/` だが、ルール自体はそれらをハードコードしていない — どのサブフォルダも非公開なので、新しいフォルダを追加しても設定変更は一切不要である。エントリーポイントの追加は単にルートファイルを追加するだけであり、バレルは不要である。
- パッケージは**フラット**である: ルート直下の子1階層のみ。パッケージの内部は好きなだけネストしてよいが、パッケージが別のパッケージを含むことはできない。
- `"type": "module"` のリポジトリでも設定の `module.exports` が機能するよう、`.js` ではなく `.cjs` を使う。
