# To Tickets

計画・スペック・会話を、一連の **チケット** — それぞれが自分を **ブロックする** チケットを宣言する、トレーサーバレット方式の垂直スライス — に分割する。

イシュートラッカーとトリアージラベルの語彙は、あなたにすでに渡されているはずである — なければ `/setup-skills` を実行すること。

## 手順

### 1. コンテキストを集める

すでに会話のコンテキストにあるものから作業する。ユーザーが引数として参照(スペックのパス、イシュー番号や URL)を渡した場合は、それを取得し、本文とコメントを全文読む。

### 2. コードベースを探索する(任意)

まだコードベースを探索していなければ、コードの現状を理解するために探索する。チケットのタイトルと説明はプロジェクトのドメイン用語集の語彙を使い、触れている領域にある ADR を尊重する。

実装をしやすくするための事前リファクタリングの機会を探す。「変更を楽にしてから、楽になった変更を行う」。

### 3. 垂直スライスを下書きする

作業を **トレーサーバレット** 方式のチケットに分割する。

<vertical-slice-rules>

- 各スライスは、あらゆる層(スキーマ、API、UI、テスト)を貫く、狭いが完全な経路を切り出す — 1つの層だけを切り出す水平スライスではなく、垂直である
- 完成したスライスは単体でデモまたは検証が可能である
- 各スライスは、1つの新しいコンテキストウィンドウに収まる大きさにする
- 事前リファクタリングがあれば、それを最初に行う

</vertical-slice-rules>

各チケットにその **ブロッキングエッジ** — それが始まる前に完了していなければならない他のチケット — を与える。ブロッカーのないチケットはすぐに開始できる。

**大規模なリファクタリングは垂直スライスの例外である。** **大規模なリファクタリング** とは、1つの機械的な変更 — カラムのリネーム、共有されたシンボルの型変更など — であり、その **影響範囲** がコードベース全体に広がるため、1回の編集で数千の呼び出し箇所が一度に壊れ、どの垂直スライスもグリーンで着地できないものを指す。これをトレーサーバレットに無理やり詰め込まず、**拡張—収縮** として順序立てる。まず拡張: 何も壊れないよう、新しい形を古い形の隣に追加する。次に、影響範囲の大きさ(パッケージ単位、ディレクトリ単位)に応じたバッチで呼び出し箇所を移行する。各バッチはそれぞれ独自のチケットとし、拡張のチケットにブロックされる。古い形がまだ存在するので、バッチからバッチへ CI をグリーンに保てる。最後に収縮: 呼び出し元が残らなくなったら、すべての移行バッチにブロックされるチケットの中で古い形を削除する。バッチ単体ではグリーンを保てない場合でも、この順序は保ったまま、それらに統合ブランチを共有させ、それらすべてが最終的な統合・検証チケットをブロックするようにする — グリーンが約束されるのはそこだけである。

### 4. ユーザーに問う

提案する分割を番号付きリストとして提示する。各チケットについて次を示す:

- **タイトル**: 短く説明的な名前
- **ブロックされる要因**: (もしあれば)先に完了していなければならない他のチケット
- **提供するもの**: このチケットが動くようにするエンドツーエンドの振る舞い

ユーザーに次を尋ねる:

- 粒度は適切に感じられるか?(粗すぎる/細かすぎる)
- ブロッキングエッジは正しいか — 各チケットは本当に自分をゲートするチケットだけに依存しているか?
- マージすべき、あるいはさらに分割すべきチケットはあるか?

ユーザーがこの分割を承認するまで繰り返す。

### 5. 設定済みのトラッカーへチケットを公開する

承認されたチケットを公開する。**方法** は `/setup-skills` が設定したトラッカーによって決まる — チケットの内容自体はどちらでも同じで、ブロッキングエッジの形だけが変わる:

- **ローカルファイル** → `.scratch/<feature-slug>/issues/<NN>-<slug>.md` の下にチケット1つにつき1ファイルを書き、依存関係の順(ブロッカーを先に)で `01` から番号を振る。各ファイルの「Blocked by」には依存する番号/タイトルを列挙する。下記のチケットごとのファイルテンプレートを使う — 1ファイルにつき1チケット、まとめた1ファイルには決してしない。
- **実際のイシュートラッカー(GitHub、Linear など)** → 依存関係の順(ブロッカーを先に)で、チケットごとに1つのイシューを公開する。こうすることで各チケットのブロッキングエッジが実際の識別子を参照できる。プラットフォームにネイティブなブロッキング/サブイシューの関係があればそれを使い、なければ各チケットの「Blocked by」にブロッキングイシューを設定する。特に指示がない限り `ready-for-agent` トリアージラベルを適用する — このチケットは構造上、最初からエージェントが着手できる状態である。

**フロンティア** に取り組む: ブロッカーがすべて完了しているチケットのこと。純粋に一直線のチェーンであれば、それは上から下への順を意味する。

親イシューをクローズしたり変更したりしては **ならない**。
