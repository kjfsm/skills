# スキル集をネイティブな Claude Code プラグインとして出荷し、ネイティブな Codex プラグインは見送る

これらのスキルは、これまでずっと [skills.sh](https://skills.sh/kjfsm/skills)(`npx skills add kjfsm/skills`)経由でインストール可能だった。これは編集可能なスキルファイルを、Claude Code、Codex、その他 Agent-Skills 標準に準拠したハーネスをまたいで、ユーザーのプロジェクトにコピーする仕組みである。繰り返し寄せられる要望が **差し込んですぐ使える** 配布方法だ: 自分でフォークして所有するのではなく、読み取り専用かつ常に最新の状態でこの集合を購読したい、というものである。それこそまさにネイティブなプラグインシステムが提供するものだ。

我々はネイティブな **Claude Code プラグイン** を出荷し、今のところネイティブな **Codex プラグイン** は **見送る**。この切り分けは、それぞれのエコシステムのプラグインマニフェストがスキルをどう選択するかと、このリポジトリのバケット構成とのぶつかり合いによって強いられたものである。

## 制約: バケット化されたスキル と 単一パス選択

スキルは `skills/` 配下のバケットフォルダに置かれている — `engineering/` と `productivity/` は **昇格済み**(出荷対象)であり、`misc/`、`personal/`、`in-progress/`、`deprecated/` は **そうではない**。プラグインは昇格済みの集合だけを公開しなければならず、それは2つのバケットフォルダにまたがっている。

- **Claude Code** — `.claude-plugin/plugin.json` は `skills` を **明示的なスキルディレクトリパスの配列** として受け付ける。昇格済みのスキルを1つずつ列挙し、それ以外はすべて曖昧さゼロで除外し、さらに `.claude-plugin/marketplace.json` を追加してこのリポジトリ自体を単一プラグインのマーケットプレイスにしている。エンドツーエンドで検証済み: `claude plugin validate . --strict` が通り、`marketplace add` → `install` は昇格済みのスキルをすべて解決する。

- **Codex** — `.codex-plugin/plugin.json` は `skills` を **単一のパス文字列としてのみ** 受け付け(配列は `missing or invalid plugin.json` として拒否される)、Codex はその配下を再帰的に走査して `SKILL.md` ファイルを見つける。1つのパスから2つのバケットフォルダを指定したり、部分集合を選び取ったりする方法はない。2つの回避策を試したが、どちらも却下した:
  - `./skills/` を指定すると、`deprecated/`、`in-progress/`、`personal/`、`misc/` も一緒に出荷されてしまう — 意図的に昇格させていない、引退済み・下書き・個人用のスキルである。
  - バケットへの **シンボリックリンク** を集めたフラットなディレクトリを用意しても、インストールを生き延びない: Codex はプラグインツリーを自分のキャッシュにコピーする際に **シンボリックリンクを落としてしまう** ため、スキルは空の状態で届く。

Codex に昇格済みだけの単一パスを渡す頑健な方法は、(a) `skills/` に昇格済みのスキルだけが入るよう **再構成する**(昇格していないバケットを外に移す — `CLAUDE.md`、`scripts/link-skills.sh`、各バケットの README、そして `in-progress/` と `personal/` に依存しているローカルの開発ワークフローにまで影響が及ぶ大きな作業になる)か、(b) 昇格済みスキルの **複製をフラットなディレクトリにコミットする**(同期の手間が生じ、真実の源が2つになる)かのいずれかしかない。どちらも構造上の意思決定であり、Claude プラグインを出荷する作業に一緒に詰め込むべきものではない。これはおそらく、以前プラグインが出荷されなかった本来の理由 — うろ覚えだったもの — そのものだろう: マニフェスト形式が、バケット化されたリポジトリの一部集合をきれいに表現できなかったのだ。

## 決定

- **Claude Code プラグイン**(`.claude-plugin/plugin.json` + `.claude-plugin/marketplace.json`)を、昇格済みの集合に絞った形で、v1.2 の目玉として今すぐ出荷する。
- **skills.sh** を汎用インストーラーとして維持する — これは今日すでに Codex やその他のハーネスに対応しているので、Codex ユーザーがインストール手段を失うことはない。
- ネイティブな Codex プラグインは、`skills/` を昇格済みのみに再構成するか、生成したフラットな複製をコミットするかを決めるまで **見送る**。Codex が `skills` 配列 / include リストをサポートするか、インストール時にシンボリックリンクを保持するようになったら、再検討する。

## この決定が生む不変条件

- 昇格済みのスキルはすべて `.claude-plugin/plugin.json` の `skills` 配列にエントリを持つ(これはすでに `CLAUDE.md` のルールとして存在していたが、今やプラグインの内容もこれによってゲートされる)。

## 更新の届け方は、その後この決定を離れた

<details>
<summary>当初この ADR が立てた不変条件(いまは成り立たない)</summary>

> `.claude-plugin/plugin.json` の `version` は `package.json` のバージョンを追随する — リリース時は両方を一緒に上げること。Claude はプラグインの `version` を見て、インストール済みユーザーにいつ更新を表示するか決める。

</details>

**現行は逆である: `version` はどこにも置かない。** 公式はプラグインの更新の届き方を3通り定めており、`version` を明示すると「上げたときだけ更新が届く」、`plugin.json` と marketplace エントリの **両方から省く** と「解決されるコミットが変わるたびに更新が届く」になる。リリースの刻みを持たないこのリポジトリでは後者が正しいので、`version` を書かないことそのものが不変条件になった。

- 検査 11. が両方のマニフェストを見る。
- CI が `claude plugin validate` から `--strict` を外しているのも同じ理由である — `--strict` は `version` 不在を error に格上げしてしまう(この ADR の本文が「`--strict` が通る」と書いているのは、`version` を持っていた当時の話である)。
- 根拠は `CLAUDE.md` にまとめてある。
