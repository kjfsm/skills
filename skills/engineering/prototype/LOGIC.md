# Logic Prototype

ユーザーが手でステートモデルを動かせる、小さな対話型ターミナルアプリ。問いが **ビジネスロジック、状態遷移、データの形** に関するものであるとき — 紙の上では妥当に見えるが、実際のケースを通してみて初めておかしいと感じられるようなものに使う。

## この形が適している場合

- 「この状態機械が X の後に Y というエッジケースを処理できるか自信がない。」
- 「このデータモデルは、実際に…というケースを表現できるのか?」
- 「書く前に、この API がどんな見た目になるべきか感触をつかみたい。」
- ユーザーが **ボタンを押して状態が変わるのを見たい** ものすべて。

問いが「これはどう見えるべきか」であれば — 分岐を間違えている。[UI.md](UI.md) を使う。

## 手順

### 1. 問いを述べる

コードを書く前に、どのステートモデルとどの問いをプロトタイピングしているのかを書き留める。プロトタイプの README か、ファイル先頭のコメントに1段落で。間違った問いに答えるロジックプロトタイプは純粋な無駄である — ユーザーが今見ていても、後で離席先から戻ってきても確認できるよう、問いを明示する。

### 2. 言語を選ぶ

ホストとなるプロジェクトが使っているものを使う。プロジェクトに明らかなランタイムがない場合(ドキュメントのリポジトリなど)は尋ねる。

ツールについてはプロジェクトの既存の慣習に合わせる — プロトタイプのためだけに新しいパッケージマネージャやランタイムを追加しない。

### 3. ロジックを持ち運び可能なモジュールに隔離する

実際のロジック — 問いに答えている部分 — を、後で持ち上げて本物のコードベースに落とし込めるような、小さく純粋なインターフェースの裏に置く。それを囲む TUI は使い捨てだが、ロジックのモジュールはそうであってはならない。

正しい形は問いによって決まる:

- **純粋な reducer** — `(state, action) => state`。アクションが離散的なイベントで、状態が単一の値であるときに向く。
- **ステートマシン** — 明示的な状態と遷移。「今どのアクションがそもそも許可されているか」が問いの一部であるときに向く。
- プレーンなデータ型に対する **少数の純粋関数の集合**。暗黙の現在状態がなく、単なる変換だけであるときに向く。
- ロジックが本当に継続的な内部状態を持つ場合の、明確なメソッド表面を持つ **クラスやモジュール**。

TUI に配線しやすいかではなく、問われている問いに最も合う形を選ぶ。純粋に保つ: I/O なし、ターミナル用のコードなし、制御フローのための `console.log` なし。TUI がそれをインポートして呼び出す。逆方向には何も流れない。

これが、プロトタイプをその寿命を超えて役立たせる理由である: 問いに答えが出たら、検証済みの reducer/マシン/関数群だけを単独で本物のモジュールへ持ち上げられる。

### 4. 状態を見せる最小の TUI を作る

**軽量な TUI** として作る — 毎ティック、画面をクリアし(`console.clear()` / `print("\033[2J\033[H")` / 同等のもの)、フレーム全体を再描画する。ユーザーには常に、際限なく伸びるスクロールバックではなく、1つの安定したビューが見えるべきである。

各フレームは、この順で2つの部分を持つ:

1. **現在の状態**。整形され、diff しやすい形で(1行に1フィールド、または整形された JSON)。フィールド名やセクションの見出しには **太字**、あまり重要でない文脈(タイムスタンプ、ID、派生値)には **暗く** を使う。素の ANSI エスケープコードで構わない — 太字は `\x1b[1m`、暗くは `\x1b[2m`、リセットは `\x1b[0m`。プロジェクトにすでにスタイリング用ライブラリがない限り、新たに導入する必要はない。
2. **キーボードショートカット**。下部に列挙する: `[a] add user  [d] delete user  [t] tick clock  [q] quit`。キーを太字に、説明を暗くする、あるいはその逆 — きれいに読める方でよい。

振る舞い:

1. **状態を初期化する** — 単一のインメモリのオブジェクト/構造体。開始時に最初のフレームを描画する。
2. 一度に **1回のキー入力(または1行)** を読み、状態を変更するハンドラにディスパッチする。
3. アクションのたびに **フレーム全体を再描画する** — 追記せず、置き換える。
4. **終了するまでループする。**

フレーム全体が1画面に収まるべきである。

### 5. 1コマンドで実行できるようにする

プロジェクトの既存のタスクランナー(`package.json` の scripts、`Makefile`、`justfile`、`pyproject.toml`)にスクリプトを追加する。ユーザーは `pnpm run <prototype-name>` かそれに相当するものを実行できるべきであり、パスを覚える必要は決してない。

ホストとなるプロジェクトにタスクランナーがない場合は、実行コマンドをプロトタイプの README の先頭に書くだけでよい。

### 6. 引き渡す

ユーザーに実行コマンドを伝える。ユーザー自身がそれを動かす。興味深い瞬間は、ユーザーが「待って、それはあり得ないはずだ」や「え、X は違うと思っていた」と言うときである — それらは _アイデア_ の中のバグであり、それこそが本来の狙いである。新しいアクションを追加してほしいと言われたら、追加する。プロトタイプは進化する。

### 7. 答えとプロトタイプを記録する

プロトタイプが問いに答えたら、答えを記録し、それから [SKILL](SKILL.md) が説明する方法でプロトタイプ自体を記録する。ロジック固有の対応付け: 検証済みの reducer/マシン/関数群は本物のモジュールに持ち上がる(決定が吸収される)。TUI の外殻は、プロトタイプを一次情報源として保持する使い捨てブランチに一緒に乗っていく。

## アンチパターン

- **テストを追加しない。** テストが必要になったプロトタイプは、もはやプロトタイプではない。
- **本物のデータベースに配線しない。** 問いが特に永続化についてのものでない限り、インメモリのストアを使う。
- **一般化しない。** 「後で X をサポートしたくなったら」はなし。プロトタイプは1つの問いに答える。
- **ロジックと TUI を混ぜ合わせない。** reducer/ステートマシンが `console.log`、プロンプト、ターミナルのエスケープコードを参照しているなら、それはもう持ち運び可能ではない。TUI は純粋なモジュールの上の薄い殻に保つ。
- **TUI の外殻を本番に出荷しない。** その外殻は、ターミナルから手で動かされることに最適化されている。その裏にあるロジックのモジュールこそが、残す価値のある部分である。
