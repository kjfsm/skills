# Deepening

依存関係を踏まえて、浅いモジュールのクラスタを安全に深化させる方法。[SKILL.md](SKILL.md) の語彙(**module**、**interface**、**seam**、**adapter**)を前提とする。

## 依存のカテゴリ

深化の候補を評価するときは、その依存関係を分類する。このカテゴリが、深化したモジュールがそのシームを越えてどうテストされるかを決める。

### 1. In-process(プロセス内)

純粋な計算、インメモリの状態、I/O なし。常に深化可能 — モジュールを統合し、新しいインターフェースを通して直接テストする。アダプターは不要。

### 2. Local-substitutable(ローカルで代替可能)

ローカルのテスト用代替物がある依存(Postgres に対する PGLite、インメモリのファイルシステムなど)。代替物が存在すれば深化可能。深化したモジュールは、テストスイートの中でその代替物を動かしてテストする。シームは内部にあり、モジュールの外部インターフェースにポートは現れない。

### 3. Remote but owned(自分が所有するリモート、ポート&アダプター)

ネットワークの境界を越えた、自分自身のサービス(マイクロサービス、内部 API)。シームに **ポート**(インターフェース)を定義する。深いモジュールがロジックを所有し、トランスポートは **アダプター** として注入される。テストはインメモリのアダプターを使う。本番は HTTP/gRPC/キューのアダプターを使う。

推奨の形: _「シームにポートを定義し、本番用の HTTP アダプターとテスト用のインメモリアダプターを実装する。こうすれば、ネットワークをまたいでデプロイされていても、ロジックは1つの深いモジュールに収まる。」_

### 4. True external(本物の外部、モック)

自分が制御していないサードパーティのサービス(Stripe、Twilio など)。深化したモジュールは、その外部依存を注入されたポートとして受け取る。テストはモックのアダプターを提供する。

## シームの規律

- **アダプターが1つなら、それは仮のシームである。アダプターが2つなら、本物のシームである。** 少なくとも2つのアダプター(典型的には本番用+テスト用)が正当化されない限り、ポートを導入しない。アダプターが1つだけのシームは、単なる間接参照にすぎない。
- **内部シーム vs 外部シーム。** 深いモジュールは、インターフェースにある外部シームに加えて、内部シーム(その実装にプライベートで、自分自身のテストが使うもの)を持つこともある。テストがそれを使っているというだけの理由で、内部シームをインターフェース越しに公開しない。

## テスト戦略: 積み重ねるのではなく、置き換える

- 浅いモジュールに対する古いユニットテストは、深化したモジュールのインターフェースでのテストが存在するようになった時点で無駄になる — 削除する。
- 深化したモジュールのインターフェースで新しいテストを書く。**インターフェースがテストの表面である。**
- テストは、内部状態ではなく、インターフェースを通して観察できる結果に対してアサートする。
- テストは内部のリファクタリングを生き延びるべきである — それらは実装ではなく振る舞いを記述する。実装が変わったときにテストも変えなければならないなら、それはインターフェースの先をテストしている。
