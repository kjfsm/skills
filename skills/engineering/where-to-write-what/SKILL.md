# 何をどこに書くか

**コードには How、テストには What、コミットログには Why、コードコメントには Why not。**

情報には **宛先** が 1 つある。同じ事実を 2 か所に書くと、片方だけ直る日が来て、残った方が嘘をつく。この規律が決めるのは「書くか書かないか」ではなく「どこに書くか」 — 書きたくなった情報は捨てずに、正しい宛先へ届ける。

残りの宛先はこの 4 本から派生する: JSDoc = 実行して確かめられない What、PR 本文 = レビュアーが読む Why、ADR = モジュールをまたぐ Why not、docs = 使う側の How。

## How — コード自体

説明したくなった内容は、まず命名・関数抽出・型で言えないか試す。言えたら、コメントの仕事は残らない。

判定テスト: **コメントを消して、コードだけを読む。失われる情報が無ければ、その情報の宛先はコードだった** — コードに語らせ、コメントは消す。

逐語的な説明(「〜を取得」「〜を更新」)がコメントに現れるのは、How を 2 回書いている合図である。

## What — テストコード

「この関数は何を保証するか」の宛先はテストである。散文で書いた仕様は実装が変わった日に嘘になるが、テストは嘘になった瞬間に落ちる。

- テスト名が仕様の文になっているか(`returns null when the cursor is past the last page`)
- 一つの assert が一つの保証に対応しているか
- 説明したくなった挙動が、まだテストされていない挙動ではないか — その場合の宛先はコメントではなくテストの追加である

テスト **内** のコメントは、テストコードにとっての Why not である — なぜこの入力なのか、この境界を緩めるとどんな利用が壊れるのか。4 本の柱はテストの中でも同じ形で効く。

## Why — コミットメッセージ

件名は変更の要約。本文は「これまでどうだったか → なぜ問題か → どうしたか」で、diff からは読めない部分 — 変更前の状態、動機、採らなかった選択肢 — に紙面を使う。

- バグ修正は、正しいとわかった仮説を書く — 次にデバッグする人が学べるように
- 対応する issue への参照(`#123`、`Closes #45`)を含める — レビューする側はここからスペックを辿る

## Why not — コメント

コメントが運ぶのは、コードをいくら読んでも出てこない情報である。どれも「なぜ素直な書き方ではないのか」の形をしている:

- 採らなかった素直な書き方と、それがだめな理由(「〜すると…が壊れるため、こうしている」)
- 外部の制約(API 仕様、RFC、プラットフォームの上限、ランタイムの挙動) — なぜこちらの都合で決められないか
- 不変条件と順序依存(「先に削除しないと UNIQUE 制約に当たる」) — なぜ別の順序ではだめか
- issue・ADR への参照 1 行(本文はそちらに置く)

書きたくなったものが別の宛先のものだったら、そちらへ届ける:

| 書きたくなったもの                           | 本当の宛先                                       |
| -------------------------------------------- | ------------------------------------------------ |
| 処理の逐語的な説明(「〜を取得」「〜を更新」) | コード自体(命名・抽出)                           |
| 「この関数は〜を返す」という仕様の説明       | テストコード                                     |
| 変更の経緯(「submit から button に変えた」)  | コミットメッセージ                               |
| 使わなくなったコード                         | git 履歴(そのまま削除する)                       |
| ファイルパス・目次・セクション見出し         | ファイルシステムとエディタが持っている(削除する) |

## JSDoc — 実行して確かめられない What

型と名前がすでに言っていることは 0 行で足りる。書くのは型に出ない契約のうち、**テストでは示せないもの** に限る:

- 単位・範囲・フォーマット(「JST 00:00」「hex エンコード」)
- null / undefined / 既定値が意味すること
- 副作用と呼び出し条件

具体例(`"残り2日"`)を書くなら 1 つだけ — フォーマットを一目で示すためのものであって、保証ではない。保証はテストが持つ。`@param` / `@returns` もタグ 1 つずつ同じ判定にかける。共有パッケージの公開 API は、名前に足す情報がある場合に限り概要 1 行(エディタのホバーで効く)。

## PR 本文 — レビュアーが読む Why

レビュアーがブランチを checkout せずに判断できるだけの文脈: 何が変わるか、どう確かめたか、どこから読み始めるか、UI ならスクリーンショット。squash マージ運用では PR 本文がそのままメインラインのコミット本文になる — その場合、コミットメッセージの基準がそのまま PR 本文の基準である。

## ADR — モジュールをまたぐ Why not

コメントの Why not が行やファイルの単位で効くのに対し、ADR は複数モジュールにまたがり後戻りしにくい判断を扱う。却下した代替案とその理由もここに書く。コードからは ADR 番号の参照 1 行で指す — 判断の本文を書き写すと、ADR を直した日にコメントが古くなる。

用語の定義と呼び方は用語集(`CONTEXT.md` など)へ。ADR が判断を、用語集が語彙を持つ。

## README / docs — 使う側の How

docs が運ぶのは動かし方であって、動き方ではない。リポジトリを渡された人がコードを読み始める **前** に要るもの — セットアップ、実行のしかた、運用時の判断 — に限られる。

判定テスト: **そのページを消して、clone した人が詰まるか。詰まらなければ消す。**

書きすぎはたいてい同じ形で現れる。どれも、実装が変わった日に真っ先に嘘になる:

| 書きすぎの形                         | 本当の宛先                                                       |
| ------------------------------------ | ---------------------------------------------------------------- |
| ディレクトリ構成・アーキテクチャ概観 | コード自体(読めば分かる。書くなら「なぜその形か」だけを ADR へ)  |
| API・オプション・型の一覧            | 型定義とスキーマ(写すと二重管理になる。生成できるものは生成する) |
| 個数・バージョン・網羅的な一覧       | 書かない(数えた結果ではなく、数え方を書く)                       |
| 設計判断の経緯                       | ADR                                                              |

## このスキルを呼ばずに効かせる

このスキルは呼ばれて初めて読まれる。だがコメントを書く場面でモデルは「迷った」と自覚しないので、自分からは呼ばない。毎回効いてほしいなら、コメントの判定はリポジトリの `CLAUDE.md` / `AGENTS.md` に **本文として常駐** していなければならない — `/setup-skills` がそれをリポジトリごとに一度書き込む。
