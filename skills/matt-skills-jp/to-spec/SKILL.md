# スペックにする

このスキルは、今の会話のコンテキストとコードベースの理解をもとにスペック(PRD として知られるドキュメントかもしれない)を作成する。ユーザーにインタビューは **しない** — すでに知っていることをまとめるだけ。

イシュートラッカーとトリアージラベルの語彙は、あなたにすでに渡されているはずである — なければ、`/setup-skills` を実行するようユーザーに伝える。

## 手順

1. まだ探索していなければ、リポジトリを探索してコードベースの現状を理解する。スペック全体を通してプロジェクトのドメイン用語集の語彙を使い、触れている領域にある ADR を尊重する。

2. 機能をテストするシームの見取り図を描く。新しいシームより既存のシームを優先する。可能な限り最も高いシームを使う。新しいシームが必要な場合は、できるだけ高い位置に提案する。コードベース全体にまたがるシームは少ないほどよい — 理想は1つである。

これらのシームがユーザーの期待と一致しているか確認する。

3. 下記のテンプレートを使ってスペックを書き、プロジェクトのイシュートラッカーへ公開する。テンプレートは **形** の見本であり、書く言語はリポジトリの既存文書に合わせる。`ready-for-agent` トリアージラベルを適用する — 追加のトリアージは不要。

## 問題文

ユーザーの視点から見た、ユーザーが直面している問題。

## 解決策

ユーザーの視点から見た、その問題への解決策。

## ユーザーストーリー

長い、番号付きのユーザーストーリーのリスト。各ユーザーストーリーは次の形式にすること:

1. As an <actor>, I want a <feature>, so that <benefit>

<user-story-example>
1. As a mobile bank customer, I want to see balance on my accounts, so that I can make better informed decisions about my spending
</user-story-example>

このユーザーストーリーのリストは非常に網羅的で、機能のあらゆる側面をカバーすること。

## 実装上の決定事項

下された実装上の決定事項のリスト。次のものを含められる:

- 構築・変更されるモジュール
- 変更されるそれらのモジュールのインターフェース
- 開発者からの技術的な確認事項
- アーキテクチャ上の決定
- スキーマの変更
- API の契約
- 具体的なやり取り

具体的なファイルパスやコードスニペットは含め **ない** こと。すぐに古くなってしまう可能性がある。

例外: プロトタイプが、プローズより正確に決定を表現するスニペット(ステートマシン、reducer、スキーマ、型の形)を生み出した場合は、関連する決定の中にそれをインラインで含め、プロトタイプ由来であることを簡潔に注記する。決定の要点が詰まった部分だけに削ること — 動くデモではなく、重要な部分だけでよい。

## テストに関する決定事項

下されたテストに関する決定事項のリスト。次を含めること:

- 良いテストとは何かの説明(内部実装の詳細ではなく、外部から見える振る舞いだけをテストする)
- どのモジュールがテストされるか
- そのテストの先例(コードベース内の同種のテストなど)

## 動作の証明

この機能が動いたと言える、**エンドツーエンドの1つの経路**。誰が何を操作し、何が観測できれば完了なのかを、実際に実行できる粒度で書く — 叩くエンドポイントと返るべきレスポンス、辿る画面遷移と見えるべき表示、走らせるコマンドと期待する出力など。

テストに関する決定事項がシームごとの合否を決めるのに対し、ここは機能が丸ごと1本通ることを決める。`/verification-loop` の観測が駆動するのはこの経路である。
