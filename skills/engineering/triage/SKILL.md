# Triage

プロジェクトのイシュートラッカー上のイシューを、トリアージロールという小さなステートマシンに沿って進める。

このリポジトリが外部からのプルリクエストを要望の受け口として扱っている場合(イシュートラッカーの設定を参照)、トリアージはそれらもカバーする: **PR とはコードが添付されたイシューである** — 同じロール、同じ状態、同じ機械であり、下記に「PR の場合」として印した数点の差異があるのみ。裸の `#42` は、トラッカーの設定に従ってイシューか PR に解決する。

トリアージ中にイシュートラッカーへ投稿されるコメントやイシューは、すべてこの免責事項で始まら **なければならない**:

```
> *This was generated by AI during triage.*
```

## ロール

2つの **カテゴリ** ロール:

- `bug` — 何かが壊れている
- `enhancement` — 新機能または改善

5つの **状態** ロール:

- `needs-triage` — メンテナーの評価待ち
- `needs-info` — 報告者からの追加情報待ち
- `ready-for-agent` — 仕様が固まっており、AFK エージェントの着手待ち
- `ready-for-human` — 人間による実装が必要
- `wontfix` — 対応しない

PR の場合、同じ状態が添付されたコードに対して読み替えられる: `ready-for-agent` はブリーフが添付されていてエージェントが差分に対して次の一手を打つべきことを意味し、`ready-for-human` は人間がマージする準備ができていることを意味する。

トリアージされたイシューは、それぞれ正確に1つのカテゴリロールと1つの状態ロールを持つべきである。状態ロールが競合する場合は、他の何かをする前にそれを指摘し、メンテナーに尋ねる。

これらは正規のロール名である — イシュートラッカーで実際に使われるラベル文字列は異なる場合がある。この対応付けはあなたにすでに渡されているはずである — なければ `/setup-skills` を実行すること。

状態遷移: ラベルのないイシューは通常まず `needs-triage` になる。そこから `needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix` のいずれかへ移る。`needs-info` は報告者が返信すると `needs-triage` に戻る。メンテナーはいつでも上書きできる — 通常と異なる遷移に見える場合は指摘し、進める前に尋ねる。

## 呼び出し

メンテナーが `/triage` を呼び出し、自然言語で望むことを記述する。その要求を解釈して行動する。例:

- 「対応が必要なものを見せて」
- 「#42 を見てみよう」(イシューまたは PR)
- 「#42 を ready-for-agent に移して」
- 「エージェントが着手できるものは何?」

## 対応が必要なものを見せる

イシュートラッカーに問い合わせ、3つのバケットを古い順に提示する:

1. **ラベルなし** — 一度もトリアージされていない。
2. **`needs-triage`** — 評価が進行中。
3. **前回のトリアージメモ以降に報告者の動きがあった `needs-info`** — 再評価が必要。

PR がスコープに含まれる場合は、これらのバケットに外部からの PR も含め、各行に `[PR]` または `[issue]` のタグを付ける。この発見処理は _外部からの_ PR だけを表面化させる(誰が外部にあたるかはトラッカーの設定が定義する) — コラボレーターの進行中の PR はトリアージ作業ではない。このフィルタは発見時にのみ適用される。明示的に名指しされた PR は、作者に関わらず常にトリアージされる。

件数と、項目ごとの1行要約を示す。選ぶのはメンテナーに任せる。

## 特定のイシューまたは PR をトリアージする

1. **コンテキストを集める。** イシューまたは PR 全体(本文、コメント、ラベル、作者、日付。PR の場合は差分も)を読む。既に解決済みの問いを再度尋ねずに済むよう、過去のトリアージメモがあれば読み解く。プロジェクトのドメイン用語集を使ってコードベースを探索し、その領域にある ADR を尊重する。コードベースに対して2つのチェックを行う: (a) **重複** — 要求された振る舞いの既存実装を、(要求の言い回しだけでなく)ドメイン概念で検索し、どこを調べたかを報告する。見つかった場合、それはすでに実装済みの `wontfix` である(手順5)。(b) **過去の却下** — `.out-of-scope/*.md` を読み、この要求に似たものがあれば表面化させる。

2. **推奨する。** カテゴリと状態についての推奨を、理由とともにメンテナーに伝える。加えて、要求に関連する簡潔なコードベースの要約 — すでに実装されているかどうかを含む — も伝える。指示を待つ。

3. **主張を検証する。** グリリングを始める前に、その主張が成り立つか確認する。バグであれば、報告者の手順から再現する。PR であれば、差分が主張通りに動くことを確認する — チェックアウトし、関連するテストやコマンドを実行する。何が起きたかを報告する: 確認できた(コードパスつき)、失敗した、または情報が不十分(`needs-info` の強いシグナル)。確認が取れた検証は、はるかに強力なエージェントブリーフになる。

4. **必要ならグリリングする。** 要求を肉付けする必要がある場合は、`/grilling` と `/domain-modeling` のスキルを一緒に実行する — 一度に1つの問いずつ形にしていき、ドメイン用語を研ぎ澄まし、決定が下されるたびに `CONTEXT.md`/ADR をその場で更新する。

5. **結果を適用する:**
   - `ready-for-agent` — エージェントブリーフのコメントを投稿する([AGENT-BRIEF.md](AGENT-BRIEF.md))。
   - `ready-for-human` — エージェントブリーフと同じ構造だが、なぜ委任できないか(判断が必要、外部アクセスが必要、デザイン上の決定、手動テストなど)を書き添える。
   - `needs-info` — トリアージメモを投稿する(下記のテンプレート)。
   - `wontfix` — クローズする。コメントの内容は _理由_ によって変わる:
     - **すでに実装済み** — その変更はすでにコードベースに存在する。どこにあるかを示す。`.out-of-scope/` には **書かない**(その KB は _却下された_ 要求のためのものであり、実装済みのもののためではない)。
     - **却下(バグ)** — 丁寧に説明したうえでクローズする。
     - **却下(拡張)** — `.out-of-scope/` に書き、コメントからそれへリンクしたうえでクローズする([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md))。
   - `needs-triage` — そのロールを適用する。部分的な進捗があれば任意でコメントする。

## 状態のクイック上書き

メンテナーが「#42 を ready-for-agent に移して」と言った場合は、それを信頼して直接そのロールを適用する。これから行うこと(ロールの変更、コメント、クローズ)を確認したうえで実行する。グリリングは省略する。グリリングセッションなしで `ready-for-agent` に移す場合は、エージェントブリーフを書きたいかどうか尋ねる。

## needs-info テンプレート

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

グリリング中に解決したことはすべて「established so far」の下に記録し、作業が失われないようにする。質問は具体的で行動につながるものにすること。「もっと情報をください」のようなものにはしない。

## 以前のセッションを再開する

イシューや PR に過去のトリアージメモがある場合は、それを読み、報告者が未解決の質問に答えているかどうかを確認し、続ける前に最新の状況を提示する。解決済みの問いを再度尋ねない。
