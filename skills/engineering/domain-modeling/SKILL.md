# Domain Modeling

設計しながら、プロジェクトのドメインモデルを能動的に構築し研ぎ澄ます。これは _能動的な_ 規律である — 用語に異議を唱え、エッジケースのシナリオを考案し、それらが固まった瞬間に用語集と決定を書き留める。(語彙のために `CONTEXT.md` を単に _読む_ ことはこのスキルではない — それはどのスキルでもできる1行程度の習慣である。このスキルは、モデルを単に消費するのではなく、変更するときのためのものである。)

## ファイル構造

ほとんどのリポジトリは単一のコンテキストを持つ:

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

ルートに `CONTEXT-MAP.md` が存在する場合、そのリポジトリは複数のコンテキストを持つ。マップはそれぞれがどこにあるかを指し示す:

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← system-wide decisions
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← context-specific decisions
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

ファイルは遅延生成する — 書くべきことがあるときだけ。`CONTEXT.md` が存在しなければ、最初の用語が解決したときに作る。`docs/adr/` が存在しなければ、最初の ADR が必要になったときに作る。

## セッション中に

### 用語集に照らして異議を唱える

ユーザーが `CONTEXT.md` の既存の言葉と矛盾する用語を使ったら、すぐに指摘する。「あなたの用語集は『cancellation』を X と定義していますが、あなたは Y を意味しているように見えます — どちらですか?」

### 曖昧な言葉を研ぎ澄ます

ユーザーが曖昧、あるいは多義的な用語を使ったら、正確な正規の用語を提案する。「『account』と言っていますが、Customer のことですか、それとも User のことですか? それらは別物です。」

### 具体的なシナリオを議論する

ドメインの関係性が議論されているときは、具体的なシナリオでストレステストする。エッジケースを突くシナリオを考案し、概念の間の境界についてユーザーに正確さを求める。

### コードと照合する

ユーザーが何かの動作について述べたら、コードがそれと一致するか確認する。矛盾を見つけたら、それを表面化させる: 「あなたのコードは Order 全体をキャンセルしていますが、あなたは今、部分的なキャンセルが可能だと言いました — どちらが正しいですか?」

### CONTEXT.md をその場で更新する

用語が解決したら、その場で `CONTEXT.md` を更新する。まとめて後回しにせず、起きた端から記録する。[CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) の形式を使う。

`CONTEXT.md` は実装の詳細を完全に含まないべきである。`CONTEXT.md` をスペックや、走り書きや、実装上の決定を保管する場所として扱わない。それは用語集であり、それ以外の何物でもない。

### ADR は控えめに提案する

次の3つすべてが真であるときにのみ、ADR の作成を提案する:

1. **後戻りしにくい** — 後で考えを変えるコストが無視できない
2. **文脈なしでは意外である** — 将来の読者は「なぜこうしたのだろう?」と疑問に思うだろう
3. **本物のトレードオフの結果である** — 本当に複数の選択肢があり、特定の理由で1つを選んだ

3つのうちどれか1つでも欠けていたら、ADR は省略する。[ADR-FORMAT.md](./ADR-FORMAT.md) の形式を使う。
