# 機能を提案する

既存のアプリに **足すと便利な機能** の候補を出す。直す・整える提案は他が持っている — 構造は `/mattpocock-skills:improve-codebase-architecture`、見た目と操作感は `web-design-guidelines` と `baseline-ui`、不具合は `/mattpocock-skills:diagnosing-bugs`。ここでは、今はできないことをできるようにする提案だけを扱う。

提案の価値は根拠で決まる。根拠のない提案は「どのアプリにも言える提案」になる — 検索・通知・エクスポート・ダークモード。根拠は3つで、1つ目が欠けたら先へ進まない:

1. **目的のファイル** — 誰が、何のために使うか。何をしないか
2. **コードから読める「できること」と欠け** — 画面・API・データモデル
3. **利用ログ・本番ログ** — あれば

## 手順

### 1. 目的を読む

`docs/product.md` を読む。無ければ別の名前で同じ中身を持つもの(README の冒頭、`CONTEXT.md`、`docs/` の概要、ADR、ロードマップのイシュー)を探す。**誰が・何のために・何をしないか** の3つが揃っていれば次へ進む。

ロードマップの「後回し」は「しない」ではない。下書きでは「後回し」と印を付けて分けておき、どちらかはユーザーが決める。

揃っていなければ、ユーザーに短く聞いて `docs/product.md` を書く:

- README・`CONTEXT.md`・画面の文言から、3つの下書きを1行ずつ起こす
- 下書きを見せ、直してもらう。**何をしないか** はコードから読めないので、下書きが空でも必ず1行は聞く
- 直った3つを、[PRODUCT-TEMPLATE.md](PRODUCT-TEMPLATE.md) の形で `docs/product.md` に書く。コミットはしない — 書いたことを伝え、残すかはユーザーが決める

コードから推した目的だけで先へ進まない。コードから推した目的に対してコードの欠けを探すと、目的が欠けをそのまま映すので、提案が循環する。

完了: 誰が・何のために・何をしないかを、ユーザーが認めた文として持っている。

### 2. できることを棚卸しする

ユーザーが画面・機能・利用者を名指ししたら、そこから始める。無ければ全体を見る。

用語集(`GLOSSARY.md` か `CONTEXT.md`)と ADR を先に読む。そのあと、コードから次を一覧にする。広いアプリなら `Explore` サブエージェントに押し出し、一覧だけを受け取る。

「無い」は推さずに確かめる — 画面や API が無いと言うときは、その語で grep して出ないことを見てから書く。確かめられなかった欠けには「未確認」と付ける。

- **画面** — ルートと、各画面で利用者ができる操作
- **API** — エンドポイントと、それを呼ぶ画面
- **データモデル** — テーブルと列、それを書く経路と読む経路
- **時間で動くもの** — cron・キュー・通知・メール

一覧の上で **欠け** を探す。欠けは次の形で現れる:

- **書くだけで読まれない** — 保存しているのに、どの画面にも出ない列。利用者が見たいはずの値に限る — `user_agent` や監査用の時刻は死に列であって欠けではない
- **片道の操作** — 作れるが直せない・取り消せない・まとめて扱えない
- **行き止まりの状態** — 状態の列にあるのに、そこへ移る・そこから出る操作が無い
- **手作業の跡** — `scripts/` の管理用スクリプト、`TODO`、手で DB を触る手順を書いた docs。利用者が誰かに頼んでいることの印である
- **言葉だけの概念** — 用語集にあるのに、画面にも API にも無い

`git log` と `CHANGELOG`、開いているイシューも読む。何度も手が入る画面は、利用者が実際に使っている画面である。イシューに要望として出ているだけの欠けは、そのイシューを根拠に足す。

完了: 画面・API・データモデル・時間で動くものの一覧と、欠けの一覧を持っている。各欠けにファイルの場所が付いている。

### 3. 利用ログを読む

ログを読める手段(Workers Observability の MCP、`wrangler tail`、アプリ自身の集計テーブル)があれば、読み取りだけで当たる: よく叩かれる経路と叩かれない経路、利用者が踏むエラー、同じ操作の繰り返し。経路は ID を伏せたルートの形(`/events/:id`)でまとめて数える。サンプリングされたログなら件数ではなく経路どうしの比で読む。読めなければ、読まなかったと記録して次へ進む。

完了: ログから拾った数字があるか、読まなかったことが記録されている。

### 4. 候補を選り分ける

欠けを、目的の文と突き合わせて候補にする。1つの候補は **目的の1文** と **コードの場所1つ以上** を根拠に持つ。次に当たるものは落とす:

- **目的の文を引けない** — 誰の、何のための機能かを `docs/product.md` の文で言えない
- **何をしないかに触れる** — 目的のファイルが「しない」と書いたもの
- **名前を入れ替えても通る** — 候補の本文のアプリ名を、同じ種類の別のアプリに入れ替えても文が成り立つ。それはこのアプリの提案ではない。「コメントを編集できる」はコメントのあるどのアプリでも通る。「休んでいるメンバーを催促の母数から外せる」は、催促を任せると目的に書いたアプリでしか通らない
- **既に詰めてある** — 設計まで書かれたイシューがある。要望が出ているだけなら落とさず、根拠に数える
- **他の領分** — 構造の整理、見た目、不具合。コードが自分の意図(名前・コメント・テスト)と食い違っていれば不具合、意図どおりに動いて利用者を行き止まりに置くなら機能の欠けである

数を揃えない。根拠を持つ候補が1つなら1つ、0なら0と報告する。

各候補に強さを付ける: `Strong`(目的の文・コード・ログの3つが同じ方向を指す — ログが利用者の回避やつまずき、つまり同じ操作の繰り返し・エラー・行き止まりの経路を示している。隣の画面が見られている数だけでは指さない)、`Worth exploring`(目的の文とコード)、`Speculative`(目的の文はあるが、欠けの読みに自信が無い)。大きさも付ける: `S`(既存の画面に操作1つ)、`M`(画面か API を足す)、`L`(データモデルを変える)。

完了: 残った候補のどれもが、目的の文1つとコードの場所1つ以上を引用できる。

### 5. HTML レポートで見せる

自己完結の HTML を OS の一時ディレクトリに書く — リポジトリには何も置かない。`$TMPDIR`、無ければ `/tmp` の下に `feature-proposals-<timestamp>.html` を作る。開いて(Linux は `xdg-open`、WSL は `wslview`、macOS は `open`)、絶対パスを伝える。

書き方は [HTML-REPORT.md](HTML-REPORT.md) にある。

まだ設計しない — 画面の配置も API の形も、選ばれたあとで詰める。書き終えたら、どれを詰めたいかを聞いて止まる。

### 6. 選んだ1件を詰める

ユーザーが1件選んだら、`grilling` スキルを呼んで、決めることの木を一緒に下る: 誰がいつ使うか、今その人はどう回避しているか、最小の形はどれか、データモデルを変えずに済むか、何をしないか。

決まったものはその場で残す。`domain-modeling` スキルを呼んで用語を揃える:

- **用語集に無い概念を名付けた** — 用語集に足す
- **候補が根拠のある理由で却下された** — `docs/product.md` の「何をしないか」に理由と一緒に足すかを聞く。次の実行が同じ候補を出さないのは、そこに書かれたものだけである。「今は要らない」のような一時の理由なら足さない
- **詰め終えた** — 実装へ進むなら、ユーザーに `/mattpocock-skills:to-spec` を実行してもらう
