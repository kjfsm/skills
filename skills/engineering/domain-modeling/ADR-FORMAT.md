# ADR の形式

テンプレートは **形** の見本である。書く言語はリポジトリの既存文書に合わせる — 見本が英語であることは、英語で書く理由にならない。

ADR は `docs/adr/` に置かれ、`0001-slug.md`、`0002-slug.md` のように連番を使う。

`docs/adr/` ディレクトリは遅延生成する — 最初の ADR が必要になったときだけ。

## テンプレート

```md
# {決定の短いタイトル}

{1〜3文: どんな背景で、何を決め、なぜそうしたか。}
```

これだけである。ADR は1段落でもよい。価値があるのは、決定が下された _こと_ と、その _理由_ を記録することであり、セクションを埋めることではない。

## 任意のセクション

本当に価値を加えるときだけ含める。ほとんどの ADR はこれらを必要としない。

- **Status** の frontmatter(`proposed | accepted | deprecated | superseded by ADR-NNNN`) — 決定が再検討されるときに役立つ
- **Considered Options** — 却下した代替案を覚えておく価値があるときだけ
- **Consequences** — 自明でない波及効果を指摘する必要があるときだけ

## 番号付け

`docs/adr/` を確認して既存の最大番号を見つけ、1を足す。

## いつ ADR を提案するか

次の3つすべてが真でなければならない:

1. **後戻りしにくい** — 後で考えを変えるコストが無視できない
2. **文脈なしでは意外である** — 将来の読者はそのコードを見て「一体なぜこんなやり方をしたのだろう?」と思うだろう
3. **本物のトレードオフの結果である** — 本当に複数の選択肢があり、特定の理由で1つを選んだ

決定が簡単に覆せるなら省略する — どうせ覆すことになる。意外でないなら、誰もなぜかと疑問に思わない。本物の代替案がなかったなら、「当たり前のことをした」以上に記録することは何もない。

### 何が該当するか

- **アーキテクチャの形。** 「モノレポを使っている。」「書き込みモデルはイベントソーシングで、読み込みモデルは Postgres に投影されている。」
- **コンテキスト間の統合パターン。** 「Ordering と Billing は同期の HTTP ではなく、ドメインイベント経由で通信する。」
- **ロックインを伴う技術選定。** データベース、メッセージバス、認証プロバイダ、デプロイ先。すべてのライブラリではなく、置き換えに四半期かかるようなものだけ。
- **境界とスコープの決定。** 「Customer データは Customer コンテキストが所有し、他のコンテキストは ID でのみ参照する。」明示的な「しない」は「する」と同じくらい価値がある。
- **明白な道筋からの意図的な逸脱。** 「X という理由で ORM ではなく手書きの SQL を使っている。」まともな読者が逆を想定してしまうようなもの全般。これらは、次のエンジニアが意図的だったものを「修正」してしまうのを防ぐ。
- **コードから見えない制約。** 「コンプライアンス要件のため AWS を使えない。」「パートナーの API 契約のため応答時間は200ms未満でなければならない。」
- **却下が自明でない場合の、却下された代替案。** 微妙な理由で GraphQL を検討したうえで REST を選んだのなら、それを記録する — そうしないと、半年後にまた誰かが GraphQL を提案することになる。
