ユーザーが渡す固定した基点と `HEAD` の間の差分を二軸でレビューする:

- **Standards** — コードはこのリポジトリの明文化されたコーディング標準に沿っているか?
- **Spec** — コードは元となったイシュー/PRD/スペックを忠実に実装しているか?

両方の軸を **並列サブエージェント** として実行することで互いのコンテキストを汚染しないようにし、その後このスキルがそれぞれの発見をまとめる。

イシュートラッカーはあなたにすでに渡されているはずである — `docs/agents/issue-tracker.md` がなければ `/setup-skills` を実行すること。

## 手順

### 1. 固定した基点を定める

ユーザーが言ったものが固定した基点である — コミットの SHA、ブランチ名、タグ、`main`、`HEAD~5` など。指定されていなければ尋ねる。

差分コマンドを一度だけ確定する: `git diff <fixed-point>...HEAD`(3つのドットにすることで、比較対象がマージベースになる)。`git log <fixed-point>..HEAD --oneline` によるコミット一覧もメモしておく。

先に進む前に、その固定した基点が解決できること(`git rev-parse <fixed-point>`)と、差分が空でないことを確認する。不正な参照や空の差分は、ここで失敗させるべきであり、2つの並列サブエージェントの中で失敗させるべきではない。

### 2. スペックの出所を特定する

元となったスペックを、次の順で探す:

1. コミットメッセージ内のイシュー参照(`#123`、`Closes #45`、GitLab の `!67` など) — `docs/agents/issue-tracker.md` にあるワークフロー経由で取得する。
2. ユーザーが引数として渡したパス。
3. ブランチ名や機能と一致する、`docs/`、`specs/`、`.scratch/` 配下の PRD/スペックファイル。
4. 何も見つからなければ、ユーザーにスペックの場所を尋ねる。ないと言われた場合は、**Spec** サブエージェントはスキップして「スペックが利用できない」と報告する。

### 3. 標準の出所を特定する

`CODING_STANDARDS.md` や `CONTRIBUTING.md` など、コードをどう書くべきかをリポジトリ内で明文化しているもの全般。

リポジトリが明文化しているものに加えて、Standards の軸は常に下記の **スメルの基準線** を持ち運ぶ — リポジトリが何も明文化していない場合にも適用される、Fowler のコードスメル(『リファクタリング』第3章)の固定セットである。これには2つのルールが結びつく:

- **リポジトリの規約が優先される。** 明文化されたリポジトリの標準は常に勝つ。基準線が指摘するものをその標準が認めている場合は、そのスメルは抑制する。
- **常に判断の余地がある。** 各スメルはラベル付けされたヒューリスティック(「Feature Envy の疑いあり」)であり、決してハードな違反ではない。そしてここでの他の標準と同様、すでにツールが強制しているものはスキップする。

各スメルは *それが何か* → *どう直すか* という形式で読む。これを差分に照らし合わせる:

- **Mysterious Name(謎の名前)** — 何をするか、何を保持するかを明かさない、関数・変数・型の名前。→ リネームする。誠実な名前が出てこないなら、設計が曖昧である。
- **Duplicated Code(重複コード)** — 同じロジックの形が、変更の中の複数のハンクやファイルに現れる。→ 共有される形を抽出し、両方からそれを呼ぶ。
- **Feature Envy(機能への横恋慕)** — 自分自身のデータより他のオブジェクトのデータに多く踏み込むメソッド。→ そのメソッドを、それが恋い焦がれているデータの側へ移す。
- **Data Clumps(データの群れ)** — 同じ少数のフィールドや引数がいつも一緒に移動する(生まれたがっている型)。→ それらを1つの型にまとめ、それを渡す。
- **Primitive Obsession(基本型への執着)** — 独自の型を持つべきドメイン概念の代わりをしている、プリミティブや文字列。→ その概念に小さな専用の型を与える。
- **Repeated Switches(繰り返される分岐)** — 同じ型に対する同じ `switch`/`if` の連鎖が、変更の中で繰り返し現れる。→ ポリモーフィズムに置き換えるか、両方の箇所が共有する1つのマップに置き換える。
- **Shotgun Surgery(散弾銃手術)** — 1つの論理的な変更が、差分の中の多くのファイルにまたがる散発的な編集を強いる。→ 変わるものたちを1つのモジュールにまとめる。
- **Divergent Change(分岐する変更)** — 1つのファイルやモジュールが、いくつもの無関係な理由で編集される。→ 各モジュールが1つの理由でだけ変わるように分割する。
- **Speculative Generality(思弁的な汎用性)** — スペックにない需要のために追加された抽象化、パラメータ、フック。→ それを削除する。本当に必要になるまでインライン化しておく。
- **Message Chains(メッセージの連鎖)** — 呼び出し元が依存すべきでない、長い `a.b().c().d()` のたどり方。→ その経路を、最初のオブジェクトの1つのメソッドの裏に隠す。
- **Middle Man(仲介人)** — ほとんど単に委譲するだけのクラスや関数。→ それを取り除き、本当の対象を直接呼ぶ。
- **Refused Bequest(拒否された遺産)** — 継承したもののほとんどを無視するか上書きする、サブクラスや実装。→ その継承をやめ、コンポジションを使う。

### 4. 両方のサブエージェントを並列に起動する

2つの `Agent` ツール呼び出しを含む1つのメッセージを送る。両方とも `general-purpose` サブエージェントを使う。

**Standards サブエージェントのプロンプト** — 次を含める:

- 完全な差分コマンドとコミット一覧。
- 手順3で見つけた標準の出所ファイルの一覧、**さらに手順3のスメルの基準線を全文** 貼り付けたもの — サブエージェントはそれ以外にそこへアクセスする手段がない。
- 依頼内容: 「該当する場合はファイル/ハンクごとに報告してください — (a) 差分が明文化された標準に違反しているすべての箇所: その標準(ファイルとルール)を引用すること。(b) 見つけた基準線スメルすべて: 名前を挙げ、該当ハンクを引用すること。ハードな違反と判断の余地があるものを区別してください — 明文化された標準への違反はハードな場合がありますが、基準線スメルは常に判断の余地があり、明文化されたリポジトリの標準は基準線より優先されます。ツールが強制しているものはスキップしてください。400語以内で。」

**Spec サブエージェントのプロンプト** — 次を含める:

- 差分コマンドとコミット一覧。
- スペックのパスまたは取得済みの内容。
- 依頼内容: 「報告してください: (a) スペックが求めた要件のうち欠けているか一部しか実装されていないもの、(b) 差分の中にある、求められていなかった振る舞い(スコープの逸脱)、(c) 実装されているように見えるが実装が誤って見える要件。それぞれの発見についてスペックの該当行を引用してください。400語以内で。」

スペックが見つからない場合は Spec サブエージェントをスキップし、最終レポートにその旨を記す。

### 5. 集約する

2つのレポートを、そのまま、あるいは軽く整えたうえで `## Standards` と `## Spec` の見出しの下に提示する。発見事項を統合したり順位付けし直したりは **しない** — 2つの軸は意図的に分けられている(_なぜ二軸なのか_ を参照)。

最後に1行の要約をつける: 各軸の発見件数の合計と、(あれば)_それぞれの軸の中で_ 最悪の問題。軸をまたいで単一の勝者を選ばないこと — それは、この分離がまさに防ごうとしている再順位付けである。

## なぜ二軸なのか

ある変更は、一方の軸を通っても、もう一方は失敗しうる:

- あらゆる標準に従っているが、間違ったものを実装しているコード → **Standards は合格、Spec は不合格。**
- イシューが求めた通りに正確に動くが、プロジェクトの規約を破っているコード → **Spec は合格、Standards は不合格。**

これらを別々に報告することで、一方の軸がもう一方を覆い隠してしまうのを防ぐ。
