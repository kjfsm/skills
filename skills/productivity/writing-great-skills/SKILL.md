スキルは、確率的なシステムから決定性を絞り出すために存在する。**予測可能性(Predictability)** — エージェントが毎回同じ出力を生むのではなく、毎回同じ _プロセス_ を取ること — が根本的な美徳であり、以下のすべてのレバーはそれに仕える。

**太字の用語** は [`GLOSSARY.md`](GLOSSARY.md) で定義されている。完全な意味はそちらを参照。

## Invocation(呼び出し)

異なるコストを天秤にかける、2つの選択肢:

- **モデル呼び出し型(model-invoked)** のスキルは **description** を保持し、エージェントが自律的にそれを発火でき、_かつ_ 他のスキルもそれに到達できる(自分でその名前を入力することもできる)。これは **context load(コンテキスト負荷)** に寄与する — description は毎ターン、ウィンドウの中に居座る。仕組み: `disable-model-invocation` を省略し、豊富なトリガー表現("Use when the user wants…, mentions…")を持つモデル向けの description を書く。
- **ユーザー呼び出し型(user-invoked)** のスキルは description をエージェントの到達範囲から取り除く: あなたがその名前を入力したときだけ、あなただけがそれを呼び出せる — そして他のどのスキルもできない。コンテキスト負荷はゼロだが、代わりに **cognitive load(認知負荷)** を消費する: それが存在することを覚えていなければならない索引は _あなた_ である。仕組み: `disable-model-invocation: true` を設定する。`description` は人間向けになる — トリガーのリストを取り除いた、1行の要約。

モデル呼び出しを選ぶのは、エージェントが自力でそのスキルに到達しなければならないとき、あるいは他のスキルが到達しなければならないときだけにする。手で発火する以外に決して使われないなら、ユーザー呼び出し型にして、コンテキスト負荷を支払わない。

ユーザー呼び出し型のスキルが覚えきれないほど増えたときは、その積み上がった認知負荷を **ルータースキル(router skill)** で治療する: 他のスキルを名指しし、それぞれにいつ手を伸ばすべきかを示す、1つのユーザー呼び出し型のスキル。

## description を書く

モデル呼び出し型の **description** は2つの仕事をする — そのスキルが何であるかを述べ、それを発火させるべき **分岐(branches)** を列挙する。すべての単語が **context load(コンテキスト負荷)** を増やすので、description は本文よりもさらに厳しい刈り込みに値する:

- **スキルの先導語を前面に出す** — description は、その呼び出しの仕事をする場所である。
- **分岐ごとに1つのトリガー。** 単一の分岐を言い換えただけの同義語は **重複(duplication)** である — 「TDD で機能を構築する…テストファーストの開発を求める」は、1つの分岐が2度書かれたものである。それらを畳み込み、本当に別個の分岐だけを残す。
- **すでに本文にある固有の説明は削る。** description はトリガーと、「他のスキルが…を必要とするとき」という到達節だけに留める。

## Information hierarchy(情報階層)

スキルは、自由に混ざり合う2つのコンテンツの種類 — **steps(ステップ)** と **reference(リファレンス)** — から成る: スキルはすべてステップでも、すべてリファレンスでも、両方でもよい。核心となる決定は、どちらを使うか、そしてそれぞれをエージェントがどれだけ即座に必要とするかで順位付けされた階段である **information hierarchy(情報階層)** のどこに置くかである:

1. **スキル内のステップ** — `SKILL.md` の中の順序立った行動、最優先の層: エージェントが何を、どの順で行うか。各ステップは、作業が完了したことをエージェントに伝える条件である **completion criterion(完了基準)** で終わる。それを _確認可能_(エージェントは完了と未完了を見分けられるか?)にし、重要な場面では _網羅的_(「変更リストを作る」ではなく「変更されたすべてのモデルを漏れなく確認する」)にする — 曖昧な基準は **premature completion(早すぎる完了)** を招く。
2. **スキル内のリファレンス** — `SKILL.md` の中の定義、ルール、事実で、必要に応じて参照される。しばしば正当にフラットな並列集合である(あるレビューのすべてのルールが1段に並ぶ)— これは良い配置であり、悪い兆候ではない。_このスキルはすべてリファレンスである。_
3. **外部リファレンス** — `SKILL.md` の外の別ファイルに押し出されたリファレンスで、**context pointer(コンテキストポインタ)** を通じて到達し、そのポインタが発火したときだけ読み込まれる。(`GLOSSARY.md` のような、まだそのスキルの一部である _開示された_ リファレンスから、スキルシステムの外に存在し、どのスキルも指し示せる完全な **外部リファレンス(external reference)** まで幅がある。)

要求度の高い完了基準は、スキルがステップを持つかどうかに関わらず、徹底した **legwork(実作業)** — エージェントが作業の中で行う掘り下げ — を駆動する。「すべてのルールが適用された」がフラットなリファレンスを縛るのは、「すべてのステップが完了した」が手順を縛るのとまったく同じだからである。

押し下げが少なすぎると上部が肥大化し、押し下げすぎるとエージェントが本当に必要とする資料を隠してしまう。その緊張関係こそが、決定のすべてである。

**progressive disclosure(段階的開示)** とは、階段を下ることである — `SKILL.md` の外、リンクされたファイルへ — こうして上部を読みやすく保つ。仕組み: スキルのフォルダの中にある、その中身にちなんで名付けられたリンク先の `.md` ファイル(このスキルは、その完全な定義を `GLOSSARY.md` に開示している)。あるスキルは複数の使われ方をすることがあり、それぞれ別個の使われ方が **分岐(branch)** である — 実行ごとに、そのスキルを通る異なる経路を取る。分岐は最もクリーンな開示の判定基準である: すべての分岐が必要とするものはインラインにし、一部の分岐しか到達しないものはポインタの裏に押し込む。**context pointer(コンテキストポインタ)** の _文言_ こそが、その対象ではなく、エージェントがいつ、どれだけ確実にその資料に到達するかを決める。

階段が、ある部分が _どれだけ下に_ 位置するかを決めるのに対し、**co-location(併置)** は、そこに来たときに _何が隣にあるか_ を決める: ある概念の定義、ルール、注意点を、散らばらせるのではなく1つの見出しの下にまとめ、一部を読むとその隣接部分もついてくるようにする。

第3のコンテンツの種類である **executable(実行可能物)** は、この階段に段を持たない。階段に乗るのはそれを呼ぶ1行だけで、コードの中身は — 実行させるかぎり — 一度もコンテキストに乗らない。読ませるつもりで同梱したときだけ、それは **リファレンス** として階段に戻ってくる。_散文か、コードか_ を参照。

## いつ分割するか

**granularity(粒度)** とは、スキルをどれだけ細かく分けるかであり、それぞれの切り分けは2種類の負荷のどちらかを消費するので、その切り分けに見合うときにだけ分割する。2つの切り口:

- **呼び出し方式による分割** — それ自体を発火させるべき明確な **leading word(先導語)** がある、あるいは他のスキルがそれに到達しなければならないとき、**モデル呼び出し型(model-invoked)** のスキルを切り出す。新しく常時読み込まれる **description** のために **context load(コンテキスト負荷)** を支払うので、その独立した到達可能性が見合うものでなければならない。
- **手順による分割** — この先にあるステップ(あるステップの **post-completion steps(完了後のステップ)**)が、エージェントに目の前のステップを急がせる誘惑になる(**premature completion(早すぎる完了)**)とき、一連の **steps(ステップ)** を分割する。それらを視界の外に置くことで、エージェントは今のタスクにより多くの **legwork(実作業)** を行うようになる。

## 散文か、保証か

スキルの散文は勧告である — エージェントの注意を通って効くので、確率的に守られる。ハーネスのフックは **guarantee(保証)** である — ハーネスが実行するので、注意を通らない。

判定基準: それは **毎回、例外なく** 起きなければならないか? そうならフックであり、スキルの行ではない。編集のたびのフォーマット、危険なコマンドのブロック、ターンを終える前のチェック — どれも散文で頼めば大抵守られ、フックにすれば必ず守られる。

これで **no-op(ノーオプ)** の処方が2つになる。デフォルトで守られている行は **削除** する。守られなければ困るのに散文では守りきれない行は **フックへ移す** — その行はスキルから消えるが、振る舞いは残る。

## 散文か、コードか

**executable(実行可能物)** — スキルのフォルダに同梱され、エージェントが実行するスクリプト — は、散文が苦手な2つの仕事を引き受ける。

- **決定的である。** 手続きを散文で書けば、エージェントは実行のたびにそれを書き直し、そのたびに少しずつ違うものが出てくる。スクリプトは毎回同じ答えを返す — **predictability(予測可能性)** に直接効く。
- **安い。** リストの並べ替えをトークン生成で近似するのは、並べ替えを1本走らせるより高い。しかも実行されるコードは、コンテキストに一度も乗らない。

判定基準: エージェントが **毎回ほぼ同じコードを書いている** なら、それは同梱物になりたがっている。同梱すれば、散文に残るのは呼び出し方1行だけになる。

同梱物には2つの読まれ方があり、どちらを意図しているかは **context pointer(コンテキストポインタ)** の文言が決める:

- **実行させる** — 「`./scripts/check-log-hygiene.sh` で差分を検査する」。中身は読まれない。これが既定である。
- **読ませる** — 「`loop.template.sh` を写して手順を埋める」。写して埋めるひな形か、やり方を示す作例。この場合それは **reference(リファレンス)** であり、コードの形をしているだけである。

## 刈り込み

各意味を **single source of truth(唯一の信頼できる情報源)** に保つ: 1つの権威ある場所に置き、振る舞いを変えることが1か所の編集で済むようにする。

すべての行について **relevance(関連性)** を確認する: それはいまだにそのスキルの動作に関わっているか?

それから、行単位だけでなく文単位で **no-ops(ノーオプ)** を狩る: 各文を単独で取り出してノーオプの判定を行い、失敗したら単語を削るのではなく文全体を削除する。積極的であること — 判定に失敗したプローズのほとんどは、書き直すのではなく削除すべきである。

## 先導語

**leading word(先導語)** とは、モデルの事前学習にすでに存在する、コンパクトな概念であり、エージェントはそのスキルを実行しながらそれで考える(例: _lesson_、_fog of war_、_tracer bullets_)。文章全体を通して繰り返されることで(ただし必ずしもそうとは限らない — 強い先導語は1度だけで済むこともある)、分散した定義を積み重ね、モデルがすでに持っている先行知識を呼び起こすことで、できるだけ少ないトークンで振る舞いのある領域全体を束ねる。

これは予測可能性に二重に貢献する。本文の中では _実行_ を束ねる: その言葉が現れるたびに、エージェントは同じ振る舞いに手を伸ばす。description の中では _呼び出し_ を束ねる: 同じ言葉があなたのプロンプト、ドキュメント、コードに存在するとき、エージェントはその共有された言語をそのスキルに結びつけ、より確実に発火させる。

スキルを先導語を使うようリファクタリングする機会を狩る。3か所で綴られた三つ組(**重複**)、1つの考えを示すために1文を費やす description — それぞれが、1つのトークンへと **畳み込まれる** ことを求めている一節である。例:

- 「速く、決定的で、オーバーヘッドが低い」 -> _tight_ — 1つのフェーズ全体で言い換えられていた1つの性質を、1つの事前学習済みの言葉(_tight_ ループ)へ。
- 「信頼できるループ」 -> _red_ — 曖昧なゲートを、二値の観測可能な状態に変換する(そのループはバグに対して _red_ になるか、ならないか)。

これで二重に得をする: トークンは減り、_かつ_ エージェントが思考をかけられる、より鋭いフックが手に入る。すべてのスキルは、先導語が退役させられる言い換えを抱えていると想定し、それらを見つけに行く。

## 失敗モード

これらを使って、ユーザーがそのスキルで抱えているかもしれない問題を診断する。

- **premature completion(早すぎる完了)** — あるステップを、本当に完了する前に終えてしまうこと。注意が _完了すること_ に滑ってしまう。防御は、この順で: まず完了基準を研ぎ澄ます(安価で局所的)。それがどうしても曖昧であり、かつ実際に急いでいる様子が観察されたときにのみ、分割によって完了後のステップを隠す(手順による切り分け)。
- **duplication(重複)** — 同じ意味が複数の場所にある状態。保守とトークンのコストがかかり、ある意味の階段上での目立ち度を、その本来の順位を超えて膨らませる。
- **sediment(堆積物)** — 追加することは安全に感じられ、削除することはリスクに感じられるために積み重なる、古びた層。刈り込みの規律を持たないあらゆるスキルの、既定の末路。
- **sprawl(肥大化)** — すべての行が有効で一意であっても、単純に長すぎるスキル。読みやすさと保守性を損ない、トークンを無駄にする。治療法は階段である: **リファレンス** をポインタの裏に開示し、**分岐** や手順で分割して各経路が必要なものだけを運ぶようにする。
- **no-op(ノーオプ)** — モデルがデフォルトですでに従っている行であり、何も言わないために負荷を支払っている。判定基準: それはデフォルトと比べて振る舞いを変えるか? 弱い先導語(エージェントがすでにある程度徹底しているときの _be thorough_)はノーオプである。その修正はより強い言葉(_relentless_)であって、別の技法ではない。ノーオプはモデル相対的なので **モデルが上がるたびに新しく生まれる** — 乗り換えのたびに狩り直す層であり、自己検証と自己修正の指示が真っ先に追い越される。
- **negation(否定形)** — 禁止による操舵は裏目に出る: _象のことを考えるな_ は、象を名指しし、それを少なくするどころかより呼び出しやすくしてしまう。**肯定形** で促す — 目指す振る舞いを述べ、禁じられたものが決して語られないようにする。禁止は、肯定形で言い表せない固いガードレールとしてのみ保持し、それでもなお、代わりに何をすべきかと対にする。

## 評価

原則は下書きまでしか連れて行かない。そこから先は、代表的なタスクでそのスキルを実際に走らせ、どこで詰まるかを観測して直す。

測るものは2つある:

- **invocation(呼び出し)** — 発火すべきときに発火したか、発火すべきでないときに黙っていたか。ここが外れているなら直す対象は **description** であり、本文をどれだけ磨いても動かない。
- **predictability(予測可能性)** — 何度走らせても同じ経路を取ったか。ばらけるなら直す対象は **completion criterion(完了基準)** の明確さか、**context pointer(コンテキストポインタ)** の文言である。

どの行が **no-op(ノーオプ)** かで意見が割れたときも、決着をつけるのは議論ではなく実行である — 2人が割れているのはその行についてではなく、モデルのデフォルトについてだからである。ハーネスの `skill-creator` は、この観測(eval と、実行ごとのばらつきの分析)を回せる。
