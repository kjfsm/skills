# コメントを削るパス

**書く瞬間に自制させるのではなく、書かれたものを別のパスで削る。** 規約をいくら常駐させても、コメントの饒舌さは指示を上書きする強さで出てくる([anthropics/claude-code#65961](https://github.com/anthropics/claude-code/issues/65961) — CLAUDE.md・メモリ・フックを積み上げても部分的にしか効かない)。予防の層には天井があるので、回収はここで行う。

## 手順0 — 増えていなければ降りる

このパスは `/implement` のコミット前の並びに**必ず**入る。だから最初に機械的に数え、**コメント行が1行も増えていなければ、何もせず終える** — サブエージェントは立てない。必須の並びに置きながらコストを条件付きに保つための段であって、ここでは何も判断しない。

```bash
git diff <基点>...HEAD -- '*.ts' '*.tsx' '*.js' '*.jsx' '*.go' '*.rs' '*.java' '*.c' '*.h' '*.cpp' '*.cs' '*.swift' '*.kt' '*.php' '*.dart' '*.vue' '*.svelte' '*.css' '*.scss' '*.py' '*.rb' '*.sh' '*.sql' |
  grep -cE '^\+[[:space:]]*(//|/\*|\*[^/]|#($|[^!])|--[^-])'
```

拡張子を絞るのは、`#` が Markdown では見出し、YAML ではキーだからである。**この正規表現は全言語のコメント記法を一括で当てるので多めに数える**(シェルの `case` の `*)` が C 系の枝に当たるなど)— 判定は「0 か、0 でないか」だけなので、多めに出て困るのは無駄に1回走ることだけであり、拡張子ごとに振り分ける複雑さに見合わない。0 が返ったら、その旨だけ伝えて終える。

## 走らせ方

**`general-purpose` サブエージェント1つに渡す。** 自分で読みながら消さない — 直前に自分で書いたコメントは、目的が思い出せてしまう分だけ残す方向に倒れる。汚れていないコンテキストであることが、このパスの効きの半分を占める。

範囲は **差分の中で触れたファイルのコメントだけ**。基点はユーザーが言ったもの、無ければ `git merge-base` からの `git diff <基点>...HEAD`。継承した古いコメントまで広げるのは、ユーザーが明示的に求めたときだけである — 範囲を広げると1回の判断数が増え、その分だけ判断が雑になる。

サブエージェントには、下の**6段のルール**と**残す基準**を全文貼り付ける。それ以外にそこへアクセスする手段が無い。

## 6段のルール — この順に当てる

順序を固定するのは、実行ごとのばらつきを潰すためである。「よしなに整理して」は毎回違う結果を返す。

1. **コードの言い直し** — 隣の行を日本語や英語でなぞっているだけのもの(「ユーザーをループ」「〜を取得」「〜を更新」)、ブロックの終わりを示すだけのもの。→ **消す**
2. **変更の経緯** — 「v2 クライアントに更新」「submit から button に変えた」。差分とコミットログが既に持っている。→ **消す**
3. **動く的への参照** — 「仕様 §7 に従う」「設計ドキュメント参照」のような、指し先が動いたら黙って嘘になるもの。→ 参照先が安定した識別子(issue 番号、ADR 番号、RFC 番号)なら**残す**。節番号やドキュメント名なら、**中身を1行で書き写して参照を消す**
4. **膨らんだ理由づけ** — 言いたいことは正しいが5行ある。→ **1行に削る**。削れないなら、それは複数の別々の事実が1つのコメントに詰まっている合図なので、分ける
5. **陳腐化** — 隣のコードが既にそう動いていない。→ **消す**(直すのではない。正しい記述を書き直したいなら、それは別の作業である)
6. **本物の制約** — 採らなかった素直な書き方とその理由、外部の制約(API 仕様・RFC・プラットフォームの上限)、不変条件と順序依存。→ **残す**

## 残す基準は非対称である

**迷ったら、Why は残す。How は消す。**

対称に見える判断を対称に扱わない。**警告を1つ誤って消す損害は、凡庸なコメントが1つ残る損害よりはるかに大きい。** 消したコメントが実は順序依存を守っていた、という失敗は、後から差分を見ても気づけない。

## 合格基準

**減った行数ではない。** 減らすことを目標にすると、全消しが最適解になる。

合格は「**残ったコメントが全部、コードから復元できない情報を運んでいる**」である。1行も減らないパスがありうるし、それは正しい結果でありうる。

## 報告する

削ったら、次を出す:

- 段ごとの件数(1〜5 で何件消し、6 で何件残したか)
- **消した中で判断が割れたもの**(あれば)を、消した理由1行つきで列挙する — ユーザーが `git checkout` で戻す判断ができるように
- 1行も消さなかったなら、そう言う。**それは失敗ではない**

## このパスがやらないこと

**足さない。** 書かれるべきだったのに書かれていない Why not を探すのは、差分に写っていないものを探す作業で、消す作業とは要求される見方が逆である。同じパスに混ぜると、削る手が緩む。そちらは `/two-axis-review` の Standards 軸が受け持つ。
