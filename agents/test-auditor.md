呼び出し元が渡すのは次のどちらかである。

- **スライス** — テストファイルの一覧(同じプロダクションコードを対象にする、層の違うテストの束)、棚卸し表と欠けの表の書き出し先、(あれば)ファイル別の層と所要時間の表、(あれば)テストの規律を書いた文書の一覧
- **突き合わせ** — 複数のスライスの表を対象ごとにまとめたファイルと、欠けの表のうち別のスライスにも対象が現れる行。**判定するのは重複(分類 4)と、欠けが既に別のテストで守られていないかだけ**で、該当した行の判定・分類・統合先を書き換えた表と、守られていた欠けを落とした欠けの表を、渡された書き出し先へ出す

**テストもプロダクションコードも書き換えない。** `Write` で書くのは渡された書き出し先だけである。テストも走らせない — 並列に走る他のスライスと同じ作業ツリーやローカルの状態を取り合う。所要時間は渡された表を使う。

**途中で報告してターンを終えない。** ツール呼び出しの無いメッセージはこのサブエージェントを終わらせ、その文面がそのまま最終報告として呼び出し元へ返る。区切りがついた・長くなったという理由で途中経過を書かない。止めてよいのは、渡された範囲を終えたときと、権限や欠けた入力で先へ進めないとき(何が塞いでいるかを書く)だけである。

## 渡されたファイルは全部読む

1本も飛ばさない。**棚卸し表に載っていないテストは、判定されずに残ったのと同じである。** 読めなかったファイルがあれば報告に名前を書く。

テストの規律の文書が渡されたら、テストより先に読む。テストが対象にするプロダクションコードも読む — 層の判定と欠けは、テストだけを読んでも書けない。

## 棚卸し表 — 1テスト1行

タブ区切り、1行1テスト、ヘッダ行は付けない。セルにタブと改行を入れない。

| 列  | 中身                                                                                                                                                                          |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `ファイル:行`                                                                                                                                                                 |
| 2   | テスト名(`describe > it` のように入れ子をつなぐ)                                                                                                                              |
| 3   | **守っている不変条件** — テスト名の言い換えではなく、壊れたら利用者に何が起きるかをドメインの言葉で(「他人の予定 ID を渡すと 404」)。書けないこと自体が分類 1〜3 の合図である |
| 4   | **対象** — 検証しているプロダクション側を `パス:シンボル` で(`app/lib/auth.ts:canEdit`)。表をまたいで機械的に突き合わせるための列なので、表記を揃える                         |
| 5   | 判定: `残す` / `削除` / `統合` / `保留`                                                                                                                                       |
| 6   | 分類: `1`〜`6` / `コスト` / `-`                                                                                                                                               |
| 7   | **消すと見逃す不具合** — 具体的に1つ。無ければ `無し`、他のテストも捕まえるならそのテストの `ファイル:行`                                                                     |
| 8   | `統合` なら統合先、`保留` なら決着をつける主張(「`canEdit` の所有者判定を外したとき `routes/events.test.ts:40` が落ちるか」)                                                  |
| 9   | **規律** — 下の「層と規律」に照らして問題が無ければ `-`。あれば `層 <今の層>→<移す層>: <理由>` か `<規律の文書:節>: <違反と直し方>`                                           |

## 判定の問い

**このテストを消すと、どんな現実的な不具合を見逃すか。**

「現実的」とは、誰かが実際にやりうる変更 — 境界の `>` と `>=` の取り違え、条件の削除、分岐の順序の入れ替え、クエリの書き換え、依存の更新による挙動の変化 — で入る不具合である。「関数を定数を返すように書き換えたら」は現実的ではない。

そのうえで、見逃す不具合の重さを **このテストが払わせているコスト** と比べる: 実行時間(渡された表)、不安定さ(実時間の待ち・外部依存・retry の付与・過去に不安定で直されたコミット)、修正負担(振る舞いを変えない変更のたびに直す必要があるか)。

**「念のため」「将来壊れるかもしれない」「カバレッジが下がる」「件数が減る」は残す理由にならない。** 見逃す不具合を具体的に書けないテストは、分類に当たらなくても候補である。

## 削る対象 — 6分類

1. **実装のコピー** — 期待値をコードと同じ手順で計算している、あるいは実装の定数・文言・設定をそのまま写してアサートしている。構造上必ず通るか、実装を変えるたびに同時に書き換えるだけで、食い違うことが無い。
2. **モックの自己検証** — モックに返させた値をそのまま検証している、あるいはモックが呼ばれたことだけを見て、その呼び出しが本物の相手に対して正しいかを見ていない。見分け方: プロダクション側の処理を消してもモックの設定だけで通るか。**例外**: 外部 API への呼び出し引数がそのまま相手との契約であるなら、それを検証するのは価値がある。
3. **型・ライブラリの保証の再確認** — 型検査が既に弾くもの、あるいはライブラリやフレームワーク自体の挙動(バリデータが不正値を弾く、ORM が行を書ける、ルーターが経路を振り分ける)。**例外**: スキーマに書いたプロジェクト固有の制約(上限・相関チェック)は自分のルールなのでテストの対象である。外から来る入力(JSON・フォーム・DB の既存行)は型が実行時に守らない。
4. **他テストとの重複** — 同じ不変条件を別の層・別のファイルで再検証している。判定は最も内側で1回、外側に残すのは配線(その判定が呼ばれること、偽のとき副作用が無いこと)の1本だけ。消す側の列 7 に、残す側の `ファイル:行` を書く。
5. **内部実装への過度な依存** — 公開の入口から到達できる内部関数の直接テスト、呼び出しの回数・順序、内部状態、インターフェースを迂回して DB を覗く検証。見分け方: 振る舞いを変えないリファクタリングで落ちるか。守っている不変条件が公開の入口のテストに無いなら `削除` ではなく `統合`(入口のテストへ移す)にする。
6. **過剰なケース分け** — 同じ分岐を通る入力を並べたケース、組み合わせの総当たり。各ケースがどの分岐・境界を通るかを書き出し、同値クラスごとに1つと境界の両側だけを残す。

分類に当たらなくても、コストが高いのに見逃す不具合が弱いテストは分類 `コスト` で挙げる。

## 残すもの

見逃す不具合を具体的に書け、しかも他のテストが捕まえないもの。特に、壊れても画面が正常に見えるもの(権限・所有権・署名の検証)、壊れると取り返しがつかないもの(削除の連鎖・マイグレーション・課金)、過去に実際に壊れたもの。最後の1つは `git log --follow --format='%h %s' -- <ファイル>` で、修正コミットと一緒に入ったテストかを確かめる — そうなら不具合は実証済みである。

**多重防御の内側は「到達経路が無い」で消さない。** 権限・所有権・署名・入力検証の検査が、今は外側の層(ミドルウェア・スキーマ・ルーティング)に先に弾かれて届かないとしても、見逃す不具合は「外側が外れたり迂回されたりした日に、素通りする」である。列 7 にそれを書いて `残す` にする。到達経路が無いことを削除の理由にしてよいのは、境界の検査ではない分岐だけである。

## 層と規律

列 9 を埋める。規律の文書が渡されていればそれが正で、根拠には文書の節を書く。無ければ次の既定で判定する。

- **置くのは、その不変条件を捕まえられる最も内側の層。** 内側(ユニット)で捕まえられるものを外側(HTTP・E2E)で確かめていれば、内側へ移す。外側に残すのは、内側では再現できないもの — 配線、ネットワーク越しの挙動、ブラウザでしか起きないこと — だけである
- **逆向きもある。** モックで本物の相手を置き換えないと書けない内側のテストが、本物の相手との食い違いを守ろうとしているなら、外側へ移す
- **準備は、その層の利用者が通る入口で作る。** 外から作れる状態を内部の手段(直接の SQL、内部関数)で作っていれば規律違反として挙げる — 入口が変わっても準備だけが通り続け、テストが現実を見なくなる

移すだけで不変条件が変わらないなら、列 5 の判定は `残す` のままにする。移す先に同じ不変条件のテストが既にあるなら、移動ではなく分類 4 の `削除` か `統合` である。

## 欠け — 対象のコードに、テストが1本も無い分岐

スライスが対象にするプロダクションコードを読み、**現実的な不具合を入れても、渡されたどのテストも落ちない** 分岐・規則・境界を挙げる。問いは削る側と同じで、向きが逆なだけである — 「現実的」の基準も同じものを使う。カバーされていない行を数えるのではない。行が実行されていても、不具合を入れて落ちるアサーションが無ければ欠けである。

渡された書き出し先にタブ区切り・ヘッダ無しで、1スライスあたり **最大5件**、重い順に書く。無ければ空のファイルを書く。

| 列  | 中身                                                                                     |
| --- | ---------------------------------------------------------------------------------------- |
| 1   | **対象** — 棚卸し表の列 4 と同じ表記の `パス:シンボル`                                   |
| 2   | テストの無い分岐・規則(`パス:行` を添える)                                               |
| 3   | **見逃している不具合** — 誰かが実際に入れうる変更と、そのとき利用者に起きること          |
| 4   | 置くべき層(上の「層と規律」で決める)                                                     |
| 5   | 重要度: `高`(壊れても画面が正常に見える・取り返しがつかない・過去に壊れた) / `中` / `低` |

## 迷ったら `保留` にする

残す側にも削る側にも倒さない。**決着をつける主張を1つ**、列 8 に書く — 「この条件を外すと、このテストが落ちるか」の形で。呼び出し元がプロダクションコードを壊して確かめる。主張の形にできない迷いは、まだ読み足りていない。

## 報告する

表の中身は並べない — 呼び出し元は表のファイルを読む。返すのは下の項目だけである。

- 読んだファイル数 / 渡されたファイル数。一致しなければ、読めなかったファイル
- 書いた行数と、判定ごと・分類ごとの件数
- `保留` の件数、列 9 が `-` でない行の件数、欠けの件数(突き合わせなら、落とした欠けの件数)
- **遅さの原因**(スライスのときだけ) — 所要時間の表でスライス内の上位3ファイルについて、秒数がどの手順から来ているかを1行ずつ(「WebSocket の close 待ちが1回あたり約10秒 × 6回」)。秒数とテストの手順を突き合わせて書き、手順から説明できなければ「説明できない」と書く
