# テスト駆動開発

TDD とはレッド → グリーンのループである。このスキルは、そのループが残す価値のあるテストを生み出すためのリファレンスである: 良いテストとは何か、テストはどこに置くか、アンチパターン、そしてループの規則。すべての節はサイクルのたびに適用される — ループの前と最中に参照すること、後からではない。

コードベースを探索するときは(存在すれば)`CONTEXT.md` を読み、テスト名とインターフェースの語彙がプロジェクトのドメイン言語と一致するようにし、触れている領域にある ADR を尊重する。

## 良いテストとは何か

テストは、実装の詳細ではなく公開インターフェースを通じて振る舞いを検証する。コードはまるごと変わることがあっても、テストは変わるべきではない。良いテストは仕様書のように読める — 「ユーザーは有効なカートでチェックアウトできる」は、まさにどんな能力が存在するかを伝える — そして内部構造を気にしないので、リファクタリングを生き延びる。

例は [tests.md](tests.md) を、モックのガイドラインは [mocking.md](mocking.md) を参照。

## シーム — テストを置く場所

**シーム** とは、内部に踏み込まずに振る舞いを観察できる、テスト対象の公開境界のことである。テストはシームに置かれるものであり、内部構造に対して書くものでは決してない。

**事前に合意したシームでのみテストする。** テストを書く前に、テスト対象のシームを書き出し、ユーザーと確認する。合意されていないシームでテストは書かない。すべてをテストすることはできない — 事前にシームに合意しておくことで、テストの労力があらゆるエッジケースにではなく、重要な経路や複雑なロジックに向かうようになる。

尋ねる: 「公開インターフェースは何か、どのシームをテストすべきか?」

## アンチパターン

- **実装結合** — 内部の協力オブジェクトをモックする、プライベートメソッドをテストする、あるいは側道(インターフェースを使わずデータベースへ直接問い合わせる、など)を通じて検証する。見分け方: 振る舞いが変わっていないのにリファクタリングでテストが壊れる。
- **同語反復** — アサーションが、コードと同じやり方で期待値を再計算している(`expect(add(a, b)).toBe(a + b)`、手作業で同じやり方で導いたスナップショット、定数を自分自身と等しいとアサートする、など)ため、構造上必ず通ってしまい、コードと食い違うことが決してない。期待値は独立した信頼できる情報源 — 既知の正しいリテラル、手計算した例、仕様 — から来なければならない。
- **水平スライシング** — すべてのテストを先に書き、その後にすべての実装を書くこと。まとめて書いたテストは _想像上の_ 振る舞いを検証する: ユーザー向けの振る舞いではなく物事の _形_ をテストしてしまい、テストは実際の変更に鈍感になり、実装を理解する前にテスト構造にコミットしてしまう。代わりに **垂直スライス** で進める — 1つのテスト → 1つの実装 → 繰り返し。それぞれのテストは、直前のサイクルが教えてくれたことに応える **トレーサーバレット** である。

## ループの規則

- **グリーンの前にレッド。** 失敗するテストを先に書き、それに通るだけのコードだけを書く。将来のテストを先取りしたり、投機的な機能を加えたりしない。
- **一度に1スライス。** 1サイクルにつき、1つのシーム、1つのテスト、1つの最小限の実装。
- **リファクタリングはこのループの一部ではない。** それはレビューの段階(`two-axis-review` スキルを参照)に属するものであり、レッド → グリーンの実装サイクルには属さない。
