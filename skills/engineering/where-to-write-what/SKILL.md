# 何をどこに書くか

コードにまつわる情報には、それぞれ **宛先** が 1 つある。同じ事実を 2 か所に書くと、片方だけ直る日が来て、残った方が嘘をつく。この規律が決めるのは「書くか書かないか」ではなく「どこに書くか」 — 書きたくなった情報は捨てずに、正しい宛先へ届ける。

## ルーティング表

| 情報の種類                                                                   | 宛先                           |
| ---------------------------------------------------------------------------- | ------------------------------ |
| 何をしているか(挙動そのもの)                                                 | コード自体(命名・関数抽出・型) |
| コードから読めない制約・理由(なぜこの実装か、なぜ素直な書き方ではだめか)     | コメント                       |
| 型シグネチャに現れない契約(単位・範囲・フォーマット・戻り値の具体例・副作用) | JSDoc                          |
| 何をなぜ変えたか(変更前の状態・動機・採らなかった選択肢)                     | コミットメッセージ             |
| レビューに要る文脈(確かめ方・影響範囲・読み順・スクリーンショット)           | PR 本文                        |
| 後戻りしにくい設計判断と、却下した代替案                                     | ADR                            |
| 用語の定義と呼び方                                                           | 用語集(`CONTEXT.md` など)      |
| 手順・セットアップ・運用                                                     | README / docs                  |

## コード自体が第一の宛先

説明したくなった内容は、まず命名・関数抽出・型で言えないか試す。言えたら、コメントの仕事は残らない。

判定テスト: **コメントを消して、コードだけを読む。失われる情報が無ければ、その情報の宛先はコードだった** — コードに語らせ、コメントは消す。

## コメント — コードから読めない制約と理由

コメントが運ぶのは、コードをいくら読んでも出てこない情報である:

- 採らなかった素直な書き方と、それがだめな理由(「〜すると…が壊れるため、こうしている」)
- 外部の制約(API 仕様、RFC、プラットフォームの上限、ランタイムの挙動)
- 不変条件と順序依存(「先に削除しないと UNIQUE 制約に当たる」)
- issue・ADR への参照 1 行(本文はそちらに置く)

書きたくなったものが別の宛先のものだったら、そちらへ届ける:

| 書きたくなったもの                           | 本当の宛先                                       |
| -------------------------------------------- | ------------------------------------------------ |
| 処理の逐語的な説明(「〜を取得」「〜を更新」) | コード自体(命名・抽出)                           |
| 変更の経緯(「submit から button に変えた」)  | コミットメッセージ                               |
| 使わなくなったコード                         | git 履歴(そのまま削除する)                       |
| ファイルパス・目次・セクション見出し         | ファイルシステムとエディタが持っている(削除する) |

テストのコメントは「このテストが守っている性質」を書く場所である — なぜこの入力なのか、この境界を緩めるとどんな利用が壊れるのか。

## JSDoc — 型に出ない契約

JSDoc は型シグネチャの隣に立つ。型と名前がすでに言っていることは 0 行で足り、書くのは型に出ない契約だけ:

- 単位・範囲・フォーマット(「JST 00:00」「hex エンコード」)
- 引数・戻り値の具体例(`"残り2日"`)
- null / undefined / 既定値が意味すること
- 副作用と呼び出し条件

`@param` / `@returns` もタグ 1 つずつ同じ判定にかける。共有パッケージの公開 API は、名前に足す情報がある場合に限り概要 1 行(エディタのホバーで効く)。

## コミットメッセージ — 何をなぜ変えたか

件名は変更の要約。本文は「これまでどうだったか → なぜ問題か → どうしたか」で、diff からは読めない部分 — 変更前の状態、動機、採らなかった選択肢 — に紙面を使う。

- バグ修正は、正しいとわかった仮説を書く — 次にデバッグする人が学べるように
- 対応する issue への参照(`#123`、`Closes #45`)を含める — レビューする側はここからスペックを辿る

## PR 本文 — レビューに要る文脈

レビュアーがブランチを checkout せずに判断できるだけの文脈: 何が変わるか、どう確かめたか、どこから読み始めるか、UI ならスクリーンショット。squash マージ運用では PR 本文がそのままメインラインのコミット本文になる — その場合、コミットメッセージの基準がそのまま PR 本文の基準である。

## ADR — 後戻りしにくい設計判断

複数モジュールにまたがる判断と、却下した代替案とその理由は ADR に書く。コードからは ADR 番号の参照 1 行で指す — 判断の本文を書き写すと、ADR を直した日にコメントが古くなる。

## README / docs — 手順と運用

docs が運ぶのは、リポジトリを渡された人がコードを読み始める **前** に要るもの — セットアップ、実行のしかた、運用時の判断 — に限られる。

判定テスト: **そのページを消して、clone した人が詰まるか。詰まらなければ消す。**

書きすぎはたいてい同じ形で現れる。どれも、実装が変わった日に真っ先に嘘になる:

| 書きすぎの形                         | 本当の宛先                                                       |
| ------------------------------------ | ---------------------------------------------------------------- |
| ディレクトリ構成・アーキテクチャ概観 | コード自体(読めば分かる。書くなら「なぜその形か」だけを ADR へ)  |
| API・オプション・型の一覧            | 型定義とスキーマ(写すと二重管理になる。生成できるものは生成する) |
| 個数・バージョン・網羅的な一覧       | 書かない(数えた結果ではなく、数え方を書く)                       |
| 設計判断の経緯                       | ADR                                                              |

## このスキルを呼ばずに効かせる

このスキルは呼ばれて初めて読まれる。だがコメントを書く場面でモデルは「迷った」と自覚しないので、自分からは呼ばない。毎回効いてほしいなら、コメントの判定はリポジトリの `CLAUDE.md` / `AGENTS.md` に **本文として常駐** していなければならない — `/setup-skills` がそれをリポジトリごとに一度書き込む。

## 迷ったら: 誰がいつ読むか

- **コードを読む人** に要る(コードと同じ寿命を生きる) → コメント / JSDoc
- **変更を追う人** に要る(その変更の瞬間の文脈) → コミットメッセージ / PR 本文
- **設計を見直す人** に要る(モジュールをまたぎ、後戻りしにくい) → ADR
