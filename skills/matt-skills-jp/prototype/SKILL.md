# Prototype

プロトタイプとは **問いに答える使い捨てのコード** である。問いがその形を決める。

## 分岐を選ぶ

ユーザーのプロンプト、周辺のコード、あるいはユーザーが近くにいれば直接尋ねることから、どの問いに答えようとしているのかを見極める:

- **「このロジック/ステートモデルはしっくりくるか?」** → [LOGIC.md](LOGIC.md)。紙の上では判断しにくいケースにステートマシンを通していける、共有できる単一の HTML ファイル(自由に押せるボタンと、タブ形式のガイド付きウォークスルー)を作る。開発者でない人でも動かせる。
- **「これはどう見えるべきか?」** → [UI.md](UI.md)。単一のルート上に、URL のクエリパラメータとフローティングのボトムバーで切り替えられる、何通りかの根本的に異なる UI バリエーションを生成する。

この2つの分岐はまったく異なる成果物を生む — ここを間違えるとプロトタイプ全体が無駄になる。問いが本当に曖昧で、ユーザーに確認できない場合は、周辺のコードによりよく合う方の分岐(バックエンドのモジュールならロジック、ページやコンポーネントなら UI)をデフォルトとし、プロトタイプの先頭にその前提を書く。

## 両方に共通するルール

1. **最初から使い捨てであり、はっきりそう分かるようにする。** プロトタイプのコードは、それが実際に使われる場所の近く(プロトタイプ対象のモジュールやページの隣)に置き、文脈が明らかになるようにする — しかし、何気なく見た人にもそれがプロトタイプであって本番コードではないと分かるように名付ける。使い捨ての UI ルートについては、プロジェクトがすでに使っているルーティングの慣習に従う。新しいトップレベルの構造を発明しない。
2. **起動が自明であること。** UI プロトタイプはプロジェクトのタスクランナーの1コマンドから始まる — `pnpm <name>`、`python <path>`、`bun <path>` など。ロジックのデモはユーザーがダブルクリックする単一の HTML ファイルである。どちらにせよ、起動に考えることは要らない。
3. **デフォルトでは永続化しない。** 状態はメモリ上に置く。永続化はプロトタイプが _確認している_ ことであって、それに依存すべきものではない。問いが明示的にデータベースに関わるなら、明確な「PROTOTYPE — wipe me」という名前のスクラッチ用 DB かローカルファイルを使う。
4. **仕上げは省く。** テストなし、プロトタイプを _実行可能にする_ 以上のエラー処理なし、抽象化なし。狙いは、素早く何かを学ぶことである。
5. **状態を見えるようにする。** アクションのたび(ロジック)、あるいはバリアントの切り替えのたび(UI)に、関連する状態全体を出力または描画し、ユーザーが何が変わったか見えるようにする。
6. **完了したら記録する。** 検証された決定は本物のコードに畳み込み、それからプロトタイプ自体を **一次情報源** として記録する: 使い捨てのブランチにコミットし、main の外に置き、実装のイシューにそのブランチへのコンテキストポインタを残す。答え — 判定と、それが解決した問い — もイシューかコミットに記録する。main ブランチには検証された決定だけが残る。
