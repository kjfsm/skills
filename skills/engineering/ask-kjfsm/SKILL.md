# Ask kjfsm

すべてのスキルを覚えていなくていい。だから尋ねる。

**フロー** とは、スキルを通り抜ける一本の道筋である。ほとんどの道筋は1つの **メインフロー** に沿って進み、そこに2つの **オンランプ** が合流する。それ以外はスタンドアロンか、その下を流れる語彙レイヤーである。

## メインフロー: アイデア → 出荷

ほとんどの作業が通る道筋。アイデアがあり、それを作りたい。

1. **`/grill-with-docs`** — インタビューでアイデアを研ぎ澄ます。**コードベースがある**場合はここから始める: これはステートフルで、学んだことを `CONTEXT.md` と ADR に保持する。(コードベースがない? `/grill-me` を使う — スタンドアロンを参照。どちらも同じ `/grilling` プリミティブを実行するが、`grill-with-docs` は形に残る記録を残す方である。)
2. **分岐 — すべての問いを会話の中で決着させられるか?** 実行可能な答えを必要とする問い(状態、ビジネスロジック、実際に見る必要のある UI)があれば、プロトタイプへ寄り道する。その行き来は **`/handoff`** が両方向で橋渡しする(セッションをまたぐを参照):
   - まず **`/handoff`** で外へ出し、そのファイルを対象に新しいセッションを開く、
   - **`/prototype`** で使い捨てのコードによってその問いに答える、
   - 学んだことを **`/handoff`** で持ち帰り、元のアイデアのスレッドから参照する。
3. **分岐 — これは複数セッションにまたがるビルドか?**
   - **はい** → **`/to-spec`**(スレッドをスペックに変換する)、続けて **`/to-tickets`** でそれをトレーサーバレット方式のチケットに分割し、それぞれに **ブロッキングエッジ** を宣言させる。ローカルのトラッカーでは `.scratch/<feature>/issues/` 配下にチケット1つにつき1ファイルを置き、ブロッカーを手作業で先に片付けていく。実際のトラッカーではそのエッジがネイティブなブロッキングリンクになるので、ブロッカーが片付いたチケットはどれでも着手できる — チケットごとに **`/implement`** を起動し、**チケットごとにコンテキストをクリアする**。
   - **いいえ** → 同じコンテキストウィンドウのまま、その場で **`/implement`**。

   どちらの場合も、**`/implement`** は内部で **`/tdd`** を駆動して各イシューをビルドし — 一度に1つのレッド・グリーンのスライスずつ進める — その後 **`/verification-loop`** で **クリーンラン**(記録されたゲートを中断なく1回で通し、加えて変更した経路を実際に駆動して観測する)を取り、コミット前に **`/two-axis-review`**(差分に対する Standards + Spec の二軸レビュー)で締めくくる。フルスペックなしでとにかく具体的な振る舞いをテストファーストで作りたいときは **`/tdd`** 単体を、変更が本当に動くか確かめたいだけのときは **`/verification-loop`** 単体を、固定した基点に対してブランチや PR をレビューしたいときは **`/two-axis-review`** 単体を使う。

   `/tdd` はテストを書ける土台があることを前提にする。Cloudflare Workers のリポジトリでその土台自体が無い、あるいは信用できないときは、先に **`/create-tests`**(テストが1本も無い)か **`/rebuild-tests`**(既存のスイートが遅い・OOM する・`vi.mock` だらけ)を通す。

### コンテキストの衛生管理

手順1〜3は **1つの途切れないコンテキストウィンドウ** の中で進める — `/to-tickets` の後まで compact もクリアもしない — こうすることで、グリリング・スペック・チケットがすべて同じ思考の上に積み上がる。各 `/implement` はその後、チケットをもとに新しいコンテキストから始める。

ここでの限界が **スマートゾーン** である: モデルが依然として鋭く推論できる範囲(最先端のモデルでおよそ12万トークン)のこと — それを超えると、コンテキストが技術的には収まっていても推論の質は落ちる。`/to-tickets` の前にセッションがこれに近づいてきたら、劣化したまま押し進めず、`/handoff` して新しいスレッドで続ける。

## オンランプ

作業を生み出す出発点となる状況で、その後メインフローに合流する。

- **バグや要望が積み上がってきた** → **`/triage`**。イシューをトリアージロールに沿って進め、エージェントが着手できる状態のイシューを生成し、それを後で **`/implement`** が拾い上げる。

  トリアージは **自分が作成していない** イシュー専用である — バグ報告、飛び込みの機能要望、生の状態で届いたものすべて。`/to-tickets` が生成したチケットはすでにエージェントが着手できる状態なので、**トリアージしない**。

- **何かが壊れている** → **`/diagnosing-bugs`**。手強いバグ向け: 一目見ただけでは太刀打ちできないバグ、断続的なフレーク、2つの正常な状態の間に忍び込んだリグレッション。**タイトなフィードバックループ** — _この_ バグですでにレッドになる1つのコマンド — を手にするまで理論化を拒み、その後リグレッションテストで修正する。実は本当の発見が「このバグを封じ込めるちょうど良いシームがない」ことだった場合、その事後検証は **`/improve-codebase-architecture`** に引き継がれる。

- **巨大で霧に包まれた取り組み — グリーンフィールドのプロジェクトや、1セッションには大きすぎる巨大な機能開発** → **`/wayfinder`**、ここで最も認知負荷の高いフロー。ここから目的地までの道筋がまだ見えていないとき、これはイシュートラッカー上に **意思決定チケット** の **共有マップ** を描き、それらを1つずつ解決していく — **成果物ではなく意思決定** を生み出しながら — 霧が晴れて道が明らかになるまで。**`/grill-with-docs`** が1セッションで抱えられるアイデアを研ぎ澄ますのに対し、wayfinder は抱えきれないアイデアのためのものであり、より遅く濃密なので、まさにそういう場合のためだけに取っておく。よく絞り込まれた機能開発には決して使わない。

  マップが晴れたら、**それはビルドせず、引き継ぐだけである**: マップにリンクされた意思決定をビルド可能な計画へと畳み込む **`/to-spec`** でメインフローに合流し、その後はいつも通り `/to-tickets` と `/implement` に進む。マップをそのまま `/implement` にループさせると、この畳み込みを飛ばしてリンクされた詳細を捨ててしまう。取り組みが実際には小さかった場合に限り、直接 `/implement` に進む。

## コードベースの健全性

機能開発ではなく、保守。

- **`/improve-codebase-architecture`** — 手が空いたときはいつでも実行し、コードベースをエージェントが操作しやすい状態に保つ。これは **深化の機会** を洗い出す。1つを選ぶと _アイデアが生まれ_、それを `/grill-with-docs` でメインフローに持ち込める。これは候補を見つける調査であり、後述の **`/codebase-design`** は選んだものを設計する作業台である。
- **`/tend-claude-md`** — CLAUDE.mdをまだ持たないリポジトリで新規に書く、あるいは肥大化・陳腐化・矛盾を疑うたびに監査してトリムする。行数の目安に収め、具体的で矛盾のない指示だけを残す。

## 下敷きとなる語彙

他のスキルの _下敷きとして_ 動く、3つのモデル呼び出し型のリファレンス — それぞれがその語彙の唯一の情報源である。プロセスではなく **言葉** が問題になったときは直接これらを使う。あるいは上記のスキルにそれらを取り込ませる。

- **`/domain-modeling`** — プロジェクトの _ドメイン_ 言語を研ぎ澄ます: 曖昧な用語に異議を唱える、多義的な言葉("account" が3つの役割を兼ねている、など)を解消する、後戻りしにくい決定を ADR として記録する。これは `/grill-with-docs` が `CONTEXT.md` をきれいな用語集に保つために駆動する能動的な規律である。
- **`/codebase-design`** — モジュールの _形_ を設計するための深いモジュールの語彙(モジュール、インターフェース、深さ、シーム、アダプター、レバレッジ、局所性): 小さなインターフェースの裏に多くの振る舞いを隠し、きれいなシームに置く。`/tdd` と `/improve-codebase-architecture` はどちらもこの語彙で話す。
- **`/delegation`** — 作業を _どこで_ 走らせるかの語彙(押し出し、階層、報告の長さ): 出力が大量で後から読み返さない作業をサブエージェントの子コンテキストへ押し出し、探索や事実確認は下位モデルに、設計判断は上位モデルに回す。**スマートゾーン** が1つのコンテキストをどこまで伸ばせるかを扱うのに対し、これはそもそも何をそこに入れずに済ませるかを扱う。サブエージェントを起動するスキル(`/research`、`/two-axis-review`、`/improve-codebase-architecture`、`/wayfinder`)はどれもこの語彙で話す。

## セッションをまたぐ

- **`/handoff`** — スレッドが埋まったとき、あるいは(たとえば `/prototype` セッションへ)枝分かれする必要があるとき、これは会話をマークダウンファイルへと圧縮する。同じ場所で続けるのではなく、**新しいセッションを開いてそのファイルを参照する** ことでコンテキストを持ち越す。これはコンテキストウィンドウ間の橋であり、どちら向きにも使える。**新しいセッション** が欲しいが、**今の会話を保存しておきたい** ときに使う。
- **`/compact`**(組み込み) — **同じ会話の中** に留まり、それより前のやり取りを要約させる。**フェーズ間の意図的な区切り** で使い、逐語的な履歴を失っても構わないときに使う。フェーズの途中で compact しない — エージェントが道を見失うことがある。`/handoff` は分岐し、`/compact` は続行する。

## スタンドアロン

メインフローから完全に外れたもの。

- **`/grill-me`** — `/grill-with-docs` と同じ容赦ないインタビューだが、**コードベースがない** ときのためのもの。ステートレス: ローカルには何も保存せず、`CONTEXT.md` も作らない。リポジトリに属さない計画やデザインを研ぎ澄ましたいときに使う。
- **`/prototype`** — 1つのデザイン上の問いに答える、小さく使い捨てのプログラム: この状態モデルはしっくりくるか、この UI はどう見えるべきか。最初から使い捨て — 答えだけ残し、コードは消す。メインフローの手順2における寄り道だが、デザイン上の問いが紙の上では決着しにくいときはいつでも使ってよい。
- **`/research`** — 調べ物の力仕事を **バックグラウンドエージェント** に委ねる: **一次情報源** に対してある問いを調査し、引用付きのマークダウンファイルをリポジトリに残す。読んでいる間も作業を続けられる。それが生成するファイルは `/grill-with-docs` で メインフロー に **持ち込む** ものである — リサーチは思考の材料になるのであって、思考の代わりにはならない。
- **`/teach`** — 現在のディレクトリをステートフルな作業スペースとして使い、複数セッションにわたって概念を学ぶ。
- **`/writing-great-skills`** — スキルをうまく書き、編集するためのリファレンス。

## 前提条件

**`/setup-skills`** — 最初のエンジニアリングフローの前に実行し、他のスキルが前提とするイシュートラッカー、トリアージラベル、ドキュメント配置を設定する。独自のイシュートラッカーにも対応する。
