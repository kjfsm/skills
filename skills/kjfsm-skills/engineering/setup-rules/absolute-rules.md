# `CLAUDE.md` / `AGENTS.md` に置く2つのブロック

どちらも `paths:` を書けない — どのファイルを触っていても効く必要がある。そのうえで rule ではなく本体を使うのは、**最優先で、短い**からである。圧縮を挟んでも先頭が残り、他のどれより先に読まれる。

宛先は **すでにある方**。`AGENTS.md` があれば(`CLAUDE.md` がその symlink でも)そちらへ置く — `.claude/rules/` を読まないハーネスにも同じ絶対ルールが届く。

`[ ]` は埋める箇所。それ以外は**全リポジトリで同一文面**に保つ。

## 絶対ルール

```markdown
## 絶対ルール

スタックに依存しない最優先ルール。全リポジトリで同一文面。

1. **言語**: [コメント・コミットメッセージ・PR タイトル・PR 本文・AI とのやり取りの言語]。ブランチ名は英語のみ。識別子・型名・ログ・UI 表示テキストは英語のまま触らない。
2. **変更後は検証ゲートを通す**。順序とコマンドは `docs/agents/verification.md` が正。失敗を残したままコミットしない。
3. **`[デフォルトブランチ]` へは原則 直 push しない**。ブランチを切って PR を出す。急ぎで直接入れることはあってよいが、既定の経路にはしない。
4. **シークレットをコード／Git にハードコードしない**。`[.dev.vars / .env]` は commit せず、ログにも出さない。**認証情報を本来の保管場所の外へ持ち出さない**(個人リポジトリ・クラウドストレージ・チャット/メール添付・スクショ等へコピーしない)。環境ごとに別の値を使い、本番値を開発に流用しない。
5. **pre-commit / pre-deploy フックを `--no-verify` でスキップしない**。フックが落ちたら根本原因(型・lint・テスト)を直す。
6. **自動生成ファイルを手編集しない**(具体パスは `.claude/rules/[生成物の rule]` を参照)。
```

項目の増減について:

- **足す前に `.claude/rules/` を試す。** ここに1行足すと全セッションのコンテキストを消費し、他の5項目の重みを薄める。`paths:` を書けるなら rule が正しい宛先である
- **実態と食い違う項目は置かない。** 直コミットが常態のリポジトリに項目3を置けば、守られないルールが1つできる。1つ守られないと、残りも「守らなくてよいもの」に見え始める。外すか、実態を規則化した文面に直す
- **項目3が「禁止」ではなく「原則」なのは、実態を数えた結果である。** 手元のリポジトリを `git log --first-parent` で数えると、PR 経由がほぼ 100% のものと、`main` で直接作業するのが設計のもの(使い捨て・fork・メモ置き場)に割れる。後者に機構で `git push` を止めると、設計どおりの作業を毎日止める。**ここは運用で守り、機構にはしない** — `/kjfsm-skills:setup-hooks` の条件4(実態を数えた)がそう判定する
- **6項目はどれも「守らなかったときに取り返しがつかない」もの**として選ばれている — シークレットの流出、生成物の取り違え、検証を経ない変更。取り返しがつく失敗はここに置かない
- 項目2と6が具体値を持たず参照になっているのは、同一文面を保つためである。コマンド名や生成物のパスを直接書くと、そのリポジトリでだけ更新が要る行になる

## 自己更新ルール

```markdown
## 自己更新ルール

同じ指摘を 2 回以上受けた事項は、以下の優先順位でドキュメントに追記する。

1. **パス固有の事実** → `.claude/rules/<area>.md`(`paths:` 指定で該当パス編集時のみ自動注入)
2. **手順・テンプレ・ワークフロー** → `.claude/skills/<name>/SKILL.md`(`/<name>` で明示呼び出し)
3. **決定的に弾きたい挙動** → 効く範囲の広い層から順に(`permissions.deny` → `scripts/check-*.ts` を検証ゲートと CI から → `.claude/hooks/*.sh`)
4. **呼び名がぶれた語** → `CONTEXT.md`(用語と「避ける表現」を 1 か所に)
5. **全セッションで必要な絶対ルール** → この `CLAUDE.md`
```

このブロックが決めているのは**追記の順序**である。1 から順に「これで足りるか」を問い、足りたところで止める。上ほど注入が絞られていて、下ほど全セッションに効く — つまり上ほど安く、下ほど高い。

**項目3の中にもう一段の順序がある。** Claude のフックは、そのマシンの Claude セッションにしか届かない — クローンにも CI にも人間にも効かない。同じ検査を `permissions.deny` かリポジトリの検査スクリプトに置けるなら、そちらが先である。どの層に置けるかは「何から見えるか」で機械的に決まる(`/kjfsm-skills:setup-hooks`)。

**発火条件は「2回以上」である。** 1回目は偶然かもしれず、先回りで書いたルールは守る理由が誰にも分からないまま残る。ルールが増えるのは、実際に2度同じ訂正を打ったときだけでよい。

`.claude/hooks/` と `CONTEXT.md` が無いリポジトリでも、この5項目はそのまま置いてよい — どこへ足すかの判断が先にあり、置き場所は必要になった時点で作られる。
