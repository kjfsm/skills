# QA セッション

インタラクティブな QA セッションを実行する。ユーザーが遭遇している問題を説明し、あなたは明確化し、コードベースを探索して文脈を把握し、耐久性があり、ユーザー視点で、プロジェクトのドメイン言語を使った GitHub イシューを作成する。

## ユーザーが挙げる各イシューについて

### 1. 聞き、軽く明確化する

ユーザーに自分の言葉で問題を説明させる。以下に絞って**最大2〜3個の短い確認質問**をする:

- 何を期待していたか vs 実際に何が起きたか
- 再現手順(自明でなければ)
- 常に起きるか、それとも間欠的か

過度にヒアリングしないこと。作成できるほど説明が明確であれば先に進む。

### 2. 背景でコードベースを探索する

ユーザーと会話している間に、Agent(subagent_type=Explore)を背景で起動し、関連する領域を理解する。ゴールは修正方法を見つけることでは**ない**。以下が目的である:

- その領域で使われているドメイン言語を学ぶ(UBIQUITOUS_LANGUAGE.md を確認する)
- その機能が本来何をすべきなのかを理解する
- ユーザーに見える振る舞いの境界を特定する

この文脈はより良いイシューを書く助けになる — ただしイシュー自体は特定のファイル、行番号、内部の実装詳細を参照すべきでは**ない**。

### 3. スコープを見極める: 単一イシューか、分割するか?

作成前に、これが**単一のイシュー**か、複数のイシューに**分割する**必要があるかを判断する。

以下の場合は分割する:

- 修正が複数の独立した領域にまたがる(例: 「フォームのバリデーションがおかしい、かつ成功メッセージが表示されない、かつリダイレクトが壊れている」)
- 別々の人が並行して取り組める、明確に分離可能な関心事がある
- ユーザーが複数の異なる失敗モードや症状を説明している

以下の場合は単一イシューのままにする:

- 一箇所でおかしい振る舞いが1つだけである
- すべての症状が同じ根本的な振る舞いに起因している

### 4. GitHub イシューを作成する

`gh issue create` でイシューを作成する。先にユーザーへレビューを求めては**いけない** — 作成してから URL を共有する。

イシューは**耐久性がある**ものでなければならない — 大きなリファクタの後でも意味が通るようにする。ユーザー視点で書く。

#### 単一イシューの場合

以下のテンプレートを使う:

```
## What happened

[ユーザーが経験した実際の振る舞いを、平易な言葉で説明する]

## What I expected

[期待していた振る舞いを説明する]

## Steps to reproduce

1. [開発者がたどれる具体的な番号付き手順]
2. [内部のモジュール名ではなく、コードベースのドメイン用語を使う]
3. [関連する入力、フラグ、設定を含める]

## Additional context

[ユーザーやコードベース探索からの追加の観察で、イシューの理解を助けるもの — 例:「これは Docker レイヤーを使っているときだけ発生し、ファイルシステムレイヤーでは発生しない」 — ドメイン言語を使い、ファイルは引用しない]
```

#### 分割する場合(複数イシュー)

実際のイシュー番号を参照できるよう、依存関係の順序(ブロッカーを先に)でイシューを作成する。

各サブイシューに以下のテンプレートを使う:

```
## Parent issue

#<parent-issue-number>(追跡用イシューを作成した場合)または "Reported during QA session"

## What's wrong

[この特定の振る舞いの問題を説明する — 全体ではなく、この一部分だけ]

## What I expected

[この一部分に対して期待される振る舞い]

## Steps to reproduce

1. [このイシューに固有の手順]

## Blocked by

- #<issue-number>(このイシューが他のイシューの解決まで修正できない場合)

ブロッカーがなければ "None — can start immediately" とする。

## Additional context

[この一部分に関連する追加の観察]
```

分割を作成するとき:

- **少数の厚いイシューより、多数の薄いイシューを優先する** — それぞれが独立して修正・検証できるようにする
- **ブロッキング関係を正直に示す** — イシュー B が本当にイシュー A の修正まで検証できないなら、そう明記する。独立しているなら両方に "None — can start immediately" と記す
- **依存関係の順序でイシューを作成する** ことで、「Blocked by」に実際のイシュー番号を参照できるようにする
- **並列性を最大化する** — 複数の人(あるいはエージェント)が異なるイシューを同時に着手できるようにするのがゴールである

#### すべてのイシュー本文に共通するルール

- **ファイルパスや行番号を含めない** — すぐに古くなる
- **プロジェクトのドメイン言語を使う**(UBIQUITOUS_LANGUAGE.md があれば確認する)
- **コードではなく振る舞いを説明する** — 「applyPatch() が42行目で例外を投げる」ではなく「同期サービスがパッチの適用に失敗する」
- **再現手順は必須である** — 特定できない場合はユーザーに尋ねる
- **簡潔に保つ** — 開発者が30秒でイシューを読めるようにする

作成後、すべてのイシュー URL(ブロッキング関係の要約付き)を表示し、「次のイシューがありますか、それとも完了ですか?」と尋ねる。

### 5. セッションを続ける

ユーザーが完了と言うまで続ける。各イシューは独立している — まとめて処理しない。
