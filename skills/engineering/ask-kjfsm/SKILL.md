# Ask kjfsm

全部は覚えなくていい。だから尋ねる。名前を思い出すだけなら `/help-skills`。

**フロー** = スキルを通り抜ける一本の道筋。ほとんどは1つの **メインフロー** に沿い、そこへ3つの **オンランプ** が合流する。残りはスタンドアロンである。

ここにあるのは **起点** — どのフローへ入るか。走っている最中に状況が満たされたときだけ入るものは [`SITUATIONS.md`](SITUATIONS.md) にある: テストの土台が無い・信用できない、スタック固有の規律(React Router / Drizzle / D1)、ロジックを変えない大量の機械的変更、マージがコンフリクトで止まった、スレッドが埋まった、プロセスではなく言葉が問題になった。

## メインフロー: アイデア → 出荷

1. **`/grill-with-docs`** — インタビューでアイデアを研ぐ。学んだことを `CONTEXT.md` と ADR に残す。コードベースなし → **`/grill-me`**(同じ `/grilling` プリミティブ、記録は残さない)。
2. **実行しないと答えられない問い**(状態、ビジネスロジック、見ないと決まらない UI)がある → プロトタイプへ寄り道。**`/handoff`** で外へ出し、新セッションの **`/prototype`** が使い捨てコードで答え、`/handoff` で持ち帰る。
3. 複数セッションにまたがるビルド → **`/to-spec`**(スレッド → スペック)→ **`/to-tickets`**(トレーサーバレット方式に分割し、各チケットに **ブロッキングエッジ** を宣言させる。ローカルは `.scratch/<feature>/issues/` に1チケット1ファイル、実トラッカーではネイティブなブロッキングリンク)。チケットごとに **`/implement`** を起動し、**チケットごとにコンテキストをクリアする**。1セッションで収まる → その場で **`/implement`**。

   **`/implement`** は **`/tdd`** を駆動してビルドし(レッド・グリーンを1スライスずつ)、**`/verification-loop`** で **クリーンラン**(記録されたゲートを中断なく1回で通し、変更した経路を実際に駆動して観測)を取り、コミット前に **`/two-axis-review`**(Standards + Spec)で締める。単体でも使う: テストファーストで作る → `/tdd`、動くか確かめるだけ → `/verification-loop`、固定した基点でブランチや PR をレビュー → `/two-axis-review`。

### コンテキストの衛生管理

手順1〜3は **1つの途切れないコンテキストウィンドウ** で進める — `/to-tickets` の後まで compact もクリアもしない。グリリング・スペック・チケットが同じ思考の上に積み上がる。各 `/implement` は新しいコンテキストから始める。

限界が **スマートゾーン** — モデルが鋭く推論できる範囲(最先端でおよそ12万トークン)。超えると技術的に収まっていても推論の質は落ちる。`/to-tickets` の前に近づいた → 押し進めず `/handoff` して新スレッドへ。

## オンランプ

- **バグや要望が積み上がった** → **`/triage`**。トリアージロールに沿って進め、エージェントが着手できる状態にする。後で `/implement` が拾う。**自分が作成していない** イシュー専用 — `/to-tickets` のチケットはすでに着手可能なので **トリアージしない**。

- **何かが壊れている** → **`/diagnosing-bugs`**。一目では太刀打ちできないバグ、断続的なフレーク、2つの正常な状態の間のリグレッション向け。**タイトなフィードバックループ**(_この_ バグですでにレッドになる1コマンド)を手にするまで理論化しない。発見が「このバグを封じ込めるシームがない」だった → **`/improve-codebase-architecture`** に引き継ぐ。

- **巨大で霧に包まれた取り組み**(グリーンフィールド、1セッションに大きすぎる機能)→ **`/wayfinder`**、最も認知負荷が高い。イシュートラッカー上に **意思決定チケット** の **共有マップ** を描き、1つずつ解決していく — **成果物ではなく意思決定** を生みながら。1セッションで抱えられるアイデアは `/grill-with-docs`、抱えきれないアイデアがこちら。よく絞り込まれた機能には決して使わない。

  晴れたマップは **ビルドせず、引き継ぐ**: **`/to-spec`** がリンクされた意思決定をビルド可能な計画へ畳み込み、メインフローに合流する。そのまま `/implement` へループさせると、畳み込みを飛ばしてリンクされた詳細を捨てる。実際には小さかったときに限り直接 `/implement`。

## コードベースの健全性

- **`/improve-codebase-architecture`** — 手が空いたら実行し、エージェントが操作しやすいコードベースを保つ。**深化の機会** を洗い出し、1つ選ぶと _アイデアが生まれ_、`/grill-with-docs` でメインフローに持ち込める。候補を見つける調査であり、選んだものを設計する作業台は **`/codebase-design`**。
- **`/tend-memory-files`** — セッション開始時にロードされる指示ファイル(`CLAUDE.md`、`CLAUDE.local.md`、`.claude/rules/`)を新規に書く、あるいは肥大化・陳腐化・矛盾を疑うたびに監査してトリムする。

## スタンドアロン

- **`/grill-me`** — `/grill-with-docs` と同じ容赦ないインタビュー、**コードベースがない** とき用。ステートレスで、ローカルに何も保存せず `CONTEXT.md` も作らない。
- **`/prototype`** — デザイン上の問い1つに答える使い捨てのプログラム。答えだけ残しコードは消す。メインフロー手順2の寄り道だが、そこに限らない。
- **`/research`** — 調べ物を **バックグラウンドエージェント** に委ね、**一次情報源** に当たった引用付きマークダウンを残す。読む間も作業を続けられる。成果は `/grill-with-docs` でメインフローに **持ち込む** — 思考の材料であって代わりではない。
- **`/teach`** — 現在のディレクトリをステートフルな作業スペースとして、複数セッションにわたり概念を学ぶ。
- **`/writing-great-skills`** — スキルを書き、編集するための語彙と判断基準。公式の数値上限・frontmatter 仕様・名指しのアンチパターンは同梱の `OFFICIAL.md`。

## 前提条件

**`/setup-cf-app`** — リポジトリがまだ無いときの出発点。Cloudflare Workers のフルスタックアプリを標準ライブラリ構成で立ち上げ、`/setup-repo` へ続く。

**`/setup-repo`** — 最初のエンジニアリングフローの前に実行する、setup 系の **唯一の入口**。順序と依存はこれが持つ。**再実行してよい** — 済んだ工程は飛ばし、ずれだけを直す。

敷くのは **届き方の違う4つの層**。下ほど確実に効き、上ほど広く効く。

- **`/setup-skills`**(毎セッション)— 他のスキルが前提とする設定一式。**検証ゲートの定義** もここ
- **`/setup-rules`**(その glob を編集するとき)— `paths:` を持つ rule と絶対ルール。**敷く側** で、監査とトリムは `/tend-memory-files`
- **`/setup-ci`**(push / PR)— そのゲートを CI で回す。手元で通しても記録は残らない
- **`/setup-hooks`**(ツール呼び出しのたび)— 散文では守られないものを決定的に弾く。**先回りしない**

規約が `CLAUDE.md` / `AGENTS.md` にも載るのは重複ではない。**出力スタイルはサブエージェントに届かない** — `/two-axis-review` や `/improve-codebase-architecture` が投げる子コンテキストに効かせるのはこちら側である。
