# メモリファイルの手入れ

対象は、セッション開始時にロードされる指示ファイル一式 — `CLAUDE.md`、`CLAUDE.local.md`、`.claude/rules/` — で、`/context` が **Memory files** として並べるものである。

CLAUDE.mdはセッション開始のたびに丸ごとコンテキストへ読み込まれる。長くなるほど指示への従いやすさ(adherence)は下がる — 公式ドキュメント([code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory))は1ファイル200行未満を目安に挙げている。このスキルは新規作成と既存ファイルの手入れの両方を、この一線を守りながら進める。

公式の裏取りが要るときは `/writing-great-skills` の `OFFICIAL.md` §10 を引く。何を入れて何を入れないかについて、ブログと製品ドキュメントが食い違っている箇所と、その裁き方がそこにある。

## 分岐

- **CLAUDE.mdがまだない** → 作成(手順1〜4)
- **すでにあり、肥大化・陳腐化・矛盾を疑っている** → 監査(手順5〜8)

## 作成

### 1. 線引きの基準

残る行は **発見不可能** かつ **グローバルに有用** の両方を満たす。片方でも欠けたら宛先が違う。

- **発見できる** — コード・config・`package.json`・型・検査スクリプトが答えを持っている。書かない。エージェントは探索フェーズでそれを読む
- **グローバルでない** — 一部のパスにしか効かない、特定の作業でしか要らない。`.claude/rules/`(`paths` 付き)かスキルへ

そのうえで、書き足す引き金は次のいずれかである:

- Claudeが同じ間違いを2度した
- コードレビューが、このコードベース特有の何かを見落としたと指摘した
- 前回のセッションで打ったのと同じ訂正・補足を、今回も打つ羽目になった
- 新しいチームメンバーが生産的になるために同じ文脈を必要とする

満たさないものは書かない。特に次の内容は、CLAUDE.mdではなく別の置き場所を持つ:

| 内容の性質                                                                                           | 置き場所                                                                                                                                                                                    |
| ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 複数手順の手続き                                                                                     | `skills/` 配下のスキル                                                                                                                                                                      |
| コードベースの一部にしか関わらないルール                                                             | `.claude/rules/`(`paths` frontmatterでglob指定)                                                                                                                                             |
| コードを読めば分かること(ディレクトリ構成、依存関係一覧、アーキテクチャ概観)                         | 書かない — Claudeは自分でコードを読める。`/doctor` のトリムが真っ先に削るのもここ。例外は**コードを読んでも出てこない構成情報**(モノレポでどのパッケージが何を担うか、生成物と手書きの境界) |
| 個数や網羅的な一覧のようなスナップショット(ファイル数、対応言語の数、依存パッケージのバージョンなど) | 書かない — プロジェクトが変わるたびに真っ先にズレる。数えた結果ではなく、数え方やルールを書く                                                                                               |

### 2. 下書きを作る

**`/init` の出力を出発点にしない。** 生成されるのはコマンド一覧・アーキテクチャ概観・ファイルとサービスの対応で、前2つは `package.json` と config を読めば出るもの、3つ目はリネームした瞬間に嘘になって能動的にミスリードする。実測でも、リポジトリ概要のコンテキストファイルはタスク成功率を上げないまま推論コストを2割以上増やしている — 従われるのは概要ではなく明示的な指示の方である。空のファイルから、手順1を通った行だけを足す方が速い。

すでに `/init` を走らせた後なら、生成された行を1つずつ手順1にかける。**ほとんど残らないのが正常である。**

材料はコードベースの解析ではなく **これまでのセッション** から取る — 打ち直した訂正、レビューの指摘、2度した間違い。手順1の引き金4つは、そのまま「どこを探すか」の一覧でもある。

### 3. 具体性を上げる

下書きの各行を検証可能な形に書き換える:

- 「コードを整形する」ではなく「インデントはスペース2つ」
- 「変更をテストする」ではなく「コミット前に `npm test` を走らせる」
- 「ファイルを整理しておく」ではなく「APIハンドラは `src/api/handlers/` に置く」

見出しと箇条書きで関連する指示をまとめる — Claudeは構造を人間と同じように読み取る。各行について「これは真か偽かを確認できるか?」と問い、答えがYesになるまで書き換えを終えない。

### 4. 目安の行数に収める

行数を数える。冒頭の目安を超えていたら手順1の表に戻り、何をスキルや `.claude/rules/` へ追い出せるか、何をただ削れるかを探す。各行に「これを消したらClaudeが間違えるか?」と問い、答えがNoならその行は消す。それでも収まらないほど大きなプロジェクトでは、ルートのCLAUDE.mdは骨格だけにし、詳細は `.claude/rules/` の複数ファイルへ分割する。

**`@path` の import へ移すのは、削ったことにならない。** import されたファイルは起動時にまとめて展開・ロードされるので、行数は移っただけでコンテキストは1トークンも減らない。減らせるのは2つだけである — **消す** か、`paths` frontmatter を持つ `.claude/rules/` へ移して**該当ファイルを触ったときだけロードされる**ようにするか。維持担当者向けのメモは、ブロックレベルの HTML コメント(`<!-- ... -->`)にすれば注入前に除去されるので、コンテキスト代はかからない。

## 監査

### 5. 対象を集める

ルートと各サブディレクトリのCLAUDE.md、`CLAUDE.local.md`、`.claude/rules/` 配下のファイルをすべて読む。ルート直下だけを見て終わらせない — 矛盾はたいてい階層をまたいで生まれる。

### 6. 行ごとに関連性を問う

1行ずつ、手順1の基準に照らす:

- これは今でも真か?(コードが変わって陳腐化していないか)
- 手順1の基準のどれかを満たすか?
- コードから導出できる内容や、個数・一覧のようなスナップショットになっていないか?
- 検査スクリプト・lint・型が弾くルールになっていないか?(決定的に弾けるものを散文で頼むと、コンテキストを払ったうえに「守られたか」を読む側が確認できない。散文が持つのは、機械が弾いた後に残る判断だけである)

満たさない行は削る。多手順の手続きになっている行はスキルへ、一部のファイルにしか関わらない行は `.claude/rules/` へ移す。

### 7. 矛盾を探す

手順5で集めたファイルを横断して、同じ振る舞いについて食い違う指示がないか確認する。見つけたら1つに統合する — 矛盾を放置すると、Claudeはその場でどちらかを勝手に選ぶ。

### 8. 数えて締める

`/context` を実行し、Memory filesの一覧で対象のファイルが実際にロードされていることを確認する。ロードされている各ファイルに `wc -l` をかけ、冒頭の目安を超えているものがあれば手順4と同じやり方で削る。差分をユーザーに見せ、書く前に確認を取る。

### 9. もっと大きい方を先に見る

同じ `/context` の内訳で、**Memory files より大きいのが普通なのはその隣の Tools / MCP tools である。** メモリファイルを数百行削るより、使っていないツール定義を落とす方が桁で効く。ここを持つのは `.claude/settings.json`(全プロジェクトなら `~/.claude/settings.json`)で、メモリファイルとは別の層なので、このスキルはどれが大きいかを見せるところまでを担う。

- `disableBundledSkills` / `disableWorkflows` — 機能ごと落とす。付随するツール定義と指示がまとめて消える
- `permissions.deny` に **素の名前**(`"NotebookEdit"`)を書くと、**そのツール定義がペイロードから消える**。`"Bash(rm *)"` のようなスコープ付きは呼び出しを止めるだけで、定義は載ったまま残る

**一覧を写して当てない。** 何が大きいかは `/context` を見てから決める。タスク系ツールや `Workflow` はバックグラウンドジョブとマルチエージェントが乗っているので、使っているなら消すと動かなくなる。
