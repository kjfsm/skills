# CI を敷く

`docs/agents/verification.md` が持つのは**ゲートの定義**であり、それを走らせるのは人間かエージェントの記憶しかない。CI は同じ列を、忘れようのない場所で回す。

**要るのはエージェントが嘘をつくからではない。証拠が残らないからである。** 「クリーンランを通した」という申告は、通したという記録ではない。手元と CI で環境が違えば、通ったこと自体が手元限定の事実になる — 生成物が古いまま通る、ローカルにだけ入っているツールで通る、コミットし忘れたファイルがあっても通る。CI が落とすのはたいていこの3つで、いずれも手元では症状が出ない。

**CI は `/verification-loop` の置き換えではない。** ゲートは手元で通したうえで、CI がもう一度通す。CI だけに寄せると、赤を知るのが数分後になり、その間にエージェントは次の変更を積む。

これはプロンプト駆動のスキルであり、決定的なスクリプトではない。探索し、見つけたものを提示し、ユーザーと確認し、それから書く。

## 手順

### 1. 探索する

- `docs/agents/verification.md` — **ゲートの定義はここが正**。無ければ先に `/setup-skills` の Section D を通す
- `.github/workflows/` — すでに何かあるか。あるなら追加であって新規作成ではない
- `package.json` の scripts / `Makefile` / `Taskfile` — verification.md の各行が実際に何を呼ぶか
- パッケージマネージャとロックファイル、`.node-version` / `.nvmrc` / `engines`
- `postinstall` — 生成物を作るならインストールだけで型チェックが通る。無いなら CI で明示的に生成コマンドを呼ぶ
- E2E のランナーとブラウザ。`playwright.config.ts` の `webServer`
- シークレットを要求する経路(デプロイ、リモート DB、外部 API)
- ホスティング先。GitHub 以外(GitLab CI、CircleCI)ならテンプレートは移し替える

### 2. 載る行と載らない行を分ける

verification.md の各行を1つずつ見て、**CI で走るか**を決める。推測でコマンドを足さない — ここで足した行は、手元では誰も走らせない行になる。

載らないものは3種類ある。

- **観測** — 人が画面を見る行。CI では代替できない。E2E がその一部を機械化しているが、同じものではない
- **シークレットを要る経路** — デプロイ、リモート DB へのマイグレーション。PR の CI からは触らせない
- **手元でしか意味が無いもの** — 性能の実測、対話的なウィザード

**載らないと決めた行は、verification.md 側にそう書く。** 書かないと、次に読む人が「CI が見ているはず」と思って飛ばす。

### 3. ジョブの割り方を決める

既定は **1ジョブ直列・速い順**。型チェック → lint / format → テスト → ビルド → E2E。落ちたら以降は走らない。

分けるのは、E2E が分単位で伸びてからでよい。分けると赤の原因が1画面で読めなくなり、ジョブ間でインストールとキャッシュをやり直すぶん総時間はむしろ増える。**先に分けない。**

`concurrency` で同じブランチの古い実行を打ち切る。付けないと、push を重ねたぶんだけ実行が並び、キューが詰まる。

### 4. 書く

テンプレートと各行の理由は [github-actions.md](./github-actions.md) にある。

**verification.md の順序をそのまま写す。** CI 側で並べ替えると、手元で落ちる場所と CI で落ちる場所が食い違う。

**ステップは verification.md の行と 1:1 にする。** CI にだけ存在するステップを足さない — 足したものは手元で走らないので、いずれ CI だけが赤くなる。ゲートを増やしたいなら verification.md に足してから CI に反映する。**向きは常に verification.md → CI である。**

3行を超えて畳みたくなったら、YAML に並べるのではなく `scripts/verify.sh` のような1本にまとめ、verification.md と CI の両方からそれを呼ぶ。二重管理はここでだけ避けられる。

### 5. 必須チェックにする

**ここまでで CI は助言でしかない。** 赤いままマージできる状態は、CI が無い状態とほとんど変わらない — 誰も落ちた実行を見に行かないためである。

これはリポジトリの設定であってファイルではないので、**ユーザーに手順を渡す**(自分で切り替えない):

> Settings → Branches → `main` の branch protection rule → **Require status checks to pass before merging** で、いま追加したジョブ名を選ぶ。

ジョブ名は追加後1度実行しないと選択肢に出ない。先に PR を1本通す。

`main` への直 push を禁じている絶対ルールがあるなら、同じ画面の **Require a pull request before merging** も入れる — 散文のルールが設定と一致していないと、どちらが正か判断する場面が生まれる。

### 6. 越えない線

- **CI から push しない。** フォーマッタの自動修正コミットも入れない。CI が書き戻すと、手元のブランチが黙って古くなり、次の push が非 fast-forward で落ちる。フォーマットは `--check` で**落とす**だけにする
- **`continue-on-error` でゲートを緑にしない。** 通らない行は、載せないか直すかの2択である
- **PR の CI に本番のシークレットを渡さない。** fork からの PR には渡らないので、渡す前提のゲートは fork で必ず落ちる

### 7. 完了

置いたファイルと、どのイベントで走るかをユーザーに伝える。**必須チェックの設定はユーザーの手に残っていること**を明示する — ここを伝え忘れると、緑を見て「守られている」と誤解したまま運用が始まる。

verification.md 側に、CI に載らないと決めた行の印を入れたことにも触れる。
