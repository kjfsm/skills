# EmDash を上げる

`create emdash` が落としてくる公式テンプレート([`emdash-cms/templates`](https://github.com/emdash-cms/templates)。既定は Cloudflare 向けのブログ `blog-cloudflare`)は EmDash のリリースごとに同期されるが、同期されるのは **依存の版** であって、コードが新しい API に乗り換わるとは限らない。作った直後のサイトは、`package.json` は最新なのに、コードは数版前の書き方のまま、という状態で始まる(例: 0.38 同期時点の `blog-cloudflare` は、0.37 で変わったアバターの URL を古い形で組んでいる)。

版上げは2通りあり、手順の大半は共通で、分かれるのは範囲の取り方である。

- **初回** — `create emdash` の直後。テンプレートのコードは依存より古いので、[CHECKLIST.md](CHECKLIST.md) を版に関係なく全項目判定する
- **2度目以降** — サイトに手が入ったあと。前に上げた版より新しい変更だけを見る。加えて、サイトのパッチとワークスペースのプラグインを新しい版に合わせる

## 前提

- 初回: `setup-emdash-site` の手順 4(同梱スキルの差し替え)まで済んでいて、雛形のままのコミットがある。まだ本番へデプロイしていない — CHECKLIST.md の「本番」は、最初のデプロイのあとにやることとして持ち帰る。
- 2度目以降: 上げる前に `pnpm why emdash` で今の版を控えておく。手順 1 のあとは新しい版しか返らず、手順 3・4 で使う「前に上げた版」が引けなくなる。

## 手順

**区切りごとにコミットを1つ作る。** 依存の更新・やることリストの各項目・生成型が1つに混ざると、型チェックやビルドが赤くなったときに、上げた依存と直したコードのどちらが原因か切り分けられない。コミットメッセージはリポジトリの慣習に合わせ(まだ無ければ日本語で「何をしたか」を1行)、本文に対応した版を書く。

### 1. 依存を上げる

初回は全部を上げる:

```bash
pnpm install
pnpm up --latest
pnpm why emdash
```

初回で EmDash 以外が上がって型チェックかビルドが壊れたら、その依存だけテンプレートの版へ戻してよい。戻した理由はコミットメッセージへ。

2度目以降は、`emdash`・`@emdash-cms/admin`・`@emdash-cms/cloudflare` を同じ版に上げ、`@emdash-cms/plugin-*` はそれぞれの最新に上げる(プラグインは別の版の系列で、同じ番号の版は無い)。ほかの依存も一緒に上げてよいが、壊れたものは前の版に留め、その理由を PR 本文に書く — 手を入れたサイトには、戻せばよいテンプレートの版がもう無い。

- **ワークスペースのプラグイン(`plugins/*/package.json`)の peer も同じ版へ上げる。** 古いままだと `emdash` が2つの版で入る。
- `pnpm-workspace.yaml` の `minimumReleaseAge` を使っているなら、公開されたばかりの版は `pnpm outdated` に出ず、`pnpm up` でも入らない。待たずに上げる理由(上流のセキュリティ修正など)があるときだけ `minimumReleaseAgeExclude` に足す。足した版の行は今の版だけにする — `pnpm add` は `1.0.1 || 1.2.0` の形で前の版を残して追記することがある。

**完了基準:** `pnpm why emdash` が1つの版だけを出す。`package.json`(ワークスペースのプラグインを含む)・`pnpm-workspace.yaml`・`pnpm-lock.yaml` をコミットする。

### 2. パッチを合わせる(2度目以降)

サイトの `patchedDependencies` に EmDash のパッチがあれば、`patching-emdash` スキルの「EmDash を上げるとき」に従って1本ずつ外すか作り直す。版付きのキーは新しい版に当たらず、作り直しには新しい版の `dist/` が要る。手順 1 の install がキーの不一致で落ちたら、古いキーを外して install を通し、パッチはそのあとで作り直す。完了の基準はあちらが持つ。

### 3. 越えた版の変更履歴を読む

初回は CHECKLIST.md の最新の版と、手順 1 で入った版を比べる。2度目以降は、前に上げた版と、いま入った版を比べる。そのあいだの版ごとに変更履歴を読む:

```bash
gh release view emdash@<版> -R emdash-cms/emdash --json body -q .body
gh release view @emdash-cms/cloudflare@<版> -R emdash-cms/emdash --json body -q .body
```

サイトのコードか本番の設定に効く変更を控える(手順 4・5 で使う)。管理画面の機能のうち、サイトの設定(`astro.config.mjs` の `admin`、`seed/seed.json`)で選べるものは、入れるかを決める。`seed/seed.json` の変更は本番の DB へは流れないので、本番にも要るなら管理画面で同じことをする作業として控える。

入れないと決めた変更は、理由とともに控える(手順 7 でユーザーに示し、2度目以降は PR 本文にも残す)。次に上げる人が同じ変更を読み直さずに済む。

### 4. やることリストを判定する

[CHECKLIST.md](CHECKLIST.md) を読み、判定を上から順に流す:

- **初回は版に関係なく全項目。** 雛形の版が何であっても、テンプレートのコードは依存より古い。`blog-cloudflare` から作ったなら、冒頭の表から手を付ける。
- **2度目以降は、前に上げた版より新しい節だけ。** それより古い節と「版に依らない」節は、前の版上げで判定済みである。

各項目で:

1. **判定** を流す。当たらなければ次へ。
2. 当たったら **対応** を行う。
3. **本番** があれば控える。
4. その項目だけでコミットする。1行で済む項目どうし(import の付け替えなど)はまとめてよいが、版をまたいでまとめない。

**完了基準:** 判定した全項目について、「当たらなかった / 対応した / 対応しないと決めた(理由)」を1行ずつ言える。

### 5. リストに無い変更を足す

手順 3 で控えた変更に対応し、**同じ変更を CHECKLIST.md に項目として足す**。次に上げるサイトは、履歴を読み直さずに済む。

- 項目は判定・対応・本番の3つで書く。**判定** は、サイトで機械的に流せる grep かコマンドにする。
- 足した項目が `blog-cloudflare` にも当たるかを判定し、冒頭の表を更新する(`git clone --depth 1 https://github.com/emdash-cms/templates` をスクラッチに置いて流す)。表の版と日付も、そのとき同期されている版に書き換える。
- CHECKLIST.md の正本は kjfsm/skills にある。インストール済みのプラグインの中の写しを直しても次の更新で消えるので、kjfsm/skills のチェックアウトで直し、サイトとは別の PR にする。チェックアウトも書き込み権も無ければ、足す項目をユーザーに渡して止まる。

### 6. 検証する

1. リポジトリの検証ゲート(型チェック・lint・整形・テスト・`pnpm build`)。
2. パッチがあれば、ビルドの成果物(`dist/server`)にパッチの行が入っていることを grep で確かめる。キーが当たらなかったパッチは install で落ちるが、当てる場所がずれたパッチは黙って効かない。
3. `pnpm dev` を起動し、生成型 `emdash-env.d.ts` が作り直されたら、それだけでコミットする。型が変わらない版では作り直されない。
4. 対応した項目のうち画面に出るもの(アバター、テーマ、表、コメント欄)は、dev サーバーでそのページを開いて確かめる。確かめられなかったものは「未確認」として控える。
5. 本番でしか見えない効果(パッチで減らすはずの書き込み、キャッシュ)は、「未観測」と、デプロイのあとどこで見るかを控える。

### 7. 引き継ぐ

初回は `setup-emdash-site` の手順 6 へ戻る。2度目以降は PR を出す。どちらも次をユーザーに示し、2度目以降は PR 本文にも書く:

- 対応した項目の一覧(版つき)と、未確認のもの
- 入れないと決めた変更と、その理由
- **デプロイのあとにやること:** 手順 3・4 で控えた「本番」の作業と、手順 6 で「未観測」とした効果

**完了基準:** 上の3つが示されていて、CHECKLIST.md に足した項目があればその PR が出ている(または項目をユーザーに渡した)。
