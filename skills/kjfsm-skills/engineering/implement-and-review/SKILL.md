# 実装してレビューする

ユーザーがスペックやチケットで記述した作業をビルドし、締めて PR を出す。引数でチケットやスペックの参照が渡された場合は、それが実装対象である。

複数のチケットを渡されたときは、手順のリストではなく **タスクグラフ** として読む — 着手できるのはブロッカーが片付いたものだけで、その集合は1つ終えるたびに変わる。

## 着手する前に、既定ブランチに追いつく

`git fetch` で既定ブランチの最新を取る。

- **既定ブランチに居るなら、先にブランチを切る** — 作業から付けた短い名前で。既定ブランチへの直 push を禁じているリポジトリがあり、最後の PR もこのブランチから出す。未コミットの変更はそのまま新しいブランチへ付いてくる。
- **依頼と無関係な未コミットの変更は、自分の変更に混ぜない。** 書き手が違うものが1つの PR に入ると、レビューする人は依頼した変更がどこまでかを差分から見分けられない。先にその中身(ファイル一覧と差分の要点)をユーザーに示して確認を取り、それから、それだけで別ブランチと draft PR を1本作り、配線が済んでいない箇所を本文に名指しする — 他人の書きかけは秘密情報や未完成の断片を含みうるので、確認なしに push しない。中身は書き手のものなので、こちらで完成させない。そのうえで自分の作業を別のブランチで始める。
- **未コミットの変更があれば退避する。** `git stash push -u -m <固有のタグ>` で積み、直後に `git stash list --format='%H %gs'` で自分のエントリの SHA を控える。取り込んだら `git stash apply <SHA>` で戻し、タグで探し直して drop する。素の `git stash pop` は使わない — stash の山は他の worktree やセッションと共有されていて、他人の変更を取り出しうる。
- **`gh stack view --json` が今のブランチを含むスタックを返すなら、`gh-stack` スキルの同期の手順に任せる** — 手で取り込むと上の層がずれる。衝突したときの戻し方もそちらにある。
- それ以外は `git merge origin/<既定ブランチ>` で取り込む。rebase はしない — push 済みのブランチの履歴を書き換えると force push が要り、衝突もコミットの数だけ解き直すことになる。

衝突したら、ハンクごとに両側の出所 — そのハンクを持ち込んだコミットのメッセージ、PR、イシュー — を `git log --merge -p -- <ファイル>` から読み、2つの意図として解く。差分の見た目だけで `--ours` / `--theirs` を選ぶと、構文は通っても誰かが意図して入れた変更が黙って落ちる。両立する意図は両方残し、どちらのブランチにも無かった振る舞いを足して衝突を隠さない。解き終えたら、マージをコミットする前に型チェックと、衝突したファイルに触れるテストを走らせる — 両側の行がそれぞれ正しくても、組み合わせた振る舞いはどちらのブランチにも無かったものになりうる。スイート全体は締めの `verification-loop` が持つ。

双方の意図が両立しないハンクでは、どちらかを選ばない — ここは追いつくための取り込みで、片方を捨てる根拠になる目標が無い。そのハンクをユーザーに示して止まる。

作業ブランチが既定ブランチの最新を含み、退避した変更が戻っていたら、ビルドに入る。

## ビルドする

`tdd` スキルを呼び、シームで赤→緑を回す。シームはスペックが名指していればそれを、名指していなければ、同種の振る舞いを守っている最も近いテストの層(HTTP の入口、純粋関数、E2E など)を自分で選び、合意済みのシームとして tdd に渡す。ユーザーの確認は待たない。選んだシームは PR 本文(PR を作らないなら最後の報告)に書き、確認はレビューで受ける。シームの合意を tdd を呼ぶ前提にしない — 前提に読めると、合意の無いスペックでは tdd ごと飛ばされる。

tdd を呼ばないのは、スタイル・文言・docs だけの差分のときに限る。そう PR 本文に1行書き、確かめは締めの観測に任せる。ロジックを含むのに、その層のテスト基盤が無い(画面のコンポーネントなど)なら、ロジックを純粋関数へ出し、そこで回す。

型チェックと、触ったテストファイル単体はこまめに走らせる。スイート全体は最後に1回 — それは次の `verification-loop` が持つ。

本家の `/mattpocock-skills:implement` は経由しない — あちらは最後に `code-review` とコミットまで済ませ、コメントを削る前にコミットされる。

複数のチケットなら、ブロッカーの片付いたものを1本ずつビルドし、1本ごとに下の「締める」から PR までを通してから次へ進む。

## 締める

ビルドが済んだら `verification-loop` スキルを呼び、クリーンランを取る。**`AGENTS.md` や `CLAUDE.md` がゲートを `pnpm verify` のような1コマンドで名指ししていても、それを本体で叩いて済ませない** — 常駐の「ゲートを通す」はこのスキルを呼べば満たされる。本体で叩くと生ログが文脈に積もり、`verifier` への委譲、`docs/agents/verification.md` のカスタムチェック、変更前から赤だったゲートの切り分け、ラチェットが抜ける。

**差分が画面を触ったとき**(コンポーネント・スタイル・マークアップ)は、クリーンランの観測に加えて次の4点を実際に動かして見る。表示される文言だけを変えたなら、長い文字列だけでよい。

- **狭い幅** — 360px 前後で崩れ・はみ出し・横スクロールが出ないか
- **長い文字列** — 長い名前や改行の入らない英数字で溢れないか
- **タッチ** — ホバーに頼る操作や、指で押せない小さな当たり判定が無いか
- **読み上げ** — ラベル・見出し・フォーカスの順で意味が通るか

`break-ui`(長い文字列・狭い幅)、`mobile-native`(タッチ)、`web-design-guidelines`(読み上げ)が入っていれば、その点で呼ぶ。どれもこのプラグインは配っていないので、入っていなければ同じ点を自分で見る。結果は PR 本文(PR を作らないなら最後の報告)に1点1行で書く — 行がそろっていなければ、見なかった点があると読める。ブラウザを動かせない環境なら、見られなかった点を「未確認」と書く。

クリーンランが取れたら `prune-comments` スキルを呼び、書いてしまったコメントを削る。**レビューより先に置く** — 先に削っておくと `two-axis-review` の目が、消し忘れではなく書かれなかった Why not のほうへ向く。コメント行が1行も増えていなければ、そのスキルが自分で降りる。

続けて `two-axis-review` スキルを呼び、作業をレビューする。スペックには実装したチケットを渡す — まだコミットが無いので、渡さないとコミットメッセージから探せずユーザーに尋ねに行く。

指摘のうち、直し方が自明なものは直し、`verification-loop` スキルを呼んでクリーンランを取り直す — 直した編集は前のクリーンランに含まれていない。要件に無いもの(スペックが求めていない振る舞いや、_任意_ の改善)は直さず、PR 本文と最後の報告に載せる。

## コミットして PR を出す

コミットメッセージと PR 本文を書く前に `where-to-write-what` スキルを呼び、何をコミットと PR 本文に載せ、何をコメントや ADR へ回すかを決める。チケットが issue なら、PR 本文に `Closes #<番号>` を入れてマージで閉じる。

作業ブランチにコミットし、push して PR を出す。

- **スタックの中なら `gh-stack` スキルに従って出す** — `gh pr create` ではベースが下の層にならない。今の層が別のチケットのものなら、コミットの前に層を積む。そちらの出し方(`submit --auto`)はコミットの本文をそのまま PR 本文にするので、出たら `gh pr edit <番号> --body` で PR 本文の基準に差し替える。
- それ以外は `git push -u origin <ブランチ>` のあと `gh pr create`。

ユーザーが「PR は作らないで」「push しないで」と言っていれば、コミットで止まる。

PR の URL をユーザーに示したら完了である。
