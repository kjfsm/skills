# インターフェースを設計する

"A Philosophy of Software Design" の「Design It Twice」に基づく: 最初のアイデアが最良である可能性は低い。根本的に異なる複数の設計を生成し、それらを比較する。

## ワークフロー

### 1. 要件を集める

設計に入る前に、以下を理解する。

- [ ] このモジュールはどんな問題を解決するのか?
- [ ] 呼び出し元は誰か?(他のモジュール、外部ユーザー、テスト)
- [ ] 主要な操作は何か?
- [ ] 制約はあるか?(パフォーマンス、互換性、既存パターン)
- [ ] 内部に隠すべきものと、外に公開すべきものは何か?

尋ねる: 「このモジュールは何をする必要がありますか? 誰が使いますか?」

### 2. 設計を生成する(並列サブエージェント)

Agent ツールを使って3つ以上のサブエージェントを同時に起動する。それぞれが**根本的に異なる**アプローチを生み出さなければならない。

```
各サブエージェント向けのプロンプトテンプレート:

以下のインターフェースを設計してください: [モジュールの説明]

要件: [集めた要件]

この設計の制約: [エージェントごとに異なる制約を割り当てる]
- Agent 1: "メソッド数を最小化する - 1〜3メソッドを目安にする"
- Agent 2: "柔軟性を最大化する - 多くのユースケースをサポートする"
- Agent 3: "最も一般的なケースに最適化する"
- Agent 4: "[特定のパラダイム/ライブラリ] から着想を得る"

出力フォーマット:
1. インターフェースのシグネチャ(型/メソッド)
2. 使用例(呼び出し元がどう使うか)
3. この設計が内部に隠すもの
4. このアプローチのトレードオフ
```

### 3. 設計を提示する

それぞれの設計を次の内容とともに示す。

1. **インターフェースのシグネチャ** - 型、メソッド、パラメータ
2. **使用例** - 呼び出し元が実際にどう使うか
3. **隠しているもの** - 内部に留められた複雑さ

ユーザーが各アプローチを比較の前に消化できるよう、設計は順番に提示する。

### 4. 設計を比較する

すべての設計を示した後、以下の観点で比較する。

- **インターフェースの単純さ**: メソッド数が少なく、パラメータがシンプルか
- **汎用 vs 特化**: 柔軟性か、焦点の絞り込みか
- **実装効率**: この形は効率的な内部実装を許すか?
- **深さ**: 大きな複雑さを隠す小さなインターフェース(良い)か、実装が薄い大きなインターフェース(悪い)か
- **正しく使う容易さ** vs **誤用する容易さ**

トレードオフはテーブルではなく散文で議論する。設計が最も分岐する点を強調する。

### 5. 統合する

多くの場合、最良の設計は複数の選択肢からの洞察を組み合わせたものになる。尋ねる:

- 「どの設計があなたの主なユースケースに最も合いますか?」
- 「他の設計から取り入れる価値のある要素はありますか?」

## 評価基準

"A Philosophy of Software Design" より:

**インターフェースの単純さ**: メソッドが少なく、パラメータがシンプル = 学びやすく正しく使いやすい。

**汎用性**: 変更なしに将来のユースケースに対応できる。ただし過度な汎用化には注意する。

**実装効率**: インターフェースの形が効率的な実装を許しているか? それとも不格好な内部実装を強いていないか?

**深さ**: 大きな複雑さを隠す小さなインターフェース = 深いモジュール(良い)。実装が薄い大きなインターフェース = 浅いモジュール(避ける)。

## アンチパターン

- サブエージェントに似たような設計を生成させない - 根本的な違いを強制する
- 比較を省略しない - 価値は対比の中にある
- 実装しない - これは純粋にインターフェースの形についてのものである
- 実装の手間で評価しない
