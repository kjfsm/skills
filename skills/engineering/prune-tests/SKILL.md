# テストを削るパス

判定の軸は1つ: **このテストを消すと、どんな現実的な不具合を見逃すか。** その答えの重さを、テストが払わせているコスト — 実行時間・不安定さ・修正負担 — と比べる。

**件数とカバレッジは、どちら向きにも目的にしない。** 残す理由にもならないし、削った成果にもならない。1件も削れないという結論は失敗ではない。

書く時点の規律は `tdd` と `create-tests`、足場(設定・モックの構造)ごと作り直すのは `rebuild-tests` の仕事である。ここは足場に手を付けず、書かれてしまった中身だけを削る。

## 手順1 — 全テストを列挙し、コストを測る

作業用のディレクトリを1つ切り(`mktemp -d`)、以降の表はすべてそこに置く。**表をファイルに置くのは、この作業のコンテキストが途中で圧縮されても判定が残るようにするため**である。

- **列挙** — ユニット・統合・E2E のすべてのランナーについて、設定の `include` / `testMatch` から対象ファイルを出し、`files.txt` に1行1パスで書く。ファイル名のパターンで grep するのは出発点にすぎない — ランナーが実際に拾う集合が正である。
- **所要時間** — 各ランナーを JSON レポーターで1回だけ回し、ファイル別の秒数を `durations.tsv` に書く。回せない(外部サービスが要る、など)ランナーは「未計測」と書いて進む — **推測で埋めない。**
- **ゲートの在処** — `docs/agents/verification.md` があればそこに、無ければ `package.json` の scripts と CI の定義にある。

完了: `files.txt` がすべてのランナーの対象を漏れなく含み、各ランナーについて所要時間か「未計測」の理由がある。

## 手順2 — スライスに分けて棚卸しさせる

**`test-auditor` サブエージェントを、スライスごとに並列で起動する。** 判定の問い・6つの分類・表の列・報告の形はそちらが1部だけ持つ — **ここには写さない。** 呼び出しのたびに貼り直す本文は、貼り忘れた日に黙って消える。

自分で読んで判定しない。数百ファイルを1つのコンテキストに入れると、後半ほど判定が雑になる。

- **切り方** — 1体あたり30ファイル前後。**同じプロダクションコードを対象にするテストは同じスライスに寄せる。** ディレクトリで機械的に切ると、ユニットと統合に分かれた重複が別々のスライスに割れる
- **渡すもの** — そのスライスのファイル一覧、書き出し先(`slice-<n>.tsv`)、`durations.tsv` のパス
- テストファイルが30本に満たなくても1体に渡す。毎回同じ経路を通すためである

完了: 全員の報告で「読んだ数 = 渡した数」であり、表に載ったファイルの集合が `files.txt` と一致する。

```bash
cut -f1 slice-*.tsv | sed 's/:[0-9]*$//' | sort -u | comm -3 - <(sort -u files.txt)
```

何か出たら、それが判定されていないファイルである。そのファイルだけで、もう1体に渡す。

## 手順3 — スライスをまたぐ重複を突き合わせる

表の列 4(対象)が、2つ以上のファイルに現れる対象を抜き出す。

```bash
cat slice-*.tsv > all.tsv
awk -F'\t' '{ split($1, p, ":"); print $4 "\t" p[1] }' all.tsv | sort -u |
  cut -f1 | uniq -d > shared-targets.txt
awk -F'\t' 'NR==FNR { t[$0]; next } $4 in t' shared-targets.txt all.tsv |
  sort -t$'\t' -k4,4 > groups.tsv
```

`groups.tsv` を **`test-auditor` 1体に突き合わせとして渡す**(書き出し先は `merged.tsv`)。重複の判定もエージェントが持つ基準で行うためで、ここで自分が判定すると同じ基準が2か所に割れる。返ってきた行で `all.tsv` の該当行を置き換える。

完了: `shared-targets.txt` のすべての対象について、突き合わせを通った行が `all.tsv` に入っている。

## 手順4 — `保留` を、壊して決める

`保留` の行には、決着をつける主張(「この条件を外すと、このテストが落ちるか」)が付いている。1件ずつ確かめる。

1. `git status` がクリーンであることを確かめてから始める
2. 主張どおりにプロダクションコードを1か所だけ壊す
3. 関係するテストファイルだけを走らせ、どれが落ちたかを見る
4. `git checkout -- <壊したファイル>` で戻す

**1件ずつ、順番に。** 並列にすると、どの破壊がどのテストを落としたのか分からなくなる。結果に従って、その行を `残す` / `削除` / `統合` に書き換える。

完了: `保留` が0件か、残った `保留` のそれぞれに確かめられなかった理由がある。

## 手順5 — 一覧を出して止まる

`削除` と `統合` の行を、省けるコストの大きい順に並べて応答に出す。1件ごとに:

- 対象(`ファイル:行` とテスト名)と分類
- **消すと見逃す不具合** — `無し`、または捕まえる別のテスト
- `統合` なら統合先と、移すアサーション
- 省けるコスト(秒数・不安定さ・修正負担のうち根拠があるもの)

末尾に件数と、ファイルごと消える分の合計秒数を添える。**一部だけ消すファイルの短縮分は測っていないので、足さない。**

もう1つ、**所要時間の上位にあるのに `残す` と判定したもの** を、見逃す不具合1行つきで並べる。削らない判断も判断であり、ユーザーはコストの大きいものほどその根拠を見たい。

**ここで止まる。消さない。** 消すかどうかはユーザーが1件ずつ決める。

## 承認されたものを当てる

`統合` は先に統合先へアサーションを移してから、元を消す。消し終えたら `verification-loop` スキルでクリーンランを取る。

コミットメッセージには、消したものごとの「見逃す不具合: 無し / 捕まえる別のテスト」を書く — 消えたテストについての Why は、コミットログにしか残らない。
