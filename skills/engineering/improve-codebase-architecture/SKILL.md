# Improve Codebase Architecture

アーキテクチャ上の摩擦を表面化させ、**深化の機会** — 浅いモジュールを深いモジュールに変えるリファクタリング — を提案する。狙いはテスト可能性と AI にとってのナビゲートしやすさである。

このコマンドはプロジェクトのドメインモデルに _即して_ おり、共有された設計語彙の上に成り立っている:

- アーキテクチャの語彙(**モジュール**、**インターフェース**、**深さ**、**シーム**、**アダプター**、**レバレッジ**、**局所性**)とその原則(削除テスト、「インターフェースはテストの表面である」、「アダプターが1つなら仮のシーム、2つなら本物」)については `/codebase-design` スキルを実行する。すべての提案でこれらの用語を正確に使う — 「コンポーネント」「サービス」「API」「境界」のような言葉に流れない。
- `CONTEXT.md` のドメイン言語は良いシームに名前を与える。`docs/adr/` の ADR は、このコマンドが蒸し返すべきでない決定を記録している。

## 手順

### 1. 探索する

**スキャンする前にスコープを決める — YAGNI。** モジュールを深化させることの見返りは、それへの今後の変更を容易にすることなので、最近変更されたコードベースの部分に余分な重みを置く。見る *前に*、*どこ* を見るかを決める:

- ユーザーが方向性 — モジュール、サブシステム、痛点 — を指定していれば、それに従い、下記の推定はスキップする。
- そうでなければ、コミット履歴(`git log --oneline`)をある程度遡り、コードベースのホットスポット — 何度も出てくるファイルや領域 — を見つけ、そのパスに最初に注意を向ける。変更が散らばっていて明確なホットスポットがない場合は、網を広げる。

まずプロジェクトのドメイン用語集(`CONTEXT.md`)と、触れる領域にある ADR を読む。

それから Agent ツールを `subagent_type=Explore` で使い、コードベースを歩く。硬直したヒューリスティックに従うのではなく、有機的に探索し、摩擦を感じたところをメモする:

- 1つの概念を理解するために、多くの小さなモジュールを行き来する必要があるのはどこか?
- モジュールが **浅い** — インターフェースが実装とほぼ同じくらい複雑 — なのはどこか?
- テスト可能性のためだけに純粋関数が切り出されているが、本当のバグはそれがどう呼ばれるかに隠れている(**局所性** がない)のはどこか?
- 密結合したモジュールがそのシームを越えて漏れ出しているのはどこか?
- コードベースのどの部分がテストされていないか、あるいは現在のインターフェースを通してテストしにくいか?

浅いと疑うものすべてに **削除テスト** を適用する: それを削除したら複雑さは1か所に集約されるか、それとも単に移動するだけか?「はい、集約される」というのが求めているシグナルである。

### 2. 候補を HTML レポートとして提示する

何もリポジトリに残らないよう、自己完結した HTML ファイルを OS の一時ディレクトリに書く。一時ディレクトリは `$TMPDIR` から解決し、なければ `/tmp`(Windows では `%TEMP%`)にフォールバックし、`<tmpdir>/architecture-review-<timestamp>.html` に書いて、実行のたびに新しいファイルになるようにする。ユーザーのためにそれを開く — Linux では `xdg-open <path>`、macOS では `open <path>`、Windows では `start <path>` — そして絶対パスを伝える。

このレポートはレイアウトとスタイリングに **CDN 経由の Tailwind** を、グラフ/フロー/シーケンスが構造を確実に伝える図には **CDN 経由の Mermaid** を使う。Mermaid と手作りの CSS/SVG のビジュアルを混ぜる — 関係がグラフ的な形(呼び出しグラフ、依存関係、シーケンス)のときは Mermaid を使い、もっと編集的なもの(マス図、断面図、折りたたみアニメーション)が欲しいときは手作りの div/SVG を使う。各候補には **ビフォー/アフターの可視化** をつける。視覚的であること。

各候補について、次を含むカードを描画する:

- **ファイル** — どのファイル/モジュールが関わっているか
- **問題** — 現在のアーキテクチャがなぜ摩擦を引き起こしているか
- **解決策** — 何が変わるかの平易な説明
- **利点** — 局所性とレバレッジの観点から説明し、テストがどう改善するか
- **ビフォー/アフター図** — 並べて、独自に描いたもの。浅さと、深化していく様子を示す
- **推奨の強さ** — `Strong`、`Worth exploring`、`Speculative` のいずれかを、バッジとして描画する

レポートの最後は **一番のおすすめ** セクションで締める: どの候補に最初に取り組むべきか、そしてなぜか。

**ドメインには CONTEXT.md の語彙を、アーキテクチャには `/codebase-design` の語彙を使う。** `CONTEXT.md` が「Order」を定義しているなら、「FooBarHandler」でも「Order サービス」でもなく、「Order intake モジュール」と語る。

**ADR との衝突**: ある候補が既存の ADR と矛盾する場合、その摩擦が ADR を再検討するに値するほど本物であるときだけ表面化させる。カードの中にはっきりと印を付ける(例えば警告のコールアウト: _「ADR-0007 と矛盾するが、…という理由で再検討する価値がある」_)。ADR が禁じている理論上のリファクタリングをすべて列挙しない。

完全な HTML の骨格、図のパターン、スタイリングの指針については [HTML-REPORT.md](HTML-REPORT.md) を参照。

まだインターフェースは提案しない。ファイルを書いたら、ユーザーに尋ねる: 「これらのうち、どれを掘り下げてみたいですか?」

### 3. グリリングループ

ユーザーが候補を1つ選んだら、`/grilling` スキルを実行し、決定木を一緒に歩く — 制約、依存関係、深化したモジュールの形、シームの裏に何を置くか、どのテストが生き残るか。

決定が固まるにつれて、その場で副次的な作業が発生する — 進めながらドメインモデルを最新に保つため `/domain-modeling` スキルを実行する:

- **深化したモジュールに、`CONTEXT.md` にない概念の名前を付ける?** その用語を `CONTEXT.md` に追加する。ファイルが存在しなければ、その場で作る。
- **会話の中で曖昧な用語を研ぎ澄ました?** その場で `CONTEXT.md` を更新する。
- **ユーザーが本質的な理由でその候補を却下した?** ADR を提案する。フレーズは: _「これを ADR として記録して、今後のアーキテクチャレビューで同じ提案を繰り返さないようにしましょうか?」_ その理由が、同じ提案を繰り返さないために将来の探索者に本当に必要とされる場合にのみ提案する — 一時的な理由(「今はその価値がない」)や自明な理由はスキップする。
- **深化したモジュールの代替インターフェースを探りたい?** `/codebase-design` スキルを実行し、その design-it-twice の並列サブエージェントパターンを使う。
