# 依頼を研ぐ

曖昧な改善依頼に欠けているのは、たいてい要件ではなく **判定の問い** である。「整理したい」の対象は見えている — テスト、画面、モジュール。見えていないのは、1つの項目を前にしたとき、変えるか残すかを何で決めるかである。それが無いまま走らせると、モデルは既定の偏りで動き、実行ごとに違う結果を返す。

ここで作るのは指示文であって、作業ではない。作業は、ユーザーが指示に合意してから始める。依頼がすでに判定の問いを持っているなら、研がずにそのまま進む。

「何を作るか」自体が決まっていない — 決めることが多く、互いに依存している — なら `grilling` スキルの領分である。ここが扱うのは、対象も方向も見えているのに、良し悪しの物差しが言葉になっていない依頼である。

## 見本

「テストを整理したい」から研いだ指示:

```
コードベース内の全テストを精査し、積極的に削除・統合できるテストをすべてリストアップしてください

- 削る対象: 実装のコピー、モックの自己検証、型・ライブラリの保証の再確認、他テストとの重複、内部実装への過度な依存、過剰なケース分け
- 判断基準は「削除すると、どんな現実的な不具合を見逃すか」。念のためという理由で残さず、実行時間・不安定さ・修正負担と保証の価値を比較すること。
- テスト件数やカバレッジ維持自体を目的にしないこと。
```

見本は形の出所であって、テストの判定基準の出所ではない。実際にテストの依頼が来たら、手順1でその基準を持つスキルへ回る。

## 良い指示の7つの部品

見本はこの7つを全部持っている。1つでも欠けると、欠けた箇所をモデルが既定の偏りで埋める。

1. **範囲** — 全部か、どこか。見本では「コードベース内の全テスト」。全部なら、1つも飛ばさないことが完了の条件になる。
2. **止まる地点** — 一覧を出して止まるのか、直すところまでやるのか。見本では「リストアップ」。範囲が広い、あるいは戻しにくい変更なら、一覧で止まるのを既定にする。
3. **方向と強さ** — モデルの既定の偏りと逆へ行かせたいなら、はっきり書く。見本では「積極的に」。テストやコードは残す側に、UI は足す側に、構造は抽象を増やす側に倒れやすい。
4. **対象の名指し** — 何を変えるかを、そのドメインで既に名前の付いた失敗の形で並べる。「不要なもの」「悪いところ」は名指しではない。名前はそのドメインの確立した語彙と、このリポジトリの証拠(繰り返し直された箇所、レビューで何度も付いた指摘)から取る。
5. **判定の問い** — 1項目ずつ答えが決まる、反実仮想の問いを1つ。形は「これを変えると / 消すと、どんな現実的な<不具合 / 迷い / 手間>が<起きる / 減る>か」。
6. **比べるコスト** — 判定の問いの答えと天秤にかけるもの。見本では実行時間・不安定さ・修正負担。
7. **目的にしないもの** — 既定の言い訳(「念のため」)と、目的と取り違えやすい数(件数・カバレッジ・スコア・行数)を名指しで外す。

判定の問いは、次の3つを満たすまで直す。

- **1つの項目に当てられる** — 「全体としてきれいか」は項目に当たらない
- **答えを観測で確かめられる** — 壊す、測る、触ってみる
- **2つのセッションに同じ項目を渡すと、同じ答えが返る** — 「分かりやすいか」「きれいか」のように好みを問う形は、ここで落ちる。「現実的な」の一語は、想像上の極端(「誰かが全部書き換えたら」)を締め出すためにある

## 他のドメインでの形

同じ7部品を、見本とは別の依頼に当てるとこうなる。行をそのまま写さず、対象の名指しと問いをその依頼に合わせて起こし直す。

| 依頼               | 判定の問い                                                                         | 比べるコスト                                   | 目的にしないもの                             |
| ------------------ | ---------------------------------------------------------------------------------- | ---------------------------------------------- | -------------------------------------------- |
| UI/UX を改善したい | 変えると、どの利用者のどの作業で、迷い・誤操作・待ちがどれだけ減るか               | 実装と保守の手間、利用者が覚えた操作を崩すこと | 見た目の新しさ、スコア、画面や機能の数       |
| 構造を整理したい   | 変えると、次に来る現実的な変更で、触るファイルと知っておくべきことがどれだけ減るか | 移行の手間、差分の大きさ、レビューの負担       | 行数・ファイル数・抽象の数、パターンへの準拠 |

## 手順

### 1. 事実を集める — ユーザーに聞く前に

対象の規模(項目の数)、スタック、既存の規約とドメイン文書(`CONTEXT.md`、ADR、`docs/agents/`)、関係する過去の修正と苦情(`git log --grep`、イシュー)を見る。**調べれば分かることをユーザーに聞かない。**

このセッションで使えるスキルに、そのドメインの **判定の基準を持つ** ものがあれば、指示は「そのスキルを使う」に置き換え、足りない部品だけを足す。作るためのスキル(UI を組む、プロトタイプを作る)は判定の基準を持たないので当たらない。同じ基準を指示文とスキルの2か所に書くと、片方だけが直る日が来る。

完了: 項目の数、既存の規約、関係する過去の修正と苦情の有無が分かっていて、判定の基準を持つスキルに置き換えるかどうかが決まっている。

### 2. 7つの部品で下書きする

部品ごとに埋める。**埋められなかった部品が、ユーザーに聞く問いになる。**

### 3. 決められないものだけを聞く

聞くのは、リポジトリからは分からず、答えによって指示が変わるものに限る。多くは「誰のための改善か」(UI)か「次に来る変更は何か」(構造)である。**3問まで、それぞれ推奨の答えを添える。** それを超えて互いに依存する決定が残っているなら、それは研ぐ段階ではない — `grilling` スキルを呼ぶ。

### 4. 指示文を出して止まる

見本と同じ形で、コードブロックに入れて出す。そのまま貼って使えるようにするためである。

- **1行目** — 範囲・方向と強さ・止まる地点(見本の「全テストを精査し、積極的に…リストアップ」)
- **箇条書き** — 対象の名指し、判定の問いと比べるコスト、目的にしないもの

**指示文にはリポジトリ固有の事実を書かない。** 同じ指示を別のリポジトリや並列のセッションに配っても、同じ基準で動くようにするためである。証拠から取り出してよいのは **失敗の型** と **利用者の役割** まで — 「同名で見分けのつかない選択肢」「管理者」は書いてよく、イシュー番号・件数・ファイル名・個別の事件は書かない。後者は指示文の外に「このリポジトリでは」として添える。

完了: 7つの部品がすべてある(スキルに置き換えたなら、そのスキルが持たない部品がすべてある)。判定の問いは上の3条件を満たしている。

**ここで止まる。** 走らせるのは、ユーザーが指示に合意してから — このセッションで続けるか、別のセッションへ配るかはユーザーが決める。
