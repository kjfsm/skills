# Domain Docs

コードベースを探索するとき、エンジニアリング系スキルがこのリポジトリのドメインドキュメントをどう扱うべきか。

## 探索する前に、これらを読む

- リポジトリルートの **`CONTEXT.md`**、あるいは
- 存在すればリポジトリルートの **`CONTEXT-MAP.md`** — コンテキストごとに1つの `CONTEXT.md` を指している。話題に関連するものをそれぞれ読む。
- **`docs/adr/`** — これから作業しようとしている領域に触れる ADR を読む。複数コンテキストのリポジトリでは、コンテキスト範囲の決定について `src/<context>/docs/adr/` も確認する。

これらのファイルのいずれかが存在しない場合は、**黙って進める**。その不在を指摘せず、先回りして作成を提案しない。(`/grill-with-docs` と `/improve-codebase-architecture` から到達する)`/domain-modeling` スキルが、用語や決定が実際に解決したときに遅延生成する。

## ファイル構造

単一コンテキストのリポジトリ(ほとんどのリポジトリ):

```
/
├── CONTEXT.md
├── docs/adr/
│   ├── 0001-event-sourced-orders.md
│   └── 0002-postgres-for-write-model.md
└── src/
```

複数コンテキストのリポジトリ(ルートに `CONTEXT-MAP.md` が存在する):

```
/
├── CONTEXT-MAP.md
├── docs/adr/                          ← system-wide decisions
└── src/
    ├── ordering/
    │   ├── CONTEXT.md
    │   └── docs/adr/                  ← context-specific decisions
    └── billing/
        ├── CONTEXT.md
        └── docs/adr/
```

## 用語集の語彙を使う

あなたの出力がドメインの概念を名指しするとき(イシューのタイトル、リファクタリングの提案、仮説、テスト名など)は、`CONTEXT.md` で定義された用語を使う。用語集が明示的に避けている同義語には流れない。

必要な概念がまだ用語集にない場合、それはシグナルである — プロジェクトが使っていない言葉を作り出しているか(考え直す)、本当のギャップがあるか(`/domain-modeling` のためにメモしておく)のどちらかである。

## ADR との衝突を指摘する

あなたの出力が既存の ADR と矛盾する場合、黙って上書きするのではなく、明示的に表面化させる:

> _ADR-0007(イベントソーシングの注文)と矛盾する — ただし、…という理由で再検討する価値がある_
