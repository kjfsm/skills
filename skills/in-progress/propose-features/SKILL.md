# 機能を提案する

既存のアプリに **足すと便利な機能** の候補を出す。直す・整える提案は他が持っている — 構造は `/mattpocock-skills:improve-codebase-architecture`、見た目と操作感は `web-design-guidelines` と `baseline-ui`、不具合は `diagnosing-bugs`。ここでは、今はできないことをできるようにする提案だけを扱う。

提案の価値は根拠で決まる。根拠のない提案は「どのアプリにも言える提案」になる — 検索・通知・エクスポート・ダークモード。根拠は3つで、1つ目が欠けたら先へ進まない:

1. **目的のファイル** — 誰が、何のために使うか。何をしないか
2. **コードから読める「できること」と欠け** — 画面・API・データモデル
3. **利用ログ・本番ログ** — あれば

## 手順

### 1. 目的を読む

`docs/product.md` を読む。**誰が・何のために・何をしないか** の3節が揃っていれば次へ進む。

無いか欠けていれば、同じ中身を持つ資料(README の冒頭、`CONTEXT.md`、`docs/` の概要、ADR、ロードマップのイシュー)から下書きを起こし、[PRODUCT-TEMPLATE.md](PRODUCT-TEMPLATE.md) の形で `docs/product.md` に書く。ユーザーの確認は待たずに進む。

- 資料から起こした行には、出典を添えて `(下書き: README)` と付ける。ユーザーが認めたら印を外す
- ロードマップの「後回し」は「しない」ではない。`(下書き: 後回し #123)` と分けておく
- 何をしないかを資料から1行も引けなければ、その節は空のまま残す
- コミットはしない。書いたことを伝え、残すかはユーザーが決める

資料に無い目的を、コードから推して埋めない。コードから推した目的に対してコードの欠けを探すと、目的が欠けをそのまま映すので、提案が循環する。誰が・何のためにのどちらかを資料から1行も引けなければ、ここで止まってユーザーに聞く。

完了: `docs/product.md` に3節があり、誰が・何のためにが1行以上ある。どの行も、ユーザーが書いた行か出典付きの下書きである。

### 2. できることを棚卸しする

ユーザーが画面・機能・利用者を名指ししたら、そこから始める。無ければ全体を見る。

用語集(`GLOSSARY.md` か `CONTEXT.md`)と ADR を先に読む。そのあと、コードから次を一覧にする。広いアプリなら `Explore` サブエージェントに押し出し、一覧だけを受け取る。

「無い」は推さずに確かめる — 画面や API が無いと言うときは、その語で grep して出ないことを見てから書く。確かめられなかった欠けには `(grep 未確認)` と付ける。

- **画面** — ルートと、各画面で利用者ができる操作
- **API** — エンドポイントと、それを呼ぶ画面
- **データモデル** — テーブルと列、それを書く経路と読む経路
- **時間で動くもの** — cron・キュー・通知・メール

一覧の上で **欠け** を探す。欠けは次の形で現れる:

- **書くだけで読まれない** — 保存しているのに、どの画面にも出ない列。利用者が見たいはずの値に限る — `user_agent` や監査用の時刻は死に列であって欠けではない
- **片道の操作** — 作れるが直せない・取り消せない・まとめて扱えない
- **行き止まりの状態** — 状態の列にあるのに、そこへ移る・そこから出る操作が無い
- **手作業の跡** — `scripts/` の管理用スクリプト、`TODO`、手で DB を触る手順を書いた docs。利用者が誰かに頼んでいることの印である
- **言葉だけの概念** — 用語集にあるのに、画面にも API にも無い

`git log` と `CHANGELOG`、開いているイシューも読む。何度も手が入る画面は、利用者が実際に使っている画面である。イシューに要望として出ているだけの欠けは、そのイシューを根拠に足す。

完了: 画面・API・データモデル・時間で動くものの一覧と、欠けの一覧を持っている。各欠けにファイルの場所が付いている。

### 3. 利用ログを読む

ログを読める手段(Cloudflare API の MCP、`wrangler tail`、アプリ自身の集計テーブル)があれば、読み取りだけで当たる: よく叩かれる経路と叩かれない経路、利用者が踏むエラー、同じ操作の繰り返し。経路は ID を伏せたルートの形(`/events/:id`)でまとめて数える。サンプリングされたログなら件数ではなく経路どうしの比で読む。読めなければ、読まなかったと記録して次へ進む。

完了: ログから拾った数字があるか、読まなかったことが記録されている。

### 4. 候補を選り分ける

欠けを、目的の文と突き合わせて候補にする。1つの候補は **目的の1文** と **コードの場所1つ以上** を根拠に持つ。次に当たるものは落とす:

- **目的の文を引けない** — 誰の、何のための機能かを `docs/product.md` の文で言えない
- **決まったことに反する** — 目的のファイルが「しない」と書いたもの、ADR が退けたもの。ユーザーが ADR や docs を疑ってよいと言ったときだけ、これは落とす理由にならない。既定で覆さないのは決定が正しいからではなく、毎回の提案を前提の疑い直しにしないためである。古く見える決定は、候補にせず、落とした候補に「〜に反する」と書いて残す。その場合も、決めたときから何が変わったか(ログ・イシュー・コード)を根拠に引ける候補だけを残し、候補の「反する決定」に、どの決定に反するかを書く
- **名前を入れ替えても通る** — 候補の本文のアプリ名を、同じ種類の別のアプリに入れ替えても文が成り立つ。それはこのアプリの提案ではない。「コメントを編集できる」はコメントのあるどのアプリでも通る。「休んでいるメンバーを催促の母数から外せる」は、催促を任せると目的に書いたアプリでしか通らない
- **既に詰めてある** — 設計まで書かれたイシューがある。要望が出ているだけなら落とさず、根拠に数える
- **他の領分** — 冒頭に挙げた構造・見た目・不具合。コードが自分の意図(名前・コメント・テスト)と食い違っていれば不具合、意図どおりに動いて利用者を行き止まりに置くなら機能の欠けである

数を揃えない。根拠を持つ候補が1つなら1つ、0なら0と報告する。

各候補に強さを付ける: `Strong`(目的の文・コード・ログの3つが同じ方向を指す — ログが利用者の回避やつまずき、つまり同じ操作の繰り返し・エラー・行き止まりの経路を示している。隣の画面が見られている数だけでは指さない)、`Worth exploring`(目的の文とコード)、`Speculative`(目的の文はあるが、欠けの読みに自信が無い)。大きさも付ける: `S`(既存の画面に操作1つ)、`M`(画面か API を足す)、`L`(データモデルを変える)。

いちばんの推奨は、強さの高い順に選ぶ。強さが同じなら大きさの小さい方を推す — `L` はデータモデルを変えるので、外れたときに戻しにくい。

完了: 残った候補のどれもが、目的の文1つとコードの場所1つ以上を引用できる。

### 5. レポートで見せる

レポートはチャットの返答として Markdown で書く。ファイルは作らず、リポジトリにも何も置かない。

ユーザーが HTML で作ってと言ったときだけ HTML にし、Artifact として公開して URL を伝える。Artifact を公開できないハーネスでは、OS の一時ディレクトリ(`$TMPDIR`、無ければ `/tmp`)に `feature-proposals-<timestamp>.html` を書き、絶対パスを伝える。

中身の形は [REPORT.md](REPORT.md) にある。

まだ設計しない — 画面の配置も API の形も、選ばれたあとで詰める。書き終えたら、どれを詰めたいかを聞いて止まる。

完了: 手順4で残った候補と落とした候補がすべてレポートに載り、どれを詰めたいかを聞いている。

### 6. 選んだ1件を詰める

ユーザーが1件選んだら、`grilling` スキルを呼んで、決めることの木を一緒に下る: 誰がいつ使うか、今その人はどう回避しているか、最小の形はどれか、データモデルを変えずに済むか、何をしないか。その候補が `(下書き)` の行を根拠にしているなら、最初にその行をユーザーに確かめる。

用語が決まったら、`domain-modeling` スキルを呼んで用語集に足す。

候補が根拠のある理由で却下されたら、`docs/product.md` の「何をしないか」に理由と一緒に足すかを聞く。次の実行が同じ候補を出さないのは、そこに書かれたものだけである。「今は要らない」のような一時の理由なら足さない。

完了: 選んだ候補が、実装へ進むか却下されるかに決まっている。実装へ進むなら、ユーザーに `/mattpocock-skills:to-spec` を実行してもらう。
