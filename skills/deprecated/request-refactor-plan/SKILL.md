description: ユーザーへのインタビューを通じて小さなコミット単位のリファクタ計画を作成し、GitHub イシューとして登録する。ユーザーがリファクタを計画したいとき、リファクタリング RFC を作成したいとき、リファクタを安全な段階的ステップに分割したいときに使う。
---

このスキルは、ユーザーがリファクタリクエストを作成したいときに呼び出される。以下のステップを進める。必要ないと判断した場合はステップを飛ばしてよい。

1. ユーザーに、解決したい問題と考えうる解決策のアイデアについて、長く詳細な説明を求める。

2. リポジトリを探索し、ユーザーの主張を検証し、コードベースの現状を理解する。

3. 他の選択肢を検討したかを尋ね、他の選択肢を提示する。

4. 実装についてユーザーにインタビューする。極めて詳細かつ徹底的に行う。

5. 実装の正確なスコープを詰める。何を変更する計画で、何を変更しない計画かを明確にする。

6. コードベースを確認し、この領域のテストカバレッジをチェックする。テストカバレッジが不十分な場合、ユーザーにテストの計画を尋ねる。

7. 実装を小さなコミットの計画に分割する。Martin Fowler の助言「各リファクタリングステップをできるだけ小さくし、常にプログラムが動作している状態を確認できるようにする」を思い出すこと。

8. リファクタ計画を添えて GitHub イシューを作成する。イシューの説明には以下のテンプレートを使う:

<refactor-plan-template>

## Problem Statement

開発者が直面している問題を、開発者の視点で記述する。

## Solution

問題への解決策を、開発者の視点で記述する。

## Commits

長く詳細な実装計画。プレーンな英語で計画を書き、実装を可能な限り小さなコミットに分割する。各コミットはコードベースを動作する状態に保つこと。

## Decision Document

行われた実装上の決定の一覧。以下を含められる:

- 構築/変更されるモジュール
- 変更されるそれらのモジュールのインターフェース
- 開発者からの技術的な明確化
- アーキテクチャ上の決定
- スキーマの変更
- API 契約
- 具体的なやり取り

特定のファイルパスやコードスニペットは含め**ない**こと。すぐに古くなる可能性がある。

## Testing Decisions

行われたテストに関する決定の一覧。以下を含める:

- 良いテストとは何かの説明(外部の振る舞いのみをテストし、実装の詳細はテストしない)
- どのモジュールがテストされるか
- テストの先行事例(コードベース内の類似したテストなど)

## Out of Scope

このリファクタのスコープ外である事項の説明。

## Further Notes (optional)

リファクタに関するその他の補足事項。

</refactor-plan-template>
