# rule の型と、関心のカタログ

## ファイルの型

```markdown
---
description: <この rule が何を決めるか1行>
paths:
  - "<glob>"
---

# <関心>(<リポジトリ名> 固有)

一般作法は `/<skill>` を参照。ここには**このリポジトリ固有の事実だけ**を書く。

- <具体名(パス・関数名・コマンド)を持つ箇条書き>
- ⚠️ <黙って壊れる落とし穴>

## 対象外 / やってはいけない

- <この rule が適用されないパスと、その理由>
```

- **`description`** は1行。何を決めるファイルなのかが分かれば足りる
- **`paths`** は編集対象のパターン。設定ファイル(`vitest.config.ts` など)もその関心の一部なら含める
- **見出しに「固有」と書く** — 一般則を書き足したくなったときのブレーキになる
- 委譲先のスキルが無い関心では、冒頭の1行は落としてよい

## 関心のカタログ

**そのまま敷かない。** 探索で実在が確認できた関心だけを残す(SKILL.md 手順3)。

| 関心                     | 典型的な glob                                 | 何を持つか                                              | 委譲先                       |
| ------------------------ | --------------------------------------------- | ------------------------------------------------------- | ---------------------------- |
| コメント・宛先           | 実装コードとテスト全体                        | ADR・用語集の実体パス、コメントの手本、コミット/PR 運用 | `/where-to-write-what`       |
| テスト                   | `tests/**`、`**/*.test.*`、テストランナー設定 | 層の分け方、モックの方針、置き場                        | `/tdd` `/create-tests`       |
| エラー処理               | 実装コード全体                                | throw と Result の使い分け、エラーコード命名            | —                            |
| レイヤ境界               | 依存方向を持つディレクトリ全体                | 依存の向き、どの層から何を import してよいか            | `/codebase-design`           |
| 生成物の扱い             | 生成先のディレクトリ                          | 手編集禁止、再生成コマンド、カスタマイズの逃がし方      | —                            |
| フレームワーク固有の配置 | そのフレームワークのディレクトリ              | ルーティング方式、命名規則、認証の入り口                | そのスタックのスキル(あれば) |
| データアクセス           | DB・スキーマのディレクトリ                    | クエリの置き場、アクセス制御、DB 固有の制約             | —                            |
| デザインシステム         | スタイルとテンプレート                        | 実際のトークン、禁止事項                                | —                            |
| リリース                 | (`paths` を書けないことが多い)                | 採番、ブランチモデル、公開手順                          | —                            |

最後の行が示すとおり、**カタログに載っていても `paths` を書けない関心はある。** リリース手順のように「そのファイルを編集するとき」ではなく「その作業をするとき」効くものは、rule ではなくスキル(`/<name>` で明示呼び出し)が宛先である。判定は SKILL.md 手順2の自己更新ルールと同じ順序で下す。

## glob の書き方

- **実在するパスから書く。** 探索で見たディレクトリをそのまま使う。将来できるかもしれないパスを先回りで足さない
- **広すぎる glob は注入を無意味にする。** `**/*.ts` は「毎セッション」とほぼ同義である。そう書きたくなったら、それは毎セッション読まれる側(SKILL.md 手順2)の内容である
- **狭すぎると効かない。** その関心に触る作業が実際に開くファイル(実装だけでなく設定・テスト)が含まれているかを確認する
