# Codebase Design

**深いモジュール** を設計する: 小さなインターフェースの裏に多くの振る舞いを隠し、きれいなシームに置き、そのインターフェースを通してテスト可能にする。コードが設計または再構成されるところではどこでも、この言葉とこれらの原則を使う。狙いは、呼び出し元にとってのレバレッジ、保守者にとっての局所性、そして誰にとってもテスト可能であることである。

## 用語集

これらの用語を正確に使う — 「コンポーネント」「サービス」「API」「境界」に置き換えない。一貫した言葉こそが、この用語集の存在意義である。

**Module(モジュール)** — インターフェースと実装を持つもの全般。意図的にスケールを問わない: 関数、クラス、パッケージ、あるいは複数の層にまたがるスライス。_避ける表現_: unit、component、service。

**Interface(インターフェース)** — 呼び出し元がそのモジュールを正しく使うために知らなければならないすべて: 型のシグネチャだけでなく、不変条件、順序の制約、エラーモード、必要な設定、パフォーマンス特性も含む。_避ける表現_: API、signature(狭すぎる — それらは型レベルの表面しか指さない)。

**Implementation(実装)** — モジュールの中身、そのコードの本体。**Adapter** とは区別される: あるものは、小さなアダプターに大きな実装を持つ(Postgres のリポジトリ)ことも、大きなアダプターに小さな実装を持つ(インメモリのフェイク)こともある。話題がシームであれば「adapter」を、そうでなければ「implementation」を使う。

**Depth(深さ)** — インターフェースにおけるレバレッジ: 呼び出し元(あるいはテスト)が、学ばなければならないインターフェースの単位あたりに引き出せる振る舞いの量。モジュールは、小さなインターフェースの裏に大量の振る舞いがあるとき **深い**、インターフェースが実装とほぼ同じくらい複雑なとき **浅い**。

**Seam(シーム)** _(Michael Feathers)_ — その場所を編集せずに振る舞いを変えられる場所。モジュールのインターフェースが存在する _位置_ のこと。シームをどこに置くかは、その裏に何を置くかとは別の、それ自体の設計上の決定である。_避ける表現_: boundary(DDD の bounded context と意味が重複する)。

**Adapter(アダプター)** — シームにおいてインターフェースを満たす具体的なもの。中身(何が入っているか)ではなく _役割_(どの枠を埋めるか)を表す。

**Leverage(レバレッジ)** — 呼び出し元が深さから得るもの: 学ぶインターフェースの単位あたりの、より多くの能力。1つの実装が、N か所の呼び出し箇所と M 個のテストにわたって元を取る。

**Locality(局所性)** — 保守者が深さから得るもの: 変更、バグ、知識、検証が、呼び出し元全体に散らばるのではなく、1か所に集約される。一度直せば、どこでも直る。

## 深い vs 浅い

**深いモジュール** = 小さなインターフェース + 多くの実装:

```
┌─────────────────────┐
│   Small Interface   │  ← Few methods, simple params
├─────────────────────┤
│                     │
│  Deep Implementation│  ← Complex logic hidden
│                     │
└─────────────────────┘
```

**浅いモジュール** = 大きなインターフェース + 少ない実装(避けるべき):

```
┌─────────────────────────────────┐
│       Large Interface           │  ← Many methods, complex params
├─────────────────────────────────┤
│  Thin Implementation            │  ← Just passes through
└─────────────────────────────────┘
```

インターフェースを設計するときは、次を問う:

- メソッドの数を減らせないか?
- パラメータを単純化できないか?
- もっと多くの複雑さを内側に隠せないか?

## 原則

- **深さはインターフェースの性質であり、実装の性質ではない。** 深いモジュールは、内部的には小さく、モックしやすく、差し替え可能な部品で構成されていてもよい — それらは単にインターフェースの一部ではないというだけである。モジュールは、インターフェースにある **外部シーム** に加えて、**内部シーム**(その実装にプライベートで、自分自身のテストが使うもの)を持つこともある。
- **削除テスト。** そのモジュールを削除したと想像する。複雑さが消え去るなら、それは素通しだった。複雑さが N 個の呼び出し元にわたって再び現れるなら、それは存在意義があった。
- **インターフェースはテストの表面である。** 呼び出し元とテストは同じシームを越える。インターフェースの _先を_ テストしたいなら、そのモジュールはおそらく形が間違っている。
- **アダプターが1つなら、それは仮のシームである。アダプターが2つなら、本物のシームである。** 実際に何かがそこをまたいで変化するのでない限り、シームを導入しない。

## テスト可能性のための設計

良いインターフェースはテストを自然にする:

1. **依存を受け入れる。自分で作らない。**

   ```typescript
   // Testable
   function processOrder(order, paymentGateway) {}

   // Hard to test
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **結果を返す。副作用を起こさない。**

   ```typescript
   // Testable
   function calculateDiscount(cart): Discount {}

   // Hard to test
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小さな表面積。** メソッドが少なければ、必要なテストも少ない。パラメータが少なければ、テストのセットアップも単純になる。

## 関係性

- **Module** はちょうど1つの **Interface**(呼び出し元とテストに対して見せる表面)を持つ。
- **Depth** は **Module** の性質であり、その **Interface** に対して測られる。
- **Seam** は **Module** の **Interface** が存在する場所である。
- **Adapter** は **Seam** に位置し、**Interface** を満たす。
- **Depth** は呼び出し元に **Leverage** を、保守者に **Locality** を生む。

## 却下した捉え方

- **深さを実装行数とインターフェース行数の比とする**(Ousterhout): 実装を水増しすることに報いてしまう。代わりに、レバレッジとしての深さを使う。
- **「interface」を TypeScript の `interface` キーワードやクラスの公開メソッドとする**: 狭すぎる — ここでの interface は、呼び出し元が知らなければならないすべての事実を含む。
- **「boundary」**: DDD の bounded context と意味が重複する。**seam** か **interface** と言う。
