# 実装してレビューする

ユーザーがスペックやチケットで記述した作業を、本家の `/mattpocock-skills:implement` でビルドしてもらい、その後を締める。引数でチケットやスペックの参照が渡された場合は、それが実装対象である。

複数のチケットを渡されたときは、手順のリストではなく **タスクグラフ** として読む — 着手できるのはブロッカーが片付いたものだけで、その集合は1つ終えるたびに変わる。

## 着手する前に、既定ブランチに追いつく

`git fetch` で既定ブランチの最新を取る。

- **既定ブランチに居るなら、先にブランチを切る** — 作業から付けた短い名前で。既定ブランチへの直 push を禁じているリポジトリがあり、最後の PR もこのブランチから出す。未コミットの変更はそのまま新しいブランチへ付いてくる。
- **依頼と無関係な未コミットの変更は、自分の変更に混ぜない。** 書き手が違うものが1つの PR に入ると、レビューする人は依頼した変更がどこまでかを差分から見分けられない。先にその中身(ファイル一覧と差分の要点)をユーザーに示して確認を取り、それから、それだけで別ブランチと draft PR を1本作り、配線が済んでいない箇所を本文に名指しする — 他人の書きかけは秘密情報や未完成の断片を含みうるので、確認なしに push しない。中身は書き手のものなので、こちらで完成させない。そのうえで自分の作業を別のブランチで始める。
- **未コミットの変更があれば退避する。** `git stash push -u -m <固有のタグ>` で積み、直後に `git stash list --format='%H %gs'` で自分のエントリの SHA を控える。取り込んだら `git stash apply <SHA>` で戻し、タグで探し直して drop する。素の `git stash pop` は使わない — stash の山は他の worktree やセッションと共有されていて、他人の変更を取り出しうる。
- **`gh stack view --json` が今のブランチを含むスタックを返すなら、`gh stack sync` に任せる** — 手で取り込むと上の層がずれる。衝突すると全ブランチを元に戻して exit 3 で終わるので、`gh stack rebase` で衝突を出して解き、`gh stack rebase --continue` で進める。
- それ以外は `git merge origin/<既定ブランチ>` で取り込む。rebase はしない — push 済みのブランチの履歴を書き換えると force push が要り、衝突もコミットの数だけ解き直すことになる。

衝突は `resolving-merge-conflicts` スキルで解く。ただし双方の意図が両立しないハンクでは、どちらかを選ばない — ここは追いつくための取り込みで、片方を捨てる根拠になる目標が無い。そのハンクをユーザーに示して止まる。

作業ブランチが既定ブランチの最新を含み、退避した変更が戻っていたら、ビルドをユーザーに渡す。

## ビルドはユーザーに `/mattpocock-skills:implement` を打ってもらう

ビルドは本家の `/mattpocock-skills:implement` が持つ。ユーザーからしか呼べないスキルなので、ここからは呼ばず、打つ行を組み立てて示し、**止まる**:

```
/mattpocock-skills:implement <実装対象のチケット/スペックの参照> — /mattpocock-skills:code-review とコミットはせず、ビルドが済んだら止まる。その先は /implement-and-review の手順で進める。
```

本家の `/mattpocock-skills:implement` は最後に `/mattpocock-skills:code-review` とコミットまで済ませる。そのまま流すと、コメントを削る前にコミットされ、この後の二軸レビューと二重になる。引数は本家の本文の後ろに付くので、この1行で最後の2手を止める。

複数のチケットなら、ブロッカーの片付いたものを1本ずつこの行にして示し、1本ごとに下の「締める」から PR までを通してから次の行を示す。

ユーザーの `/mattpocock-skills:implement` でビルドが済んだら、ユーザーを待たずに次へ進む。

## 締める

ビルドが済んだら `verification-loop` スキルを呼び、クリーンランを取る。

クリーンランが取れたら `prune-comments` スキルを呼び、書いてしまったコメントを削る。**レビューより先に置く** — 先に削っておくと `two-axis-review` の目が、消し忘れではなく書かれなかった Why not のほうへ向く。コメント行が1行も増えていなければ、そのスキルが自分で降りる。

続けて `two-axis-review` スキルを呼び、作業をレビューする。スペックには実装したチケットを渡す — まだコミットが無いので、渡さないとコミットメッセージから探せずユーザーに尋ねに行く。

指摘のうち、直し方が自明なものは直し、`verification-loop` でクリーンランを取り直す — 直した編集は前のクリーンランに含まれていない。要件に無いもの(スペックが求めていない振る舞いや、_任意_ の改善)は直さず、PR 本文と最後の報告に載せる。

## コミットして PR を出す

コミットメッセージと PR 本文を書く前に `where-to-write-what` スキルを呼び、何をコミットと PR 本文に載せ、何をコメントや ADR へ回すかを決める。チケットが issue なら、PR 本文に `Closes #<番号>` を入れてマージで閉じる。

作業ブランチにコミットし、push して PR を出す。

- **スタックの中なら `gh stack submit --auto` で出す** — `gh pr create` ではベースが下の層にならない。今の層が別のチケットのものなら、コミットの前に `gh stack add <名前>` で層を積む。`--auto` はコミットの本文をそのまま PR 本文にするので、出たら `gh pr edit <番号> --body` で PR 本文の基準に差し替える。
- それ以外は `git push -u origin <ブランチ>` のあと `gh pr create`。

ユーザーが「PR は作らないで」「push しないで」と言っていれば、コミットで止まる。

PR の URL をユーザーに示したら完了である。
