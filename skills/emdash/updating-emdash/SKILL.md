# EmDash を上げる

`create emdash` が落としてくる公式テンプレート([`emdash-cms/templates`](https://github.com/emdash-cms/templates)。既定は Cloudflare 向けのブログ `blog-cloudflare`)は EmDash のリリースごとに同期されるが、同期されるのは **依存の版** であって、コードが新しい API に乗り換わるとは限らない。`create emdash` で作った直後のサイトは、`package.json` は最新なのに、コードは数版前の書き方のまま、という状態で始まる(例: 0.38 同期時点のブログテンプレートは、0.37 で入った `avatarStorageKey` をまだ使っていない)。

だからこのスキルは2つの差を埋める: **依存の版の差** と、**テンプレート由来のコードの差**。後者を判定する項目は [CHECKLIST.md](CHECKLIST.md) にある。

## 手順

**区切りごとにコミットを1つ作る。** 依存の更新・やることリストの各項目・生成型が1つに混ざると、型チェックやビルドが赤くなったときに、上げた依存と直したコードのどちらが原因か切り分けられない。PR のレビューでも、項目ごとのコミットがそのまま「版つきの変更点」として読める。コミットメッセージはリポジトリの慣習に合わせ、本文に対応した版を書く。

### 1. 範囲を決める

- **今の版:** `pnpm why emdash` の解決済みの版(`package.json` の範囲指定ではなく)。
- **目標の版:** `npm view emdash version`。
- **やることリストを当てる範囲:**
  - **セットアップ直後なら、全項目。** テンプレートのコードは依存の版より古いので、「今の版」は何も保証しない。`blog-cloudflare` から作ったなら、CHECKLIST.md 冒頭の表から手を付ける。
  - それ以外は、`今の版 < 項目の版 ≤ 目標の版`。ただし前回の更新で飛ばした項目が残っていることがあるので、範囲外の項目も **判定** だけは流す(grep 1 本ずつで済む)。

### 2. 変更履歴を読む

範囲内の版ごとに読む。`emdash` と `@emdash-cms/admin`・`@emdash-cms/cloudflare` は同じ版で出るが、履歴は別々に書かれている:

```bash
gh release view emdash@<版> -R emdash-cms/emdash --json body -q .body
gh release view @emdash-cms/cloudflare@<版> -R emdash-cms/emdash --json body -q .body
```

読みながら、CHECKLIST.md に **無い** 変更のうち、サイトのコードか本番の設定に効くものを控える(手順 5 で使う)。管理画面だけで完結する機能追加は控えない。

### 3. 依存を上げる

- `pnpm up --latest` で一通り上げる。EmDash 以外が上がって壊れたら、その依存だけ据え置く判断をしてよい(据え置いた理由は PR 本文へ)。
- `emdash`・`@emdash-cms/admin`・`@emdash-cms/cloudflare` を **同じ版** に揃える。`plugins/*` のようなワークスペース内のパッケージが peer に EmDash を持っていれば、それも揃える — 揃えないと古い `emdash` が依存ツリーに二重に残る(`pnpm why emdash` が2行出る)。
- `pnpm-workspace.yaml` の `patchedDependencies` にキーがあれば、`patching-emdash` スキルを呼び、その「EmDash を上げるとき」に従う。版付きキーは新しい版に当たらないので、**install の前に** やる。
- `pnpm-workspace.yaml` の `overrides` と `peerDependencyRules` の各項目について、理由のコメントがまだ成り立つかを確かめる。成り立たないものは消し、成り立つものはコメントの版表記を直す。

**完了基準:** `pnpm install` が通り、`pnpm why emdash` が目標の版1つだけを出す。ここでコミットする(`package.json`・`pnpm-lock.yaml`・`pnpm-workspace.yaml`・パッチ)。EmDash 以外の依存の更新で型チェックかビルドが赤くなるなら、`pnpm up --latest` の分と EmDash の分を別のコミットに分ける。

### 4. やることリストを1項目ずつ判定する

[CHECKLIST.md](CHECKLIST.md) を読み、手順 1 の範囲の項目を上から順に:

1. **判定** を流す。当たらなければ次へ。
2. 当たったら **対応** を行う。サイトが独自に書き換えた箇所は、テンプレートの書き方ではなくサイトの書き方に合わせる。
3. **本番** があれば、PR 本文の「マージ後にやること」へ控える。
4. 対応したら、その項目だけでコミットする。1行で済む項目どうし(import の付け替えなど)はまとめてよいが、版をまたいでまとめない。

**完了基準:** 範囲内のすべての項目について、「当たらなかった / 対応した / 対応しないと決めた(理由)」を1行ずつ言える。

### 5. リストに無い変更を足す

手順 2 で控えた変更に対応し、**同じ変更を CHECKLIST.md に項目として足す**。次にこのスキルを使う人(次のサイトのセットアップ直後を含む)は、履歴を読み直さずに済む。

- 項目は判定・対応・本番の3つで書く。**判定** は、どのサイトでも機械的に流せる grep かコマンドにする — 「〜していれば」のような読み手の判断に頼る判定は、セットアップ直後の全項目走査で読み飛ばされる。
- サイト名は書かない。どのサイトで当てたかはサイトのコミットログが持つ。
- 足した項目が `blog-cloudflare` にも当たるかを判定し、冒頭の表を更新する(`git clone --depth 1 https://github.com/emdash-cms/templates` をスクラッチに置いて流す)。
- CHECKLIST.md は kjfsm/skills にあるので、サイトとは別の PR になる。

### 6. 検証する

1. リポジトリの検証ゲート(型チェック・lint・テスト・`pnpm build`)。
2. `pnpm dev` を起動し、生成型 `emdash-env.d.ts` が作り直されたら、それだけでコミットする。
3. 対応した項目が画面に出るもの(アバター、テーマ、表、コメント欄)は、dev サーバーでそのページを開いて確かめる。確かめられなかったものは PR 本文に「未確認」と書く。

### 7. PR を出す

本文は **変更 / 確認 / マージ後にやること(本番)** の3節で書く。

- 途中のコミットが単体で型チェックを通らないなら(次のコミットで直している場合)、そのことを本文に書く。
- **変更:** 上げた版と、対応した項目を版つきで1行ずつ(`**アバター**: … (0.37)`)。影響がなかった破壊的変更も、なぜ影響がないかと並べて書く。
- **マージ後にやること:** 手順 4 で控えた本番作業。DB マイグレーションが含まれる版なら、その番号と、ランタイムが当てるのかデプロイ手順が当てるのかを書く。

**完了基準:** 本番作業が PR 本文に揃っていて、CHECKLIST.md に足した項目があればその PR も出ている。
