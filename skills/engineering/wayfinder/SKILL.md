# Wayfinder

漠然としたアイデアが持ち込まれた — 1つのエージェントセッションには大きすぎ、霧に包まれている: ここから **目的地** までの道はまだ見えていない。ウェイファインディングとは、その道を見つけることであり、目的地に突進することではない。このスキルは、リポジトリのイシュートラッカー上に **共有マップ** としてその道を描き、その **意思決定チケット** — 実行すべきビルドのスライスではなく、解決すべきものが意思決定であるような問い — を、道筋が明らかになるまで1つずつ処理していく。

目的地は取り組みごとに異なり、それに名前を付けることが地図を描く最初の行為である — それがすべてのチケットの形を決める。それは、引き継いで反復していくスペックかもしれないし、計画が始まる前に固めておくべき決定かもしれないし、データ構造のマイグレーションのようにその場でなされる変更かもしれない。このマップはドメインを問わない — エンジニアリングの作業でも、講座のコンテンツでも、その形に合うものなら何でもよい。

## 計画する、実行しない

wayfinder はデフォルトで **計画** である: 各チケットは1つの意思決定を解決し、誰かが実際にそれをやりに行く前に決めるべきことが何も残っていない状態になったとき、マップは完了する。ただ作業をやってしまいたいという衝動は、たいていマップの端に到達し、そろそろ引き継ぐべきだというシグナルである。ある取り組みはその **Notes** の中でこれを上書きし、実行そのものをマップに持ち込むこともできるが、それがなければ、成果物ではなく意思決定を生み出す。

## 名前で参照する

すべてのマップとチケットはイシューなので、**名前**(そのタイトル)を持つ。人間が読むあらゆるもの — ナレーション、マップの「これまでの決定」 — の中では、裸の id、番号、スラッグではなく、常にその名前で参照する。`#42, #43, #44` の壁は読み取れない。名前は一目で読める。id と URL は消えるわけではない — 名前がそのリンクを包み込む — が、それらは名前の _内側_ に乗るのであり、決して名前の代わりにはならない。

## マップ

マップとは、このリポジトリのイシュートラッカー上の単一のイシューであり、`wayfinder:map` というラベルが付く — これが正典となる成果物である。そのチケットはマップの子イシューである。

マップは **索引** であり、保管庫ではない。下された決定を列挙し、その詳細を保持するチケットを指し示す。決定はちょうど1か所 — そのチケット — にだけ存在するので、マップはそれを繰り返し書かず、要点とリンクだけを載せる。

**マップ、その子チケット、ブロッキング、フロンティアの問い合わせが物理的にどこにあるかは、トラッカーによって異なる。** イシュートラッカーはあなたにすでに渡されているはずである — なければ `/setup-skills` を実行すること。それらを _この_ リポジトリがどう表現するかは、トラッカーのドキュメントの「Wayfinding operations」節を参照する。トラッカーが渡されていない場合は、ローカルの markdown トラッカーをデフォルトとする。

### マップとチケットの形

マップの本文テンプレート、チケットの本文テンプレート、`wayfinder:<type>` ラベル4種の使い分けは [`MAP-FORMAT.md`](MAP-FORMAT.md) にある。**マップやチケットを書く・作るときに開く。**

マップは低い解像度で、セッションごとに一度だけ読み込む。

各チケットはマップの **子イシュー** であり、トラッカーのイシュー id がその識別子である。セッションは、他の並行セッションがそれをスキップできるよう、作業を始める **前に**、マップを進めている開発者にそれを割り当てることでチケットを **引き受ける**。その担当者こそが引き受けの証である: 開いていて誰にも割り当てられていないチケットは、引き受けられていない。

ブロッキングにはトラッカーの **ネイティブな** 依存関係を使う — これは不可欠である。トラッカー自身の UI 上でフロンティアを _視覚的に_ 表示できるので、人間はマップを開かなくても何が着手可能か分かる。ネイティブなブロッキングを持たないトラッカーだけが、本文による慣習にフォールバックする。あるチケットをブロックしているチケットがすべてクローズされたとき、そのチケットは **ブロック解除** される。**フロンティア** とは、開いていて、ブロックされておらず、まだ誰にも引き受けられていない子チケットのことである — 既知の領域の端である。

## 戦場の霧

このマップは _意図的に_ 不完全である: まだ見えていないものは描かない。生きているチケットの向こうには **戦場の霧** が広がっている — やってくるとは分かっていても、まだ開いたままの問いに懸かっているためにまだ突き止められない、決定や調査のぼんやりとした眺めである。あるチケットを解決すると、その先の霧が晴れ、今や仕様化できるようになったものが新しいチケットへと格上げされる — 目的地までの道が明らかになり、チケットが1つも残らなくなるまで、1つずつ。

マップの **未確定** セクションは、そのぼんやりとした眺めが書き留められる場所である: 疑わしい問い、後で立ち返るべき領域。これは目的地に _向かう_ 未発見のフロンティアである — ここにあるものはすべてスコープ内だが、まだチケットにできるほど鋭くはない。その眺めが許す限り緩く、あるいは詳しく書く。これは、この取り組みがどこへ向かっているかを読む共同作業者にとっての道標も兼ねる。

**霧かチケットか?** 判定基準は、今その問いを正確に述べられるかどうかである — 今それに答えられるかどうか _ではない_。

- **問いがすでに鋭ければチケットにする** — たとえそれがブロックされていて今すぐには着手できなくても。
- **その鋭さでまだ言い表せないなら未確定にする。** 霧をあらかじめチケットサイズに切り分けない: それはチケットより粗いものであり、フロンティアがそこに到達したとき、1つの断片が複数のチケットに格上げされることもあれば、まったく格上げされないこともある。

**未確定** には、すでに決定済みのもの(これまでの決定)、すでに生きているチケットになっているもの、スコープ外のもの(次のセクション)は含まれない。

## スコープ外

霧は常に目的地に _向かって_ しか集まらない。目的地がスコープを定めるので、それを越えた作業は **スコープ外** である — それは霧ではなく、**未確定** には属さない。マップ上にはそれ専用の **スコープ外** セクションがあり、_この_ 取り組みから意識的に除外した作業を記す。ここに載るのは鋭さの問題ではなく、スコープの問題である。

スコープ外の作業は決して格上げされない — フロンティアは目的地で止まる — ので、それが戻ってくるのは目的地が描き直されたときだけであり、そのときは再開ではなく新しい取り組みとして戻ってくる。

何かをスコープ外と判定することは、道筋の1歩ではなく、スコープを定める行為である。すでに存在するチケットが、実は目的地の先にあると分かったとき — 地図を描いている最中にスコープを誤ったか、ある解決によって露わになったかして — そのチケットを **クローズ** し(クローズされたチケットは、疑いようもなくフロンティアの外にある)、**スコープ外** セクションに1行残す: 要点と、なぜそれがスコープ外なのか、そのクローズされたチケットへのリンクとともに。それは、実際に歩まれた道筋を記録する **これまでの決定** には含めない — スコープの境界線は、その道筋の1歩ではない。

## 呼び出し

2つのモードがある。どちらの場合も、**1セッションにつき1つを超えるチケットを解決しない** — research チケットを例外として。

### マップを描く

ユーザーが漠然としたアイデアとともに呼び出す。

1. **目的地に名前を付ける。** `grilling` と `domain-modeling` の2つのスキルを呼び、このマップが何への道を見つけようとしているのか — スペック、決定、変更 — を突き止める。目的地がスコープを定めるので、最初にこれを固める。
2. **フロンティアを地図に描く。** もう一度グリリングするが、今度は **幅優先** で行う: どれか1つのスレッドを深く掘るのではなく、空間全体に扇状に広がり、開いている決定と、今すぐ着手可能な最初の一歩を表面化させる。**もしこれで霧が何も現れなければ** — 目的地までの道はすでに明らかで、旅全体が1セッションに収まるほど小さいということなので、マップは不要である。立ち止まり、どう進めたいかユーザーに尋ねる。
3. **マップを作成する**(`wayfinder:map` のラベル): Destination と Notes を埋め、Decisions-so-far は空のまま、霧を **Not yet specified** に描き出す。
4. **今specifyできるチケットを作成する** — マップの子イシューとして。その後、**第二パス** でブロッキングエッジを配線する(イシューは互いを参照する前に id を持つ必要がある)。配線によって、それらはフロンティアとブロック済みに仕分けられる。まだ specify できないものはすべて霧 — **Not yet specified** セクション — に留まる。
5. **research チケットを解決させる。** たった今作成した `research` チケットそれぞれについて調査を走らせ、その発見を使い捨ての `research/<name>` ブランチに、チケットからのコンテキストポインタとともに記録する。何体も並べる場面なので、`/delegation` に従って各報告の長さを縛る。

   **1件なら `research` スキルを呼ぶ。複数あるならサブエージェントを並列に起動する** — `research` はフォークされたスキルであり、前の呼び出しが走っているあいだに同じスキルをもう一度呼ぶとハーネスが待つので、N 回呼ぶと直列化する。並列に走らせるときは、`research` が課している規律(一次情報源にたどる、主張ごとに出典を引用する、報告の長さの上限)を各プロンプトに畳み込む。

6. 止まる — 地図を描くことは1セッション分の作業であり、それ自体は何も解決しない。

### マップを進める

ユーザーがマップ(URL または番号)とともに呼び出す。チケットは **省略可能** である — 指定がなければ、次の決定を選ぶのはユーザーではなくあなたである。

1. **マップ** を読み込む — 低解像度のビューであり、すべてのチケットの本文ではない。
2. チケットを選ぶ。ユーザーが指定していればそれを使う。そうでなければ、順序上最初のフロンティアチケットを取る。**それを引き受ける**: 作業を始める前に自分自身に割り当てる。
3. それを解決する — **必要に応じてズームする**: 関連する、あるいはクローズされたチケットの本文は必要なときに取得する。`## Notes` ブロックが名指ししているスキルを呼ぶ。迷ったら `grilling` と `domain-modeling` の2つを呼ぶ。
4. 解決を記録する: 答えを **解決コメント** として投稿し、そのイシューを **クローズ** し、マップの Decisions-so-far に **コンテキストポインタを追記** する。
5. 新しく表面化したチケットを追加する(まず作成し、それから配線する)。その答えによって specify できるようになった霧があれば格上げし、格上げされた断片を **Not yet specified** から消して、それが新しいチケットとしてのみ存在するようにする。もしその答えによって、あるチケット — このチケットか、別のチケットか — が目的地の先にあると判明したら、道筋の上で解決するのではなく **それをスコープ外と判定する**。もしその決定がマップの他の部分を無効にするなら、それらのチケットを更新または削除する。

ユーザーはブロックされていないチケットを並行して進めるかもしれないので、他のセッションが同時にトラッカーを編集していることを想定しておく。
