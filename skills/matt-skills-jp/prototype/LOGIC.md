# Logic Prototype

誰でもボタンを押してステートモデルを動かせる、自己完結した単一の HTML ファイル(**共有できるデモ**)。問いが **ビジネスロジック、状態遷移、データの形** に関するものであるとき — 紙の上では妥当に見えるが、実際のケースを通してみて初めておかしいと感じられるようなものに使う。

インストールするものが何も無い1ファイルなので、開発者でない人(デザイナー、PM、ドメインの専門家)にそのまま渡して、モデルを自分の手で感じてもらえる。だからこのデモが話すのはコードの言葉ではなく、その人たちの言葉である。

## この形が適している場合

- 「この状態機械が X の後に Y というエッジケースを処理できるか自信がない。」
- 「このデータモデルは、実際に…というケースを表現できるのか?」
- 「書く前に、この API がどんな見た目になるべきか感触をつかみたい。」
- ユーザーが **ボタンを押して状態が変わるのを見たい** ものすべて。

問いが「これはどう見えるべきか」であれば — 分岐を間違えている。[UI.md](UI.md) を使う。

## 手順

### 1. 問いを述べる

コードを書く前に、どのステートモデルとどの問いをプロトタイピングしているのかを書き留める。1段落で、デモの先頭に — コメントではなく、**目に見える導入として**。間違った問いに答えるロジックプロトタイプは純粋な無駄である。ユーザーが今見ていても、後で離席先から戻ってきても確認できるよう、問いを明示する。

### 2. ロジックを持ち運び可能なモジュールに隔離する

実際のロジック — 問いに答えている部分 — を、単一の `<script>` ブロックの中に、後で持ち上げて本物のコードベースに落とし込める小さく純粋なモジュールとして書く。それを囲むページは使い捨てだが、このモジュールはそうではない。

正しい形は問いによって決まる:

- **純粋な reducer** — `(state, action) => state`。アクションが離散的なイベントで、状態が単一の値であるときに向く。
- **ステートマシン** — 明示的な状態と遷移。「今どのアクションがそもそも許可されているか」が問いの一部であるときに向く。
- プレーンなデータ型に対する **少数の純粋関数の集合**。暗黙の現在状態がなく、単なる変換だけであるときに向く。
- ロジックが本当に継続的な内部状態を持つ場合の、明確なメソッド表面を持つ **クラスやモジュール**。

ページに配線しやすいかではなく、問われている問いに最も合う形を選ぶ。純粋に保つ: DOM なし、`document` なし、モジュールの内側に手を伸ばすボタンのハンドラなし。ページがそれを呼び出す。逆方向には何も流れない。これが、プロトタイプをその寿命を超えて役立たせる理由である: 問いに答えが出たら、検証済みの reducer/マシン/関数群だけが単独で本物のモジュールへ持ち上がる。

### 3. 共有できる HTML ファイルを作る

1ファイル、素の HTML/CSS/JS。フレームワークなし、バンドラなし、サーバーなし、すべてインラインで — ダブルクリックで開き、メールで回されても生き延びるように。誰でも、開くだけで実行できなければならない。

開発者でない人に向けて書く。ラベルはすべて、コードではなく **ドメインの言葉** で: ボタンと状態が reducer ではなくビジネスのように読める。何が起きているかを平易な言葉で説明する。

上から下へ、きれいな階層で並べる:

1. **タイトルと、このデモで何を探れるのかの1行の説明**(手順1の問い)。
2. **現在の状態** — 関連する状態の全体を、読める形のパネルとして描画する(生の JSON ダンプではなく、ラベル付きのフィールド)。クリックのたびに再描画し、変化が見えるようにする。開発者でない人が追うのに役立つなら、いま何が変わったのかを名指しする。
3. **自由に押せるボタン** — アクションごとに1つ、常に押せる状態で並べ、誰でも好きな順にモデルをつつけるようにする。クリックするたびにそのアクションをディスパッチし、状態を再描画する。
4. **ガイド付きのウォークスルー** — **シナリオ** をタブ1つにつき1本。各タブは、そのシナリオの短い平易な説明(どんな状況を作り、何に注目すべきか)と、その下に押すべき **ボタンの並び** を持つ。各ステップは本物のボタンで、クリックするとそのアクションを実行して次のステップへ進む。ウォークスルーを開始すると既知の初期状態にリセットされ、シナリオは毎回同じように走る。

シナリオには、紙の上では考えにくい厄介なケースを選ぶ: ハッピーパス、扱いにくいエッジケース、本来なら不正であるべき操作の試み。

美しく、しかし抑制的に保つ: きれいなタイポグラフィ、たっぷりの余白、アクセントカラーは1色。アニメーションなし、小細工なし — 状態とボタンと張り合うものを置かない。

### 4. 引き渡す

ファイルを送るか、開いてあげる。相手は都合のよいときにウォークスルーを押し進め、自由に触る。興味深い瞬間は、相手が「待って、それはあり得ないはずだ」や「え、X は違うと思っていた」と言うときである — それらは _アイデア_ の中のバグであり、それこそが本来の狙いである。新しいアクションや新しいシナリオを追加してほしいと言われたら、追加する。プロトタイプは進化する。

### 5. 答えとプロトタイプを記録する

プロトタイプが問いに答えたら、答えを記録し、それから [SKILL](SKILL.md) が説明する方法でプロトタイプ自体を記録する。ロジック固有の対応付け: 検証済みの reducer/マシン/関数群は本物のモジュールに持ち上がる(決定が吸収される)。HTML の外殻は、プロトタイプを一次情報源として保持する使い捨てブランチに一緒に乗っていき、自己完結した1ファイルなので、そこでも簡単に再実行できるまま残る。

## アンチパターン

- **テストを追加しない。** テストが必要になったプロトタイプは、もはやプロトタイプではない。
- **本物のデータベースに配線しない。** 問いが特に永続化についてのものでない限り、インメモリの状態を使う。
- **一般化しない。** 「後で X をサポートしたくなったら」はなし。プロトタイプは1つの問いに答える。
- **ロジックとページを混ぜ合わせない。** 純粋なモジュールが DOM、`document`、ボタンのハンドラを参照しているなら、それはもう持ち上げられない。ページは純粋なモジュールの上の薄い殻に保つ。
- **フレームワーク・バンドラ・サーバーに手を伸ばさない。** 受け取った人がダブルクリックする1ファイルであること。React アプリや dev サーバーは「共有できる」を台無しにする。
- **HTML の外殻を本番に出荷しない。** そのページは、手でクリックされることに最適化されている。その裏にあるロジックのモジュールこそが、残す価値のある部分である。
