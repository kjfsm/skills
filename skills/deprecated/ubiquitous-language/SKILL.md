# ユビキタス言語

現在の会話からドメイン用語を抽出し、一貫したグロッサリーとして形式化し、ローカルファイルに保存する。

## プロセス

1. **会話をスキャンする**: ドメインに関連する名詞、動詞、概念を探す
2. **問題を特定する**:
   - 同じ単語が異なる概念に使われている(曖昧さ)
   - 同じ概念に異なる単語が使われている(同義語)
   - 曖昧または多義的な用語
3. **標準的なグロッサリーを提案する**: 意見を持った用語選択を行う
4. **`UBIQUITOUS_LANGUAGE.md` に書き込む**: 作業ディレクトリに、以下のフォーマットで
5. **要約を出力する**: 会話内にインラインで

## 出力フォーマット

以下の構造で `UBIQUITOUS_LANGUAGE.md` ファイルを書く:

```md
# Ubiquitous Language

## Order lifecycle

| Term        | Definition                                | Aliases to avoid      |
| ----------- | ----------------------------------------- | --------------------- |
| **Order**   | 顧客が1つ以上の商品を購入したいという要求 | Purchase, transaction |
| **Invoice** | 配送後に顧客へ送られる支払い請求          | Bill, payment request |

## People

| Term         | Definition                       | Aliases to avoid       |
| ------------ | -------------------------------- | ---------------------- |
| **Customer** | 注文を行う個人または組織         | Client, buyer, account |
| **User**     | システム内の認証アイデンティティ | Login, account         |

## Relationships

- **Invoice** は必ず1つの **Customer** に属する
- **Order** は1つ以上の **Invoice** を生む

## Example dialogue

> **Dev:** 「**Customer** が **Order** を出したら、すぐに **Invoice** を作成しますか?」
> **Domain expert:** 「いいえ — **Invoice** は **Fulfillment** が確定して初めて生成されます。商品が別々の **Shipment** で発送される場合、1つの **Order** から複数の **Invoice** が生まれることもあります。」
> **Dev:** 「では、発送前に **Shipment** がキャンセルされた場合、その分の **Invoice** は存在しないということですか?」
> **Domain expert:** 「その通りです。**Invoice** のライフサイクルは **Order** ではなく **Fulfillment** に紐づいています。」

## Flagged ambiguities

- "account" が **Customer** と **User** の両方の意味で使われていた — これらは異なる概念である: **Customer** は注文を行う存在であり、**User** は **Customer** を表すこともあれば表さないこともある認証アイデンティティである。
```

## Rules

- **意見を持つこと。** 同じ概念に複数の単語が存在する場合、最良のものを選び、他は避けるべきエイリアスとして列挙する。
- **対立を明示的にフラグする。** 会話の中で用語が曖昧に使われている場合、「Flagged ambiguities」セクションで明確な推奨とともに指摘する。
- **ドメインエキスパートに関連する用語だけを含める。** ドメイン言語上の意味を持たない限り、モジュールやクラスの名前は省く。
- **定義を簡潔に保つこと。** 最大1文。それが「何をするか」ではなく「何であるか」を定義する。
- **関係性を示すこと。** 太字の用語名を使い、明らかな場合はカーディナリティを表現する。
- **ドメイン用語だけを含める。** ドメイン固有の意味を持たない限り、汎用的なプログラミング概念(array、function、endpoint)は省く。
- **自然なクラスタが生まれる場合、用語を複数のテーブルに分ける**(例: サブドメイン、ライフサイクル、アクターごと)。各グループには専用の見出しとテーブルを設ける。すべての用語が単一の一貫したドメインに属する場合は1つのテーブルで十分である — 無理にグループ分けしない。
- **サンプル対話を書くこと。** 開発者とドメインエキスパートの短い会話(3〜5往復)で、用語が自然にどう相互作用するかを示す。対話は関連する概念間の境界を明確にし、用語が正確に使われている様子を示すべきである。

## Example dialogue

> **Dev:** 「Docker なしで **sync service** をテストするにはどうすればいいですか?」

> **Domain expert:** 「**Docker layer** の代わりに **filesystem layer** を渡してください。同じ **Sandbox service** インターフェースを実装していますが、**sandbox** としてローカルディレクトリを使います。」

> **Dev:** 「では **sync-in** は今でも **bundle** を作成して展開するんですか?」

> **Domain expert:** 「その通りです。**sync service** は自分がどのレイヤーと話しているか知りません。`exec` と `copyIn` を呼び出すだけです — **filesystem layer** はそれらをローカルのシェルコマンドとして実行するだけです。」

</example>

## Re-running

同じ会話の中で再度呼び出された場合:

1. 既存の `UBIQUITOUS_LANGUAGE.md` を読む
2. その後の議論から新しい用語を取り込む
3. 理解が深まっていれば定義を更新する
4. 新しい曖昧さがあれば再度フラグを立てる
5. 新しい用語を取り込むようサンプル対話を書き直す
