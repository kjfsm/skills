# 二軸レビュー

固定した基点から作業ツリーまでの変更を二軸でレビューする:

- **Standards** — コードはこのリポジトリの明文化されたコーディング標準に沿っているか?
- **Spec** — コードは元となったイシュー/PRD/スペックを忠実に実装しているか?

両方の軸を **並列サブエージェント** として実行することで互いのコンテキストを汚染しないようにし、その後このスキルがそれぞれの発見をまとめる。

イシュートラッカーはあなたにすでに渡されているはずである — `docs/agents/issue-tracker.md` がなければ、`/setup-skills` を実行するようユーザーに伝える。

Claude Code 組み込みの `/code-review` とは別物である。あちらは correctness のバグと整理の機会を差分から探す。こちらは **Spec 軸** — 元になったイシュー/PRD が求めたものを実装しているか — を持ち、Standards 軸は Fowler のスメルを基準線として持ち運ぶ。両方を走らせてもよい。

## 手順

### 1. 固定した基点を定める

ユーザーが言ったものが固定した基点である — コミットの SHA、ブランチ名、タグ、`main`、`HEAD~5` など。指定されていなければ、`git fetch` で既定ブランチを最新にし、`origin/<既定ブランチ>` を基点にする。

範囲は、基点とのマージベースから **作業ツリー** まで — コミット済みの変更と、まだコミットしていない編集の両方である。`<fixed-point>...HEAD` にしないのは、`implement` のようにコミットの前にレビューを通す流れで、未コミットの作業が丸ごと抜けるからである。次の3つを一度だけ確定する:

- 差分コマンド: `git diff $(git merge-base <fixed-point> HEAD)`
- 未追跡の新規ファイルの一覧: `git ls-files --others --exclude-standard` — 差分コマンドには出ないので、別に渡す
- コミット一覧: `git log <fixed-point>..HEAD --oneline`

先に進む前に、その固定した基点が解決できること(`git rev-parse <fixed-point>`)と、差分か新規ファイルのどちらかが空でないことを確認する。不正な参照や空の差分は、ここで失敗させるべきであり、2つの並列サブエージェントの中で失敗させるべきではない。

### 2. スペックの出所を特定する

元となったスペックを、次の順で探す:

1. コミットメッセージ内のイシュー参照(`#123`、`Closes #45`、GitLab の `!67` など) — `docs/agents/issue-tracker.md` にあるワークフロー経由で取得する。
2. ユーザーが引数として渡したパス、または呼び出し元のスキルが渡したチケット。
3. ブランチ名や機能と一致する、`docs/`、`specs/`、`.scratch/` 配下の PRD/スペックファイル。
4. 何も見つからなければ、ユーザーにスペックの場所を尋ねる。ないと言われた場合は、**Spec** サブエージェントはスキップして「スペックが利用できない」と報告する。

### 3. 標準の出所を特定する

`CODING_STANDARDS.md` や `CONTRIBUTING.md` など、コードをどう書くべきかをリポジトリ内で明文化しているもの全般。一覧にしてサブエージェントへ渡す — サブエージェントはそれ以外にそこへ到達する手段がない。

リポジトリが明文化しているものに加えて、Standards 軸は Fowler のコードスメル(『リファクタリング』第3章)の**基準線**を常に持ち運ぶ。基準線の全文と、それをどう適用するか(リポジトリの規約が優先される、常に判断の余地がある)は `standards-reviewer` エージェントが持つ — **ここには写さない。** 呼び出しのたびに貼り直す本文は、貼り忘れた日に黙って消える。

### 4. 両方のサブエージェントを並列に起動する

2つの `Agent` ツール呼び出しを含む1つのメッセージを送る。`subagent_type` は `standards-reviewer` と `spec-reviewer` で、どちらもこのプラグインが配る。**汎用のサブエージェントに依頼内容を書き下さない** — 依頼の全文(何を報告するか、_任意_ の印、語数の上限、モデル階層)はエージェント側に固定してあり、ここで書き直すとその2本が食い違う。

渡すのは、そのレビューでしか決まらないものだけである:

- **両方に** — 手順1で確定した差分コマンド、新規ファイルの一覧、コミット一覧。
- **Standards に** — 手順3で見つけた標準の出所ファイルの一覧。
- **Spec に** — スペックのパス、または取得済みの内容。

スペックが見つからない場合は `spec-reviewer` をスキップし、最終レポートにその旨を記す。

### 5. 集約する

2つのレポートを、そのまま、あるいは軽く整えたうえで `## Standards` と `## Spec` の見出しの下に提示する。発見事項を統合したり順位付けし直したりは **しない** — 2つの軸は意図的に分けられている(_なぜ二軸なのか_ を参照)。

_任意_ の印はそのまま持ち越す — 集約の段階で外さない。

最後に1行の要約をつける: 各軸の発見件数の合計(数えるのは _任意_ ではない発見だけ)と、(あれば)_それぞれの軸の中で_ 最悪の問題。軸をまたいで単一の勝者を選ばないこと — それは、この分離がまさに防ごうとしている再順位付けである。

## なぜ二軸なのか

ある変更は、一方の軸を通っても、もう一方は失敗しうる:

- あらゆる標準に従っているが、間違ったものを実装しているコード → **Standards は合格、Spec は不合格。**
- イシューが求めた通りに正確に動くが、プロジェクトの規約を破っているコード → **Spec は合格、Standards は不合格。**

これらを別々に報告することで、一方の軸がもう一方を覆い隠してしまうのを防ぐ。
