# レポートの形

既定は Markdown 1枚。ここが決めるのは中身と並びだけで、見た目は出し先の作法に従う。

## 並び

上から順に: ヘッダーと目的 → 候補(1件1節) → 落とした候補 → いちばんの推奨。

## ヘッダーと目的

アプリ名・日付・読んだ根拠(目的のファイルのパス、棚卸しした範囲、ログを読んだか)を1行ずつ。続けて `docs/product.md` の3節を短く引く — 各候補の根拠はここを指す。ユーザーがまだ認めていない行には「(未確認)」を付ける。前置きの段落は書かない。

## 候補

1つの候補を1つの `###` 節にする。

- **見出し** — 利用者ができるようになることを、利用者の言葉で(「先週の出欠を一覧で見返せる」)。機能名(「履歴画面」)にしない
- **強さと大きさ** — 見出しの直下に `Strong · M` のように1行
- **誰が・いつ** — 目的のファイルの利用者と場面を1文で
- **今 → 足したら** — 利用者がそれを片付けるまでの手順を、2列の表で並べる(左が今、右が足したあと)。今の側の回避策(別のツール、手作業、誰かに頼む)には **回避** と付ける。段の数の差が、そのまま便利さの量である
- **根拠** — 3つを分けて並べる
  - 目的の文 — `docs/product.md` から引用(`>`)
  - コード — ファイルの場所をコードスパンで。何が欠けているかを各行に一言
  - ログ — 数字があれば。無ければこの行ごと出さない
- **触るもの** — 画面・API・テーブルを1行ずつ。データモデルを変えるならそう書く
- **しないこと** — この候補の範囲から外すものを1〜2行
- **反する決定** — ADR や「何をしないか」を疑ってよいと言われて残した候補だけ。どの決定に反するかと、決めたときから何が変わったかを1〜2行

段落の説明を足さない。表が段落なしで読めないなら、表を作り直す。

## 落とした候補

手順4で落としたものを、落とした理由(目的の文を引けない / 決まったことに反する / 名前を入れ替えても通る / 既に詰めてある / 他の領分)と1行ずつ。ユーザーが「なぜあれが無いのか」と思ったときに答えるためにある。

## いちばんの推奨

候補名、なぜそれからかを1文、その節へのリンク。強さが同じなら大きさの小さい方を推す。

## 書き方

- 用語は用語集(`GLOSSARY.md` か `CONTEXT.md`)の言葉を使う。用語集が「出欠」と呼ぶものを「attendance」や「参加状況」と書かない
- 「便利になる」「使いやすくなる」で締めない。どの手順が何段減るか、誰に頼まずに済むかで書く
- ぼかさない。「〜かもしれません」と書きたくなった候補は `Speculative` を付けて言い切る

## HTML を求められたとき

並びと各候補の項目は上と同じ。違いは「今 → 足したら」だけで、表の代わりに図にする。左右に手順の段を並べ、回避策の段を赤で印す。画面の遷移やデータの流れが要点なら Mermaid の `flowchart` にする。強さはバッジにする(`Strong` = emerald、`Worth exploring` = amber、`Speculative` = slate)。落とした候補は `<details>` に畳む。
