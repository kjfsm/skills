# ルールを敷く

Claude Code がセッション中に読む指示を、**届き方の違う2つの層**に分けて置く。

- **`paths:` を持つ rule** — その glob にマッチするファイルを**編集するときだけ**注入される。このリポジトリ固有の事実を持つ
- **毎セッション読まれるもの** — スタックに依存しない絶対ルールと、追記先の優先順位

**層の境界は1問で決まる: `paths:` を書けるか。** この判定を飛ばして全部に `paths:` を付けると、毎セッション必要なルールが「そのパスを触ったときだけ」効く状態になる — 症状が出ないまま抜けるので、後から気づけない。

書けない側の宛先は、さらに2つに分かれる。

- **`CLAUDE.md` / `AGENTS.md` 本体** — 最優先で、短いもの。圧縮を挟んでも先頭が残り、他のどれより先に読まれる。絶対ルールはここに置く
- **`paths:` を持たない rule** — 分量があるもの。`paths:` の無い rule は毎セッション読まれるので、届き方は変わらず本体だけが短くなる(`/setup-skills` が書く `writing-conventions.md` がこれ)

**本体はすでにある方を編集する。** `AGENTS.md` があれば(`CLAUDE.md` がその symlink でも)そちらが本体である。そのうえで、毎セッション読ませたいものを `paths:` の無い rule へ逃がすと Codex など `.claude/rules/` を読まないハーネスに届かなくなる — `AGENTS.md` を持つリポジトリでは、逃がす先が実質1つ減る。

**この注意が効くのは、いま挙げた毎セッション側の2択だけである。** `paths:` を書ける規律はパス別注入という Claude Code の機能に乗るものなので、`CLAUDE.md` があるなら(symlink でも)rule が宛先である。ここで Codex を気にして本体へ戻すと、本体が長くなる代わりに得るものが無い。

本体は長くなるほど従われなくなる。`paths:` を書けるものをそこに残すのは、席を1つ潰しているのと同じである。行数の目安と削り方は `/tend-memory-files` が持つ。

これはプロンプト駆動のスキルであり、決定的なスクリプトではない。探索し、見つけたものを提示し、ユーザーと確認し、それから書く。

## 手順

### 1. 探索する

**このリポジトリで実際に何が繰り返し問題になっているか**を探す。慣習から推測して書かない — 実在の根拠が無いルールは、読む側にとって守る理由の無い1行になる。

- `.claude/rules/` — すでに何かあるか。あるなら追加であって新規作成ではない
- `CLAUDE.md` / `AGENTS.md` — すでに絶対ルールに相当する記述があるか。`## Agent skills` ブロック(`/setup-skills` の出力)はあるか
- `docs/agents/verification.md` — 検証ゲートのコマンド列。絶対ルールから参照する
- ディレクトリ構成 — レイヤの境界、生成物の出力先、テストの置き場、フレームワーク固有のディレクトリ
- `.gitignore` と生成物 — 手編集してはいけないパスの実在
- `package.json` の scripts / CI 設定 — 生成コマンド、リリース手順
- `git log` — 「同じ指摘を繰り返している」痕跡。revert、同じ箇所の修正の再発
- インストール済みのスキル — 一般則を持つスキルがあれば、rule はそれへ委譲する(手順4)

### 2. 本体に絶対ルールと自己更新ルールを置く

テンプレートは [absolute-rules.md](./absolute-rules.md) にある。**文面は全リポジトリで同一に保つ** — 言い回しがリポジトリごとに割れると、どれが正なのかを判断する場面が生まれる。

このリポジトリ固有の値(検証コマンド、生成物のパス)は文面に埋め込まず、`docs/agents/verification.md` や rules への参照にする。埋め込むと、そこだけ更新が要るファイルになって同一文面が壊れる。

**実態と食い違う項目は、置く前にユーザーに確認する。** 守られないルールが1つ混ざると、残りの信頼も落ちる。`git log --first-parent` で直コミットと PR の比率を見るなど、実態を先に確かめる。

**本体に rule の一覧を作らない。** `paths:` があれば該当パスを編集するときに自動で入るので、一覧は無くても動く。あると rule を1つ足すたびに2か所直すことになり、片方だけ直った日に一覧が嘘をつく。**すでに一覧がある本体では、そこへ足さずに1行のポインタへ畳む** — 既存の形に素直に足すのが、この失敗の最も多い入り口である。

すでに相当する記述があれば、重複を追記せずその場で統合する。

### 3. rules の候補を挙げ、確認する

[rule-catalog.md](./rule-catalog.md) の関心カタログを**候補一覧**として使う。カタログをそのまま敷かない — 探索で実在が確認できた関心だけを残す。

候補ごとに、次を1行で埋められるかを問う。

- **glob** — どのパスを編集するときに効くか。埋まらないものは手順2へ回す
- **固有の事実** — そのリポジトリでしか成り立たない事実が実際にあるか。一般則しか書けないなら、その rule は要らない

残った候補を、glob と1行要約の一覧としてユーザーに見せ、確認を取ってから書く。

### 4. 各 rule を書く

型は [rule-catalog.md](./rule-catalog.md) にある。書くときの規律は4つ。

**一般則を写さない。** その関心の一般作法を持つスキルがあるなら、冒頭で委譲を宣言する — 「一般作法は `/<skill>` を参照。ここには**このリポジトリ固有の事実だけ**を書く」。rule が持つのは、その一般則がこのリポジトリでは具体的にどのパス・どの関数・どのコマンドに対応するか、である。委譲先を書かずに一般則を写すと、上流が更新された日に rule だけが古いまま残る。

**数えた結果を書かない。** テストの本数、ファイル数、依存のバージョン一覧 — 次に1つ足した日に嘘になる。数え方(どのコマンドが出すか)を書く。

**具体名を持たせる。** 「適切にエラーを扱う」ではなく、その判定を持つ関数の実際のパスを書く。真偽を確認できる粒度まで落ちていない行は、守られたかどうかも確認できない。

**⚠️ は黙って壊れるものにだけ使う。** 型エラーや落ちるテストが教えてくれるものには要らない。値が黙って化ける、キャッシュが古いまま返る、といった**気づけない**失敗にだけ付ける。全部に付けると、どれも目立たなくなる。

### 5. 横断チェック

書いたものと既存を突き合わせる。矛盾を残すと、Claude はその場でどちらかを勝手に選ぶ。

- `CLAUDE.md`、`.claude/rules/` 配下、`docs/agents/*.md` を横断して、同じ振る舞いに食い違う指示が無いか
- 同じ事実が2か所に無いか。あるなら片方を参照に痩せさせる — 片方だけ直る日が来て、残った方が嘘をつく
- `paths:` を持たない rule が増えていないか。毎セッション読まれる側は手順2で置いたものだけのはずである

### 6. 完了

置いたファイルと、それぞれが**いつ注入されるか**をユーザーに伝える。rules は手で開く必要が無いこと、ルールが増えるのは「同じ指摘を2回受けたとき」であって先回りではないこと(その優先順位は手順2で `CLAUDE.md` に置いた自己更新ルールが持つ)に触れる。
