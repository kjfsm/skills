# グリリング

共通理解に到達するまで、ユーザーを容赦なく問い詰める。これを**設計ツリー**としてマッピングする: すべての意思決定は、そこにぶら下がる意思決定へと枝分かれする。

ツリーを**ラウンド**単位で進める。**フロンティア**とは、前提条件がすでに整っているすべての意思決定 — まだ聞いていない回答を推測せずに _今_ 問える質問のことである。フロンティア全体を1ラウンドで問う: 各質問に番号を振り、推奨回答を添える。そして次のラウンドに進む前に、ユーザーの回答を待つ。

ラウンドはこの形式で出す:

```
❓ **Q1** - **<質問のタイトル>**: <質問の本文。複数段落でも、選択肢を並べてもよい>

➡️ <あなたの推奨回答>

---

❓ **Q2** - **<質問のタイトル>**: <質問の本文。複数段落でも、選択肢を並べてもよい>

➡️ <あなたの推奨回答>
```

各ラウンドでユーザーが回答するたびにツリーは形を変える — 決着した意思決定はフロンティアを外側へ押し広げ、それに依存していた質問のブロックを解除する。フロンティアを再計算し、次のラウンドを問う。ある質問の答えが、このラウンドでまだ未解決の別の質問に依存している場合、それは今のラウンドではなく _後の_ ラウンドに属する。

_事実_ を見つけるのは常にあなたの仕事であり、ユーザーの仕事ではない。フロンティアの質問が環境(ファイルシステム、ツールなど)からの事実を必要とする場合は、サブエージェントを派遣して調べさせる — 自分で調べられることをユーザーに尋ねてはならない。それをブロッキングにしない: 実行中の調査は未解決の前提条件なので、それに依存する質問だけがサブエージェントの報告を待てばよい — フロンティアの残りは今すぐ問う。_意思決定_ はユーザーのものである — それぞれをユーザーに提示し、待つ。

既存の ADR や用語集は、推奨回答の論拠ではなく出発点である。書かれた時点の前提でだけ成り立っていた記述が、定義の顔をして残っていることがある。「ADR がこう決めている」で推奨を止めず、それが何を守ろうとしていたかまで戻り、いまも成り立つかを確かめてから推奨する。機能の設計を詰めているなら、同じ問題を解いている実在のプロダクトの **機構**(振る舞いではなく)を名指しで調べて並べ、採る/採らないを理由付きで書き分ける — それが推奨回答の材料になる。

フロンティアが空になったらセッションは完了である: 設計ツリーのすべての枝を訪れ、暗黙のうちに仮定されたものが何も残っていない状態。ユーザーが共通理解に到達したと確認するまで、それに基づいて行動してはならない。
