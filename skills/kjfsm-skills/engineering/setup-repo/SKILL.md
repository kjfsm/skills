# リポジトリを設定する

setup 系4工程の入口。**個別のスキルを覚えていなくてよい**ようにするためにあり、順序と依存はこのスキルが持つ。

敷くものは、**届き方の違う4つの層**である。

| 層                     | 効くとき                 | 敷くスキル                   |
| ---------------------- | ------------------------ | ---------------------------- |
| 規約・ドキュメント配置 | 毎セッション             | `/kjfsm-skills:setup-skills` |
| パス別ルール           | その glob を編集するとき | `/kjfsm-skills:setup-rules`  |
| CI                     | push / PR のとき         | `/kjfsm-skills:setup-ci`     |
| 弾く機構               | 該当する操作のたび       | `/kjfsm-skills:setup-hooks`  |

**下ほど確実に効き、上ほど広く読まれる。** 同じ規律を2つの層に置かない — 片方だけ直った日に、もう片方が嘘をつく。

**4行目はさらに3層に割れる** — `permissions.deny`、git hook と CI が同じ述語を呼ぶ検査スクリプト、Claude Code のフック。**「Claude のフック」はこの中で一番狭い**(そのマシンのセッションにしか届かず、クローンにも CI にも人間にも効かない)。どれに置けるかは「何から見えるか」で機械的に決まるので、判断は工程 D が持つ。

**これは冪等ではない。** 2回目は1回目と違う仕事をする — 済んだ工程を飛ばし、**ずれた箇所だけを直す**。同じ出力に戻すのではなく、同じ状態へ収束させる。

## 手順

### 1. 現況を読む

工程ごとに、**済んでいるかを観測できる印**がある。印を見るだけで、中身の妥当性はまだ問わない。

| 工程                           | 済みの印                                                                          | 依存 |
| ------------------------------ | --------------------------------------------------------------------------------- | ---- |
| A `/kjfsm-skills:setup-skills` | `docs/agents/verification.md` と `issue-tracker.md`、本体の `## Agent skills`     | なし |
| B `/kjfsm-skills:setup-rules`  | `.claude/rules/` に1本以上、本体に絶対ルール                                      | A    |
| C `/kjfsm-skills:setup-ci`     | `.github/workflows/` に検証ゲートを回すものがある                                 | A    |
| D `/kjfsm-skills:setup-hooks`  | `permissions.deny` / `lefthook.yml` / `.claude/settings.json` の `hooks` のどれか | B, C |

依存は**内容の依存**である。A が書く検証ゲートの定義が無ければ C は書けず、B が置く散文のルールが無ければ D は「何を弾くか」を決められない(先回りしたフックは、破られていないルールを守ることになる)。D が C にも依るのは、**弾く検査の多くが CI からも走る形になる**ためである — C を飛ばすと、手元だけに存在する検査ができる。

`AGENTS.md` しか無いリポジトリでは **B と D を飛ばす** — `.claude/` を読まないハーネスが対象なので、置いても届かない。

### 2. ずれを探す

印があった工程は、飛ばす前に**実態と食い違っていないか**だけ見る。ここが再実行の本体である。

- `docs/agents/verification.md` のコマンドが、`package.json` の scripts(や `Makefile`)に実在するか
- CI のステップが verification.md の行と一致しているか。**片方だけ増えていないか**
- `.claude/rules/` の `paths:` が、いまも存在するディレクトリを指しているか
- 本体の絶対ルールが名指ししているパス(生成物、シークレットのファイル)が実在するか
- `.worktreeinclude` が、いま実在する秘密のファイルを挙げているか(手順5)
- `.claude/settings.json` のフックが指すスクリプトが実在し、実行可能か
- **フックにだけ存在する検査が無いか** — 同じ述語が CI にも検証ゲートにも無いフックは、クローンでも CI でも効いていない。ここは工程 D へ回す
- **散文が、いま存在しない保護を謳っていないか** — 層を移したあと名前だけ置換された行は、嘘を書き直して温存している。`permissions.deny` はツール呼び出しにしか掛からず、Bash 経由の書き込みは通る
- 同じ規律が2つの層に重複していないか

**見つけたずれは、その工程をもう一度通すのではなく、ずれとして直す。** 通し直すと、ユーザーが手で入れた編集を巻き戻す。

### 3. 提示して確認する

未実施の工程・見つかったずれ・**何もしない工程**を、この順で1画面にまとめてユーザーに見せる。触らない工程を省かない — 「見たうえで触らない」と「見ていない」は別である。

そのうえで、どこまで進めるかを1度だけ尋ねる。工程ごとに聞き直さない。

### 4. 走らせる

A → B → C → D の順に、選ばれた工程だけを実行する。各工程は自分のスキルへ委譲する — **ここに手順を写さない**。

工程が終わるたびに1行で結果を報告し、次へ進む。途中で止まった場合、**どこまで済んだかを印の形で伝える**(次回そこから読み直せる)。

### 5. worktree へ持ち込むものを決める

4工程のどれにも属さない。**どの層にも届かず、worktree でだけ効く**ためである。

`claude -w` の worktree は新規チェックアウトなので、gitignore されたファイルが1つも入らない。A が書いた検証ゲートのうち **秘密を要するもの(dev サーバー、統合テスト、E2E)は、そこで落ちる**。`.worktreeinclude` に挙げた分だけがコピーされる。

`git status --ignored` だけでなく、**`.gitignore` と、追跡されている `*.example` も読む**。手元にその秘密がまだ無いだけで、リポジトリは在ることを前提にしている場合がある(`.dev.vars.example` を追跡していて `.dev.vars` が無い、など)。挙がっていないファイルはコピーされないだけなので、先に書いておいて損が無い。

そのうえで **手で置き直さないと落ちるもの**だけを挙げる。`.gitignore` にも `*.example` にも手掛かりが無ければ飛ばす — 空のファイルは置かない。

**生成物は挙げない。** `build/`、`.react-router/`、`worker-configuration.d.ts`、`node_modules` は worktree 側のコマンドが作り直す。コピーすると、作り直されない限り古い版がそこに居座る。

```
# Claude Code worktree へコピーする gitignore 済みファイル（.gitignore 構文）。
# worktree は新規チェックアウトのため未追跡ファイルが存在しない。
# [どのゲートに要るか] に必要な秘密だけをコピーする。
.dev.vars
```

既にあるなら、挙がっていないものを足すだけにする — ユーザーが外したものを戻さない。

### 6. 残るものを伝える

**ファイルにできない設定が2つ残る。** どちらもエージェントの手では終わらないので、手順として渡す。

- **必須チェック** — CI を敷いても、branch protection で required にするまでは助言である(`/kjfsm-skills:setup-ci` の手順5)
- **出力スタイル** — 使うなら `/config` で1度選ぶ。ただしサブセッションには届かないので、規約は A が本体側にも書いている

最後に、**4つの層のどれが何を捕まえるか**を1行ずつで示す。層の役割が読めていないと、次に問題が起きたときにどこへ足せばよいか分からず、全部が本体へ積まれていく。

## 越えない線

- **工程を先回りして足さない。** CI が要らないリポジトリ(remote が無い、個人の使い捨て)では C を飛ばす — そのとき D は、CI から呼べる検査という選択肢を1つ失ったうえで層を選ぶ。弾く機構は、破られたルールが無ければ敷かない — **実態を数えてから決める**(`git log --first-parent` の PR 経由率など)。規約に書いてあることは根拠にならない
- **既存の編集を上書きしない。** 印があるファイルは、書き直すのではなく差分を当てる
- **本体を長くしない。** 各工程が本体へ足す行が増えていたら、`/kjfsm-skills:tend-memory-files` でトリムしてから次へ進む
- **手順をここへ写して太らせない。** 工程の中身は各スキルが持つ。`setup-skills` の本体は 5000 トークンちょうどで、**数行足すだけで検査(SKILL.md body)が落ちる** — 工程 A に足したいものが出たら、まずそちらを削れるか見る
