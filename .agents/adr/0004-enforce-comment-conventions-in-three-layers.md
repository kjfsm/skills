# コメント規約は常駐テキストを増やさず、発火するフックと削るパスで効かせる

4本の柱(How=コード、What=テスト、Why=コミットログ、Why not=コメント)は `output-styles/kjfsm.md`・`CLAUDE.md`・`setup-skills` の3か所に本文として常駐し、検査 16. が同期を見ている。それでも守られない。

このとき素直に出てくる手は「**常に読まれる場所をもう1つ増やす**」である — `SessionStart` フックの標準出力、`UserPromptSubmit` の注入、`.claude/rules/` の追加。この手を捨てる。

## 常駐を増やしても何も変わらない

`SessionStart` と `UserPromptSubmit` の標準出力が着く先は、`CLAUDE.md` と出力スタイルが着く先と**同じシステムプロンプトである**([Hooks reference](https://code.claude.com/docs/en/hooks) — plain stdout がコンテキストに入るのは `UserPromptSubmit` / `UserPromptExpansion` / `SessionStart` の3イベントだけ)。同じ場所に4枚目のコピーを置いても、モデルから見た景色は1ビットも変わらない。増えるのは同期先だけである。

そもそも失敗しているのは注入ではない。`where-to-write-what` が自分について書いている通り、**コメントを書く場面でモデルは「迷った」と自覚しない**。規約はコンテキストに在るのに、いま自分がその規約の場面にいると気づかない。**読まれることと、その場面にいると気づくことは別である。**

## 指示の層には天井がある

[anthropics/claude-code#65961](https://github.com/anthropics/claude-code/issues/65961)(2026-06 起票、open、公式の返答なし)は、既定の饒舌なコメントが**明示的なユーザー指示を上書きする強さで入っている**ことを、全言語・全モデル(Opus 4-8 / Opus 5 / Sonnet 5)で報告している。`CLAUDE.md` ルール、メモリ、強制フックを積み上げても _partially_ にしかならない、というのが起票者の観測である。

外で収束している形も同じ方向を指す。[pre-hoc + post-hoc の二層](https://gist.github.com/bavanws/123e0343f8a79cec825d9141124a0a83)が代表例で、結論は「予防が新しいノイズを減らし、事後パスが取りこぼしと継承した分を回収する。**どちらか片方では足りない**」。同型のものが[スキルとして商品化](https://mcpmarket.com/tools/skills/minimalist-code-commenting)もされている。

コメントの冗長性を測る lint も CI チェックも**存在しない**。全員が LLM のパスでやっている。

## 決定

1. **常駐テキストを増やさない。** 4本の柱とコメントの判定は3か所のまま。ADR もスキルも、この本文を書き写さない — 書き写した箇所は検査 16. の管理外の4つ目になり、フックや検査が壊れた日に、揃っていない本文だけが残る。
2. **足すなら「発火の条件性」を足す。** フックにしかない梃子は注入ではない。`Edit` / `Write` で**コメント行が増えたときだけ**鳴る `PostToolUse` フック(`hooks/hooks.json` から出荷)が、増えた行を1行ずつ点検させる。
3. **フックは判定しない。** 鳴る条件は機械的(コメント行が増えたか)で、適切かの判断はモデルに残す。判定まで寄せると `setup-hooks` の条件 3 に触れ、通ってよい編集を止めた瞬間にモデルは目的を捨てて `Bash` の `sed` へ逃げる。**回避されたぶんだけ、ルールは守られたように見えて実際は緩む。**
4. **回収は削る側で行う。** `/prune-comments` が、書かれてしまったコメントを1パスで削る。
5. **削る基準は非対称にし、合格基準を「減った量」にしない。**

**この2つの運用ルールの本文は `/prune-comments` にしか置かない。** 順序の決まった6段、非対称のタイブレーカー、合格基準は、そのままサブエージェントへ貼られて**単独で立つ必要がある**側にある。ここに書き写すと同期先が2つになり、片方だけ直った日に、貼られる方が古くなる。

### 削る側に賭ける理由

- **削除は抑制より易しい。** 「このコメントは非自明な情報を運んでいるか」は手元のテキストに対する分類である。「書きたくなるが書かない」は事前分布に逆らう自制で、はるかに不安定である
- **削除は検証できて巻き戻せる。** 何を消したかは差分に全部写り、原本は git にある。抑制は不可視で、良い自制だったのか手抜きだったのか誰にも判定できない
- **書いた本人は自分のコメントを正当化する。** だから汚れていないコンテキスト(サブエージェント)で走らせる

## `setup-hooks` の3条件のうち、条件 2 は満たさない

`setup-hooks` はフックにしてよいものを3条件で絞り、「1つでも欠けたら散文のままにする」としている。このフックは条件 1(すでに散文で書いてあり実際に破られた)と条件 3(機械的に判定できる)を満たすが、**条件 2「破られたことに気づけない、または戻すのが高い」は満たさない** — 余計なコメントは差分に写るし、消すのも安い。

それでも敷くのは、**3条件が「決定的に弾く」フックのために書かれているから**である。条件 2 が守っているのは「弾くコストに見合うか」で、弾くフックの失敗は通ってよい操作を止めることだから重い。このフックは弾かない。誤って鳴ったときの損害は数十トークンの点検1回で、条件 2 が防ごうとしている損害とは桁が違う。

**`setup-hooks` の側にこの区別が書かれていないのは、そちらの穴である。** 弾かないフックの判定条件は別に立つべきで、この ADR はその不足を記録するに留める。

## 分業の境界

違反には**書きすぎ**と**書かなすぎ**があり、片方ずつ別の層でしか押さえられない。

| 層                                  | 捕まえるもの                      | 出力       |
| ----------------------------------- | --------------------------------- | ---------- |
| `PostToolUse` フック                | 書きすぎ(`Edit`/`Write` 経由のみ) | 点検の合図 |
| `/prune-comments`                   | 書きすぎ(回収)                    | **消す**   |
| `/two-axis-review` Standards 軸 (c) | **書かなすぎ**(Why not が無い)    | 報告       |

**書かれなかった Why not は差分のどこにも現れない。** だからスメルの一覧に項目を足しても永遠に出てこず、Standards サブエージェントへ**別立ての依頼として明示的に頼む**以外にない。フックにもこれは原理的に拾えない。

`/prune-comments` に足す側を担当させないのは、差分に写っていないものを探す作業が消す作業と要求される見方が逆で、同じパスに混ぜると削る手が緩むからである。

**素通しするもの**: `Bash` の `sed` やヒアドキュメントによる書き込み。`FileChanged` は監視対象をファイル名で literal に列挙する必要があり任意のソースファイルには使えないので、承知のうえで `Edit|Write` に掛けている。

## 目的関数は「少なく」ではない

[Ousterhout](https://se-radio.net/2022/07/episode-520-john-ousterhout-on-a-philosophy-of-software-design/) は Clean Code の「すべてのコメントは失敗」に明確に反対し、コードだけでは人が理解に必要なことを全ては記述できないとしてインターフェースコメントを必須と主張する。4本の柱は「型に出ない契約は JSDoc」でここを吸収しているので矛盾しない。

ただし常駐テキストは「書かない」から始まるため、**削る方向にだけ強く、足りない方向には効かない**。上の表で `/two-axis-review` に不足側を持たせているのは、この非対称を承知したうえの配置である。

## 却下したもの

- **`SessionStart` フックで規約を注入する** — 着く先が `CLAUDE.md` と同じシステムプロンプトである。同期先が1つ増えるだけで効果はゼロ
- **`Stop` フックで `git diff` を見る**(`Bash` 経由の穴を塞げる)— ループ保護(`stop_hook_active`、連続8回上限)を自分で捌く必要があるうえ、**正当に残したコメントに毎ターン鳴る**。フックの唯一の梃子は条件性で、毎ターン鳴った瞬間にそれを失って常駐テキストと同じ背景になる
- **CI でコメント密度を測る** — 閾値に意味が無い。密度が低くても中身が空のコメントは通る
- **`CLAUDE.md` に良い例・悪い例を並べる** — 「規約は行数が増えるほど従われなくなる」に反する。常駐させる価値がありそうな唯一の候補は決定 5 の非対称なタイブレーカー(判断の瞬間そのものに効く1行)だが、**まだ常駐させていない** — いまは `/prune-comments` の中にしかない。3か所を増やす前に、パスの側で使ってみて効くかを見る

## 測定はまだ済んでいない

`/prune-comments` をこの決定を入れたブランチ自身の差分に1回走らせ、コメント6ブロック中1つが削られた(フック冒頭の、`grep` で数えて返すという How をなぞった行。「判定しない」という境界は直後の1文が理由つきで持っていた)。書いた本人が残す側に倒れる、という前提が出た1件ではある。

**ただしこれは測定として成立していない。** 対象は、コメント規律そのものを議論している最中に、書き込みフックが有効な状態で書かれたコメントである — 予防が最も効いている条件のサンプルで、歩留まりの低さは予防の天井を反証しない。

**この決定が覆る条件**: コメントのことを誰も考えていない普通のセッションで書かれたコードに `/prune-comments` を当てて、**消すものがほとんど出てこない**なら、予防の天井は想定より高く、投資先は逆になる。
