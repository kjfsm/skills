# リポジトリを設定する

setup 系4工程の入口。**個別のスキルを覚えていなくてよい**ようにするためにあり、順序と依存はこのスキルが持つ。

敷くものは、**届き方の違う4つの層**である。

| 層                     | 効くとき                     | 敷くスキル      |
| ---------------------- | ---------------------------- | --------------- |
| 規約・ドキュメント配置 | 毎セッション                 | `/setup-skills` |
| パス別ルール           | その glob を編集するとき     | `/setup-rules`  |
| CI                     | push / PR のとき             | `/setup-ci`     |
| フック                 | 該当するツール呼び出しのたび | `/setup-hooks`  |

**下ほど確実に効き、上ほど広く効く。** 同じ規律を2つの層に置かない — 片方だけ直った日に、もう片方が嘘をつく。

**これは冪等ではない。** 2回目は1回目と違う仕事をする — 済んだ工程を飛ばし、**ずれた箇所だけを直す**。同じ出力に戻すのではなく、同じ状態へ収束させる。

## 手順

### 1. 現況を読む

工程ごとに、**済んでいるかを観測できる印**がある。印を見るだけで、中身の妥当性はまだ問わない。

| 工程              | 済みの印                                                                      | 依存 |
| ----------------- | ----------------------------------------------------------------------------- | ---- |
| A `/setup-skills` | `docs/agents/verification.md` と `issue-tracker.md`、本体の `## Agent skills` | なし |
| B `/setup-rules`  | `.claude/rules/` に1本以上、本体に絶対ルール                                  | A    |
| C `/setup-ci`     | `.github/workflows/` に検証ゲートを回すものがある                             | A    |
| D `/setup-hooks`  | `.claude/settings.json` の `hooks`                                            | B    |

依存は**内容の依存**である。A が書く検証ゲートの定義が無ければ C は書けず、B が置く散文のルールが無ければ D は「何を弾くか」を決められない(先回りしたフックは、破られていないルールを守ることになる)。

`AGENTS.md` しか無いリポジトリでは **B と D を飛ばす** — `.claude/` を読まないハーネスが対象なので、置いても届かない。

### 2. ずれを探す

印があった工程は、飛ばす前に**実態と食い違っていないか**だけ見る。ここが再実行の本体である。

- `docs/agents/verification.md` のコマンドが、`package.json` の scripts(や `Makefile`)に実在するか
- CI のステップが verification.md の行と一致しているか。**片方だけ増えていないか**
- `.claude/rules/` の `paths:` が、いまも存在するディレクトリを指しているか
- 本体の絶対ルールが名指ししているパス(生成物、シークレットのファイル)が実在するか
- `.claude/settings.json` のフックが指すスクリプトが実在し、実行可能か
- 同じ規律が2つの層に重複していないか

**見つけたずれは、その工程をもう一度通すのではなく、ずれとして直す。** 通し直すと、ユーザーが手で入れた編集を巻き戻す。

### 3. 提示して確認する

未実施の工程・見つかったずれ・**何もしない工程**を、この順で1画面にまとめてユーザーに見せる。触らない工程を省かない — 「見たうえで触らない」と「見ていない」は別である。

そのうえで、どこまで進めるかを1度だけ尋ねる。工程ごとに聞き直さない。

### 4. 走らせる

A → B → C → D の順に、選ばれた工程だけを実行する。各工程は自分のスキルへ委譲する — **ここに手順を写さない**。

工程が終わるたびに1行で結果を報告し、次へ進む。途中で止まった場合、**どこまで済んだかを印の形で伝える**(次回そこから読み直せる)。

### 5. 残るものを伝える

**ファイルにできない設定が2つ残る。** どちらもエージェントの手では終わらないので、手順として渡す。

- **必須チェック** — CI を敷いても、branch protection で required にするまでは助言である(`/setup-ci` の手順5)
- **出力スタイル** — 使うなら `/config` で1度選ぶ。ただしサブセッションには届かないので、規約は A が本体側にも書いている

最後に、**4つの層のどれが何を捕まえるか**を1行ずつで示す。層の役割が読めていないと、次に問題が起きたときにどこへ足せばよいか分からず、全部が本体へ積まれていく。

## 越えない線

- **工程を先回りして足さない。** CI が要らないリポジトリ(remote が無い、個人の使い捨て)では C を飛ばす。フックは、破られたルールが無ければ敷かない
- **既存の編集を上書きしない。** 印があるファイルは、書き直すのではなく差分を当てる
- **本体を長くしない。** 各工程が本体へ足す行が増えていたら、`/tend-memory-files` でトリムしてから次へ進む
