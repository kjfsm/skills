# UI Prototype

単一のルート上に、フローティングのボトムバーで切り替えられる **何通りかの根本的に異なる UI バリエーション** を生成する。ユーザーはブラウザでバリアントを切り替え、1つを選ぶ(あるいはそれぞれから良い部分をつまみ食いする)、残りは捨てる。

問いがロジック/状態についてのもので、見た目についてでなければ — 分岐を間違えている。[LOGIC.md](LOGIC.md) を使う。

## この形が適している場合

- 「このページはどう見えるべきか?」
- 「決める前に、このダッシュボードのいくつかの選択肢を見たい。」
- 「設定画面の別のレイアウトを試したい。」
- そうしなければユーザーが頭の中で3つの曖昧なモックアップから選ぶのに1日を費やすことになるとき、いつでも。

## 2つの下位分類 — 強く下位分類 A を優先する

UI プロトタイプは、**アプリの他の部分に隣接している** とき — 本物のヘッダー、本物のサイドバー、本物のデータ、本物の密度 — の方がはるかに判断しやすい。単独の使い捨てルートは真空である: どのバリアントも単独で見れば問題なさそうに見えてしまう。バリアントを収める既存のページがもっともらしくあるなら、常に下位分類 A をデフォルトにする。プロトタイプに本当に近くに置く場所がない場合にだけ、下位分類 B に手を伸ばす。

### 下位分類 A — 既存ページへの調整(推奨)

そのルートはすでに存在する。バリアントは `?variant=` の URL クエリパラメータによって切り替えられ、**同じルート上に** 描画される。既存のデータ取得、パラメータ、認証はすべてそのまま残り、描画だけが入れ替わる。これがデフォルトである。そうしない特別な理由がない限り、これを選ぶ。

プロトタイプの対象がまだページを持たないが _自然にどこかのページの中に収まる_ もの(ダッシュボードの新しいセクション、設定画面の新しいカード、既存フローの新しいステップ)であっても、それは下位分類 A である。バリアントをホストとなるページの中にマウントする。

### 下位分類 B — 新しいページ(最後の手段)

プロトタイピングの対象が、収まる既存のページが本当にない場合 — たとえば、まったく新しいトップレベルの画面や、まともに埋め込める場所がないフロー — にだけこれを使う。

プロジェクトがすでに使っているルーティングの慣習に従って **使い捨てのルート** を作る — 新しいトップレベルの構造を発明しない。それが明らかにプロトタイプだと分かるよう名付ける(例えば、パスやファイル名に `prototype` という単語を含める)。同じ `?variant=` のパターンを使う。

下位分類 B に決める前に、確認する: 本当にこれを埋め込める既存のページはないか? 空のルートは、中身のあるルートなら露わになるはずのデザイン上の問題を隠してしまう。

どちらの下位分類でも、フローティングのボトムバーは同一である。

## 手順

### 1. 問いを述べ、N を決める

デフォルトは **3バリアント**。5を超えると、根本的に異なるというより、ノイズになり始める — そこで打ち止めにする。

プロトタイプの場所か、ファイル先頭のコメントに、計画を1行で書く:

> 「設定ページの3つのバリアント。既存の `/settings` ルート上で `?variant=` によって切り替え可能。」

これは、ユーザーがここにいて異論を挟める場合でも、そうでない場合でも機能する。

### 2. 根本的に異なるバリアントを生成する

各バリアントを起草する。それぞれを次に照らす:

- ページの目的と、それがアクセスできるデータ。
- プロジェクトのコンポーネントライブラリ/スタイリングシステム(TailwindCSS、shadcn、MUI、素の CSS、何でも)。
- 明確にエクスポートされたコンポーネント名、例えば `VariantA`、`VariantB`、`VariantC`。

バリアントは、色が違うだけでなく **構造的に異なって** いなければならない — 異なるレイアウト、異なる情報の階層、異なる主要なアフォーダンス。わずかに変えたカードグリッドを3つ用意しても、それは UI プロトタイプではなく壁紙である。2つの草案が似すぎている場合は、明示的に「カードグリッドを使わない」という指示を与えて片方を作り直す。

### 3. それらを配線する

そのルート上に、単一の切り替えコンポーネントを作る:

```tsx
// pseudo-code — adapt to the project's framework
const variant = searchParams.get("variant") ?? "A";
return (
  <>
    {variant === "A" && <VariantA {...data} />}
    {variant === "B" && <VariantB {...data} />}
    {variant === "C" && <VariantC {...data} />}
    <PrototypeSwitcher variants={["A", "B", "C"]} current={variant} />
  </>
);
```

下位分類 A(既存ページ)の場合: 既存のデータ取得はすべて切り替えコンポーネントの上にそのまま残し、描画されるサブツリーだけがバリアントごとに変わる。

下位分類 B(新しいページ)の場合: `/prototype/<name>` 配下の使い捨てルートが同じ切り替えコンポーネントをマウントする。

### 4. フローティングの切り替えコンポーネントを作る

画面下部中央に固定された小さなバーで、3つの要素を持つ:

- **左矢印** — 前のバリアントへ循環する(端まで行ったら折り返す)。
- **バリアントのラベル** — 現在のバリアントのキーを示し、そのバリアントが名前をエクスポートしていればその名前も示す。例: `B — Sidebar layout`。
- **右矢印** — 次のバリアントへ循環する(端まで行ったら折り返す)。

振る舞い:

- 矢印をクリックすると URL のクエリパラメータが更新され(フレームワークのルーターを使う — Next なら `router.replace`、React Router なら `navigate` など)、バリアントが共有可能かつリロードしても安定するようにする。
- キーボード: `←` と `→` の矢印キーでも循環する。`<input>`、`<textarea>`、`[contenteditable]` にフォーカスがあるときは矢印キーを横取りしない。
- ページとは視覚的に区別できるようにする(例えば高コントラストのピル、控えめな影)。評価対象のデザインの一部ではないことが明らかであるように。
- 本番ビルドでは非表示にする — `process.env.NODE_ENV !== 'production'` かそれに相当するチェックでガードし、うっかりプロトタイプがマージされてもユーザーにこのバーが届かないようにする。

この切り替えコンポーネントは単一の共有コンポーネントに入れ、両方の下位分類が再利用できるようにする。プロジェクトの共有 UI が置かれている場所に配置する。

### 5. 引き渡す

URL(と `?variant=` のキー)を伝える。ユーザーは都合のいいときに切り替えてみる。興味深いフィードバックはたいてい **「B のヘッダーと C のサイドバーが欲しい」** のようなもの — それこそがユーザーが本当に求めているデザインである。

### 6. 答えを記録し、片付ける

あるバリアントが勝者に決まったら、答え — どのバリアントか、なぜか — を記録し、それから [SKILL](SKILL.md) が説明する方法でプロトタイプを記録する。勝者は本物のコードに畳み込み、残りは main ではなく使い捨てブランチへ移す:

- **下位分類 A** — 勝者を既存のページに畳み込む。負けたバリアントと切り替えコンポーネントは main から取り除く。
- **下位分類 B** — 勝ったバリアントを本物のルートに昇格させる。使い捨てルートと切り替えコンポーネントは main から取り除く。

バリアント一式は一次情報源なので、ゴミ箱ではなく使い捨てブランチに置かれる — main ブランチに残されたバリアントのコンポーネントと切り替えコンポーネントはすぐに腐り、次の読者を混乱させる。

## アンチパターン

- **色や文言だけが異なるバリアント。** それは調整であって、プロトタイプではない。本物のバリアントは構造について食い違う。
- **バリアント間でコードを共有しすぎる。** 共有の `<Header>` は問題ないが、共有の `<Layout>` は狙いを台無しにする。各バリアントはレイアウトを自由に捨てられるべきである。
- **バリアントを本物の変更操作に配線する。** 読み取り専用のプロトタイプは問題ない。バリアントが変更操作を必要とする場合は、スタブを向ける — 問いは「バックエンドは動くか」ではなく「これはどう見えるべきか」である。
- **プロトタイプを直接本番に昇格させる。** バリアントのコードはプロトタイプの制約(テストなし、最小限のエラー処理)の下で書かれている。畳み込むときはきちんと書き直す。
