# setup-cf-access(Cloudflare Access の標準ルール)

Worker を Access で塞ぐときの **3層ルール** を宣言する。**画面の導線も API の形も、記憶やこのファイルの固定値ではなく、その都度、公式ドキュメントで最新を確認する。** Workers と Access の統合は動きが速く、ここに写した手順はすぐ陳腐化する。

確認先(`cloudflare-docs` MCP の `search_cloudflare_documentation`、または直接):

- Workers と Access の統合、守る対象と `destinations` の型 — `/workers/configuration/cloudflare-access/`
- パス・ワイルドカードの書き方 — `/cloudflare-one/access-controls/policies/app-paths/`
- アプリ作成のリクエストスキーマ — Access applications API
- API トークンの権限グループ名 — `/fundamentals/api/reference/permissions/`

## 3層ルール

公式に載っていないのはここだけ。**このファイルが唯一の情報源**として扱う。

| 層               | decision       | include                | 何のため                                                              |
| ---------------- | -------------- | ---------------------- | --------------------------------------------------------------------- |
| **人間**         | `allow`        | 指定メールアドレスのみ | 管理者がブラウザで触る                                                |
| **機械**         | `non_identity` | サービストークン       | MCP・CI・curl                                                         |
| **自前認証パス** | `bypass`       | everyone               | アプリ自身が認証を持つパス。Access のヘッダを通せない経路のため開ける |

- `session_duration` は **168h** に揃える。
- 人間層は **reusable policy を1本作って使い回す**。メールを増やすときの編集箇所が1つで済む。
- bypass 層は「アプリ側に認証がある」ことを確認できたパスだけに、範囲を最小に切って当てる。

## 1. 経路を洗い出す

Worker に届く経路をすべて列挙する。1つ漏らすと、そこが素通りで残る — カスタムドメイン、routes、`workers.dev` 本体、プレビュー URL。既存の Access アプリと突き合わせ、**どのアプリにも載っていないホスト名**を挙げる。

使っていない経路は、Access で守るより **落とすほうが確実**(`workers.dev` を無効化するなど)。ダッシュボードで落としても Wrangler 設定に書かなければ次の deploy で復活するので、**リポジトリ側にも書く**。

完了基準: 列挙した経路それぞれについて、どの層が守るか / 落とすか / 意図して公開かを言える。

## 2. 守り方を決める

- **Worker 単位** — その Worker に紐づく全経路を一括で守り、経路が増えても追従する。これが既定。
- **ホスト名 / パス単位** — 一部のパスだけ扱いを変えるとき。bypass 層は必ずこちら。
- WebSocket を使う Worker は Worker 単位 Access で `403` になるため、ホスト名単位にする。

効く順は **ホスト名 / パス > Worker 単位 > アカウント単位**。より具体的なものが勝つので、bypass 層は Worker 単位の allow より先に効く。対象ごとの `destinations` の型は公式の「守る対象」の対応表を引く。

## 3. 手で入れるか、API で入れるかを選ばせる

**ユーザーに選ばせてから進む。** どちらにも向き不向きがあり、勝手に始めない。

| | **手動**(ダッシュボード) | **API** |
| --- | --- | --- |
| 要るもの | ブラウザ | Access 権限付き API トークン |
| 向くとき | 1回きり。トークンを増やしたくない | 繰り返す。複数の対象に同じ形で当てる |
| エージェントの役割 | 画面の導線を公式で確認して案内し、**結果を API で読み取って検証する** | 作成から検証まで通してやる |

### 手動を選んだとき

その時点の公式ページで画面の導線を確認してから案内する。画面名やボタン名を記憶で書かない。適用後、**必ず API で読み取って**意図どおりか確かめる(手動操作は取り違えが起きるため、口頭の「やった」で完了にしない)。

### API を選んだとき

作成に進む前に、副作用のないプローブで書き込めるか確かめる。存在しない ID への `PATCH` を投げ、返ったコードを見る:

| コード               | 意味                   | 直し方                                          |
| -------------------- | ---------------------- | ----------------------------------------------- |
| `10405`              | 認証スキーム自体が拒否 | **再認可では直らない。API トークンに切り替える** |
| `10000` / `9109`     | スコープ不足           | 再認可・権限追加で直る                          |
| `404` / not found 系 | 権限あり               | 次へ                                            |

**Access のアプリ・ポリシー・IdP は、OAuth(MCP の `cloudflare-api`)では必ず `10405` になる。** Cloudflare が OAuth トークンでの Zero Trust 設定変更を許していないため、権限を足しても再接続しても通らない。同じ MCP でも `access/service_tokens` の書き込みは通るので、**1か所書けたことを根拠に「Access も書ける」と判断しない** — アプリ作成そのものでプローブする。

`10405` を踏んだら、API トークンの用意をユーザーに頼む。要るのは Account スコープの `Access: Apps and Policies` **Edit** と `Access: Policies` **Edit**(サービストークンも発行するなら `Access: Service Tokens` **Edit**)。発行手順と権限グループの正確な名前は公式の権限一覧で確認する。受け取ったら `.env` の `CLOUDFLARE_API_TOKEN` に置いてもらい、Bearer で REST を叩く。

作る前に GET で引き、IdP・reusable policy・サービストークンは**同じものがあれば使い回す**。

完了基準: 適用が通ったことを確認したか、**どのコードが返ったかと必要な権限の具体名を伝えて止まった**か、どちらか。推測で作成に進まない。

## 4. 3層それぞれを curl で確かめる

手動・API のどちらで入れたかに関わらず、作っただけで終わらせない。層ごとに1回ずつ叩く:

- 人間経路 — 素の curl が `302` で Access のログインへ飛ぶ
- 機械経路 — サービストークンのヘッダを付けて `200`
- bypass 層 — 素の curl がアプリ自身の応答に届く(Access の `302` を経由しない)

完了基準: 3層すべてで期待どおりの応答が返り、手順1で挙げた経路に素通りが残っていない。
