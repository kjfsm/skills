# 用語集 — 優れたスキルを作る

優れたスキルを作るためのドメインモデル。スキルは、確率的なシステムから決定性を絞り出すために存在する。根本的な美徳は **予測可能性(Predictability)** であり、以下のすべての用語はそれに働きかけるレバーである。これは [`writing-great-skills`](SKILL.md) が開示するリファレンスである。

用語は軸ごとにグループ化されている: **Invocation(呼び出し)**(スキルにどう到達するか)、**Information Hierarchy(情報階層)**(その内容がどう配置されるか)、**Steering(操舵)**(エージェントの実行時の振る舞いがどう形作られるか)、**Pruning(刈り込み)**(どう引き締まった状態を保つか)。各 **failure mode(失敗モード)** は、それを直すレバーの隣に、_failure mode_ のタグ付きで置かれている。

どの定義の中の **太字の用語** も、それ自体がこの用語集の中で定義されている。見出しで探すこと。

## Predictability(予測可能性)

スキルが、毎回の実行でエージェントに同じ _やり方_ で振る舞わせる度合い — 同じ出力ではなく、同じプロセス(ブレインストーミングのスキルは _予測可能に_ 発散すべきである。トークンは変わっても、振る舞いは変わらない)。他のすべての用語が仕える根本的な美徳であり、コストと保守性はその症状であって、対立するものではない。

_避ける表現_: consistency, reliability, robustness, output-determinism

## Invocation(呼び出し)

スキルにどう到達するか — そして、その選択のために支払う2種類の負荷。

### Model-Invoked(モデル呼び出し型)

**description** フィールドを保持するスキルで、エージェントがそれを見て自律的に発火できる — そして人間も引き続きその名前を入力できるので、モデル呼び出し型は常にユーザーによる到達を _含む_。モデルのみという状態は存在しない: description はエージェントによる発見可能性を _追加する_ だけであり、人間のそれを取り除くことは決してない。その発見可能性と引き換えに、毎ターン恒久的な **context load(コンテキスト負荷)** を支払う。他のスキルから到達可能である。エージェントが発見できるようにする description は、そのまま呼び出し可能にもするからである。内容がすべて **reference(リファレンス)** であるモデル呼び出し型のスキルは、共有リファレンスの置き場所にもなる: 他のスキルがそれを呼び出せるので、複数のスキルが必要とするリファレンスが1か所に収まる。モデル呼び出し型を選ぶのは、エージェントが自力でそのスキルに到達しなければならない場合だけにする。手で発火する以外に決して使われないなら、description を落とし、コンテキスト負荷を支払わない。

_避ける表現_: ability, tool, capability

### User-Invoked(ユーザー呼び出し型)

**description** を取り除いたスキル — エージェントからは見えず、人間がその名前を入力したときだけ到達できる(**モデル呼び出し型** がユーザー _かつ_ エージェントであるのに対し、これはユーザーの _みに限られる_)。エージェントによる発見可能性を、ゼロの **context load(コンテキスト負荷)** と引き換える。description がないため、人間以外の何もそれに到達できない: 他のどのスキルもそれを発火できない。

_避ける表現_: procedure, workflow, command

### Description

スキルの機械可読なトリガーであり、**モデル呼び出し型** のスキルが常時読み込ませておくことを強いられる唯一の **context pointer(コンテキストポインタ)**。その存在の有無こそが、呼び出し方式の軸 _そのもの_ である: それを保持すればそのスキルはモデル呼び出し型になる(そして他のスキルから到達可能になる)。削除すればそのスキルは **ユーザー呼び出し型** になり、人間だけが到達できる。モデル呼び出し型のスキルの **context load(コンテキスト負荷)** の発生源。

_避ける表現_: frontmatter, summary

### Context Pointer(コンテキストポインタ)

エージェントのコンテキストの中に保持される参照であり、コンテキストの外にある何らかの資料を名指しし、そこに到達する条件を符号化したもの。**description** は最上位のコンテキストポインタ(コンテキストウィンドウ → スキル)であり、開示されたファイルへのポインタは、1段階下にある同じ対象である。エージェントが _いつ_ 到達するか、そして _どれだけ確実に_ 到達するかを決めるのは、その対象ではなく文言である。必須の対象が弱い文言のポインタの裏にあるのは、ばらつきのバグである: まず文言を直し、研ぎ澄ましても失敗する場合にのみ、その資料をインライン化する。

_避ける表現_: link, reference, import

### Context Load(コンテキスト負荷)

**モデル呼び出し型** のスキルがエージェントのコンテキストウィンドウに課すコスト — その **description** は常に読み込まれ、トークンと注意の両方を消費する。**ユーザー呼び出し型** のスキルが description を持たないことで免れるものであり、モデル呼び出し型のスキルをさらに分割することへのブレーキとなる。

_避ける表現_: token cost, context bloat

### Cognitive Load(認知負荷)

**ユーザー呼び出し型** のスキルが人間に課すコスト — 人間が頭の中に保持しなければならないもの: どのスキルが存在し、いつそれぞれに手を伸ばすべきか(人間自身が索引となる)。**モデル呼び出し型** が、エージェントによる発見可能性によって取り除くものであり、ユーザー呼び出し型のスキルをさらに分割することへのブレーキとなる。最小化すべきコストではない: それは人間の主体性の対価であり、一部のスキルがユーザー呼び出し型のままである理由である。人間の判断が重要な場所ではそれを費やし、そうでない場所では取り除く。

_避ける表現_: human index, burden, overhead

### Router Skill(ルータースキル)

他のユーザー呼び出し型のスキルを指し示す役目を持つ **ユーザー呼び出し型** のスキル — それぞれを名指しし、いつそれに手を伸ばすべきかを示すことで、人間が多くのスキルではなく1つのスキルを覚えていればよいようにする。ヒントを与えることしかできず、それらを発火させることは決してできない: ユーザー呼び出し型のスキルには **description** がないので、人間以外の何もそれらに到達できない。ユーザー呼び出し型のスキルが増えすぎたときの、**cognitive load(認知負荷)** の治療法。

_避ける表現_: dispatcher, menu, registry, index, router procedure

### Granularity(粒度)

スキルをどれだけ細かく分けるか。より細かい分割は、2種類の負荷のどちらかを消費する: より多くの **モデル呼び出し型** のスキルは **context load(コンテキスト負荷)** を消費する(より多くの description がウィンドウに詰め込まれ、注意を奪い合う)。より多くの **ユーザー呼び出し型** のスキルは **cognitive load(認知負荷)** を消費する(人間が覚えて手を伸ばすべきものが増える)。2つの切り口がこの分割を導く。**呼び出し方式** による切り口では、それを引き起こす明確な **leading word(先導語)** — 実際にプロンプトの中で使うトリガーの言葉 — があるときに、モデル呼び出し型のスキルを切り出す。**手順** による切り口では、あるステップの **post-completion steps(完了後のステップ)** を隠す必要があるときに、一連の **steps(ステップ)** を分割する。それを独自のコンテキストに隔離すると、その先が見えなくなるからである。逆のケースにも注意する: 手順を統合すると、各ステップの完了後のステップがその先に露出し、早すぎる完了を誘発してしまう。

_避ける表現_: chunking, modularity

## Information Hierarchy(情報階層)

スキルの内容がどう配置されるか、そして各部分がその階段のどれだけ下に位置するか。

### Information Hierarchy(情報階層)

エージェントがどれだけ即座にそれを必要とするかによって順位付けされたスキルの内容 — ファイル内かポインタの裏か、ステップかリファレンスかという2つの切り口によって生まれる、単一の階段。その段は:

- **Steps(ステップ)** — ファイル内、最優先
- **Reference(リファレンス)**、ファイル内 — 次点
- **Reference(リファレンス)**、開示された — **context pointer(コンテキストポインタ)** の裏

**steps(ステップ)** を持たないスキルは、下の2段だけを使う — しばしば正当にフラットな並列集合である(例えば、あるレビューのすべてのルールが1段に並ぶ)。これは良い配置であり、悪い兆候ではない。この階層は呼び出し方式とは独立している: スキルはすべてステップでも、すべてリファレンスでも、両方でも、モデル呼び出し型でもユーザー呼び出し型でもありうる。スキルがステップを持つとき、開示すべきファイル内リファレンスがそれを埋もれさせ、それに注意を払うかどうかがコイントスになってしまう — これは読みやすさだけでなく、ばらつきのレバーでもある。階段の上部は読みやすく保ち、押し下げられるものはすべて押し下げる。

_避ける表現_: structure, organization, layout

### Steps(ステップ)

エージェントが実行する順序立った行動 — スキルがそれを持つ場合、その内容の最優先の層であり、SKILL.md にその居場所を得る部分。すべてのスキルがステップを持つわけではない: スキルはすべてステップ(`tdd`)でも、すべて **reference(リファレンス)**(あるレビュー)でも、両方でも、呼び出し方式とは独立にありうる。すべてのステップは、明確であれ曖昧であれ、**completion criterion(完了基準)** で終わる。

_避ける表現_: workflow, instructions, choreography

### Reference(リファレンス)

エージェントが必要に応じて参照する資料 — 定義、事実、パラメータ、例、条件付きの指示。スキルが **steps(ステップ)** を持つ場合、それに対して二次的なものである。持たない場合は、それが内容のすべてである。あるいは、どのスキルの外にも存在する — **External Reference(外部リファレンス)** を参照。**context pointer(コンテキストポインタ)** を通じて到達し、**progressive disclosure(段階的開示)** の第一候補である。コードの形をしていても、読ませるつもりで同梱されたものはリファレンスである — **executable(実行可能物)** を参照。

_避ける表現_: supporting material, docs, background

### External Reference(外部リファレンス)

スキルシステムの外に存在する **reference(リファレンス)** — description も steps もなく、呼び出せない、ただのファイル — であり、どのスキルもそれを指し示せる。単独では発火する必要のない共有リファレンスの置き場所であり、2つの **ユーザー呼び出し型** のスキルが使える唯一の共有の置き場所でもある。どちらも description を持たないので、互いを発火させられないからである。

_避ける表現_: doc, resource, knowledge base

### Executable(実行可能物)

スキルのフォルダに同梱され、エージェントが **実行する** スクリプト — 手続きを散文で記述する代わりに、その手続きそのものを置いたもの。**steps(ステップ)** と **reference(リファレンス)** に並ぶ第3のコンテンツの種類だが、**information hierarchy(情報階層)** の階段には段を持たない: 階段に乗るのはそれを呼ぶ **context pointer(コンテキストポインタ)** の1行だけで、コードの中身は実行されるかぎり一度もコンテキストに入らない。2つの利点がある。**決定的である** — 実行のたびに書き直される散文の手続きはそのたびにぶれるが、スクリプトは同じ答えを返すので **predictability(予測可能性)** に直接効く。**安い** — 手続きをトークン生成で近似するのは、それを1本走らせるより高い。判定基準は、エージェントが毎回ほぼ同じコードを書いているかどうかである。読ませるつもりで同梱したもの(写して埋めるひな形、やり方を示す作例)は実行可能物ではなく、コードの形をした **reference(リファレンス)** であり、どちらを意図しているかを決めるのは対象ではなくポインタの文言である。**guarantee(保証)** とは区別される: 保証はハーネスが実行するのでエージェントの注意を通らず、実行可能物はエージェントが実行するのでポインタを通る。

_避ける表現_: script, tool, helper, utility

### Progressive Disclosure(段階的開示)

**reference(リファレンス)** を階段の下へ — SKILL.md の外、**context pointer(コンテキストポインタ)** の裏へ — 動かすことで、上部を読みやすく保つこと。主にトークンの最適化ではなく、**information hierarchy(情報階層)** を守る手段である。**branching(分岐)** によって認められる: 一部の分岐だけが必要とするものは開示し、すべての経路が必要とするものはインラインにする。必須の資料に対してポインタが不確実にしか発火しないなら、まずその文言を研ぎ澄まし、それでも失敗する場合にのみインラインに戻す。

_避ける表現_: lazy loading, chunking

### Co-location(併置)

エージェントが同時に必要とする資料を1か所にまとめておくこと — ある概念の定義、ルール、注意点をファイル中に散らばらせるのではなく、1つの見出しの下にまとめる — こうすることで、一部を読むとその隣接部分もついてくる。**Information Hierarchy(情報階層)** のファイル内での相棒: 階層はある部分が _どれだけ下に_ 位置するかを順位付けし、併置はそこに来たときに _何が隣にあるか_ を決める。**reference(リファレンス)** のまとまりの正しい形式に公式はない。判定基準は、スキルがエージェント向けに書かれたドキュメントのように読めるべきだということであり、まとめられた資料はそう読めるが、散らばった資料はそう読めない。**Duplication(重複)** とは区別される: 重複は1つの意味を2か所で繰り返すが、散らばりは1つの意味を多くの場所へ断片化する。

_避ける表現_: grouping, clustering, cohesion

### Sprawl(肥大化)

_failure mode(失敗モード)。_ 単純に長すぎるスキル — SKILL.md の行数が多すぎる — 古びているか繰り返されているかとは無関係に。すべてが有効で、すべてが一意であるスキルでも肥大化しうる。これは読みやすさ(エージェントは行動を起こす前により多くをかき分けねばならず、余剰の中で注意が薄まる)、保守性(余分な行1つ1つが、**relevance(関連性)** を保つべき対象を1つ増やす)、トークンにコストがかかる。治療法は **information hierarchy(情報階層)** である: **reference(リファレンス)** を **context pointer(コンテキストポインタ)** の裏に押し下げ、**branch(分岐)** や手順で分割し、各経路が必要なものだけを運ぶようにする。**sediment(堆積物)**(古びた蓄積による長さ)や **duplication(重複)**(繰り返された意味による長さ)とは区別される — 肥大化とは、原因が何であれ、長さそのものである。

_避ける表現_: bloat, length, size, verbosity

## Steering(操舵)

エージェントの実行時の振る舞いを **Predictability(予測可能性)** へと形作るレバー。

### Branch(分岐)

スキルが呼び出されうる明確な方法 — スキルが扱うケース — であり、異なる実行がそれを通って異なる経路を取る。多くのステップを持つスキルは多くの分岐を持つかもしれない。直線的なスキルは分岐を持たない。

_避ける表現_: path, case, fork

### Leading Word(先導語)

モデルの事前学習にすでに存在する、コンパクトな概念(_Leitwort_ とも呼ばれる)で、エージェントがそのスキルを実行しながらそれで考える言葉。モデルがすでに持っている先行知識を呼び起こすことで、できるだけ少ないトークンで振る舞いの原則を符号化する(例: _lesson_、_proximal zone of development_、_fog of war_、_tracer bullets_)。文ではなく1つのトークンとして繰り返されることで、スキル全体にわたって分散した定義を積み重ね、振る舞いのある領域全体を1つに束ねる。自分で言葉を作っても、明確に定義すればうまくいくが、作り出した言葉は先行知識を何も呼び起こさない — 事前学習済みの言葉がただで与えてくれるものを、定義のためのトークンで支払うことになる。まずは既存の言葉に手を伸ばす。

先導語は **predictability(予測可能性)** に二重に貢献する。本文の中では **execution(実行)** を束ねる — その概念が現れるたびに、エージェントは同じ振る舞いに手を伸ばす。そしてフラットなリファレンスの中では、探すべき対象のクラスに注意を集中させ、毎回正しいチェックを呼び起こす。**description** の中では **invocation(呼び出し)** を束ねる — スキルの中だけではない: 同じ言葉があなたのプロンプト、ドキュメント、コードベースに存在するとき、エージェントはその共有された言語をそのスキルに結びつけ、より確実に発火させる。そのスキルを使いたいときに実際に使う先導語で、description を組み立てる。

_避ける表現_: keyword, term, motif

### Completion Criterion(完了基準)

ある単位の作業が完了したことをエージェントに伝える条件 — それが照らし合わせて判断する目標。これがただの性質ではなくレバーであるゆえんは、2つの性質にある。その **明確さ**(エージェントは完了と未完了を見分けられるか?)は **premature completion(早すぎる完了)** に抵抗する — 曖昧な境界(「理解に達した」)は、エージェントに完了を宣言させて次のステップへ滑り込ませてしまう。この軸が効くには _ステップ_ が必要である。早すぎる完了はステップ間の失敗だからである。その **要求度**(どれだけを要求するか)は **legwork(実作業)** を決める — 「変更されたすべてのモデルを漏れなく確認する」は「変更リストを作る」よりも徹底した作業を強いる — そしてこの軸はステップに縛られ _ない_ : フラットなリファレンスのまとまりにも作用しうる。これが、ステップを持たないスキルでも網羅性の基準(「すべてのルールを適用する」)を保持できる理由である。最も強い基準は、確認可能かつ網羅的であるものの両方を満たす。

_避ける表現_: done condition, exit condition, stopping rule

### Legwork(実作業)

エージェントが1つのステップの中で舞台裏で行う作業 — ファイルを読み、コードベースを探索し、変更を加え、ユーザーに丸投げするのではなく必要なものを自分で掘り出すこと。それはステップ構造の下に存在する: 決してそれ自体のステップとして書かれず、文言の中に潜在し、スキルではなくエージェントによって制御される。**post-completion steps(完了後のステップ)** のステップをまたぐ牽引力に対する、ステップ内での相棒。**leading word(先導語)**(_comprehensive_、_thorough_)や、作業が網羅的であることを求める **completion criterion(完了基準)** によって引き上げられる — フラットなリファレンスに適用される要求度の軸も含み、それがフラットなリファレンスのスキルにそのすべての段をカバーさせる原動力となる。その要求が欠けているとき、あるいは **premature completion(早すぎる完了)** がステップを短く切り上げてしまうときに、薄くなる。

_避ける表現_: scope, effort, diligence, coverage

### Post-Completion Steps(完了後のステップ)

現在のステップに続く **steps(ステップ)**。それが見えていると、エージェントを **premature completion(早すぎる完了)** へと前のめりに引っ張る — 見える量が多いほど、その引力は強くなる。防御策は、一連のステップを2つに分割することでそれらを隠すことである。

_避ける表現_: horizon, fog of war, lookahead

### Premature Completion(早すぎる完了)

_failure mode(失敗モード)。_ エージェントの注意が作業そのものではなく完了することへ滑ってしまうために、現在のステップを本当に終わる前に終えてしまうこと。ステップ間の失敗である: これが起きるには **steps(ステップ)** が必要である。ステップを持たないスキルが早く切り上げるのは、早すぎる完了ではなく、満たされない要求の下での薄い **legwork(実作業)** である。2つの力の綱引きである: 目に見える **post-completion steps(完了後のステップ)**(前へ引く力)と、**completion criterion(完了基準)** の明確さ(抵抗する力 — 鋭く確認可能な基準は持ちこたえ、曖昧な基準は屈する)。曖昧さがその必要条件である: 鋭い境界は、後続のステップがどれだけ見えていてもその引力に抵抗する。だから、決して急がないステップには防御は要らない。急いでしまうステップを支える2つのレバーがあるが、順番に手を伸ばす: **まず境界を研ぎ澄ます** — これは局所的で安価である。基準がどうしても曖昧であり、かつ実際に急いでいる様子が観察されたときにのみ、**後のステップを隠す** — そして隠すことが効くのは、本物のコンテキスト境界をまたぐ場合だけである(ユーザー呼び出し型への引き継ぎや、サブエージェントへのディスパッチ。インラインのモデル呼び出し型の呼び出しは、後のステップをコンテキストに残したままで、何もクリアしない)。薄い実作業の原因の1つではあるが、それとは区別される: ステップが完全に完了しても、実作業が薄いままということはありうる。

_避ける表現_: premature closure, the rush, rushing, shortcutting

### Negation(否定形)

_failure mode(失敗モード)。_ 禁止によって操舵すること — エージェントに _何をしてはいけないか_ を伝えること — は、その禁じられた振る舞いをコンテキストに引きずり込み、それを少なくするどころか _より_ 呼び出しやすくしてしまう。_象のことを考えるな_ と言われれば、象しか頭に浮かばない。_冗長なコメントを決して書くな_ と言われれば、冗長さこそがエージェントがたった今読んだパターンである。否定形は弱い修飾語であり、強く活性化された概念に押し流されてしまうので、その禁止は半分、そのことをしろという指示のように読まれてしまう。その **leading word(先導語)** は _象_ である: 禁止が何であれフレームの中に持ち込んでしまうもの。治療法: **肯定形** で促す — 目指す振る舞いを記述し(「1行のコメントを書く」)、禁じられたものが決して語られないようにする。禁止が居場所を得るのは、肯定形で言い表せない振る舞いに対する固いガードレールとしてだけである。それでも、注意が「何をすべきか」に向かうよう、肯定形の目標と対にする。

_避ける表現_: ironic rebound, don't-prompting, the pink elephant

### Guarantee(保証)

ハーネス自身が実行することで、エージェントの注意を通らずに成り立つ振る舞い — スキルの散文がエージェントの注意を通ってしか効かないのに対して。フック(編集の後、コミットの前、ターンを終える前に走るスクリプト)がその形をしている。散文は勧告であり、大抵は守られる。保証は決定的であり、必ず守られる。判定基準は **毎回、例外なく** 成り立つ必要があるかどうかであり、そうであるものはスキルの行ではなくフックに属する。**no-op(ノーオプ)** の第2の処方でもある: デフォルトで守られている行は削除し、守られなければ困るのに散文では守りきれない行は保証へ移す — 行はスキルから消えるが、振る舞いは残る。**completion criterion(完了基準)** とは区別される: 完了基準はエージェントに自分で判定させ、保証はエージェントに判定させない。

_避ける表現_: hook, enforcement, automation

## Pruning(刈り込み)

スキルを引き締まった状態に保つこと — それぞれの治療法は、それが直す失敗と対になっている。

### Single Source of Truth(唯一の信頼できる情報源)

各意味がちょうど1つの権威ある場所に存在し、スキルの振る舞いへの変更が1か所の編集で済むという、望ましい状態。**Duplication(重複)** はその違反である。

_避ける表現_: home, canonical location

### Duplication(重複)

_failure mode(失敗モード)。_ 同じ意味が複数の **single source of truth(唯一の信頼できる情報源)** を与えられている状態。保守のコストがかかり(1か所を変えたら、他も変えなければならない)、トークンのコストがかかり、目立ちすぎるようになる — ある意味を繰り返すと、その本来の順位を超えて階段上での重みが増してしまう。これは **leading word(先導語)** の偶発的な逆パターンである。先導語は1つのトークンを繰り返すことで、意味ではなく意図的に注意を引き上げる。

_避ける表現_: repetition, redundancy

### Relevance(関連性)

ある行が、いまだにそのスキルの動作に関わっているかどうか — 何を残すかを判断するレンズ。ある行が関連性を失うのは、そもそもタスクに関わっていなかったか(単なる説明、あるいは開示すべき **branch(分岐)**)、あるいは古びていったか(それが記述する振る舞いや世界が変わるにつれて、時代遅れになっていく)のいずれかである。短いスキルほど関連性を保ちやすい。各行を確認するコストが低いからである。**no-op(ノーオプ)** とは区別される: 関連性は、ある行がタスクに関わっているかを問うのであって、振る舞いを変えるかどうかを問うのではない。

_避ける表現_: load-bearing, staleness, freshness

### Sediment(堆積物)

_failure mode(失敗モード)。_ 追加することは安全に感じられ、削除することはリスクに感じられるために、スキルの中に積み重なって決して片付けられない古いコンテンツの層 — こうして古びた無関係な行が蓄積し、まだ有効なものを見つけるにはそれらを掘り下げなければならなくなる。刈り込みの規律を持たないあらゆるスキルの、既定の末路。**duplication(重複)** の繰り返された意味とは対照的な、**relevance(関連性)** のゆっくりとした侵食である。

_避ける表現_: accretion, bloat, cruft, rot

### No-Op(ノーオプ)

_failure mode(失敗モード)。_ モデルがデフォルトですでにそうしているために、何も変えない指示 — エージェントがどのみちやることを伝えるために、負荷を支払っている。判定基準: その行はデフォルトと比べて振る舞いを変えるか? ある行は完全に **relevant(関連性がある)** でありながら、それでもノーオプでありうる。**leading word(先導語)** を無料にする先行知識と同じものが、ノーオプを無価値にする。処方は2つある: 削除するか、**guarantee(保証)** へ移すか。

先導語は _技法_ であり、ノーオプはある行に対する _判定_ である — そして両者は交差する。デフォルトに勝てないほど弱い先導語はノーオプである(エージェントがすでにある程度徹底しているときの _be thorough_)。その修正は、その判定を通過するより強い言葉(_relentless_)であって、別の技法ではない。だから、ノーオプの判定基準 — デフォルトと比べて振る舞いを変えるか? — は、ある先導語がその繰り返しに見合っているかどうかを評価する方法でもある。これはモデル相対的であり、読み手相対的ではない: ある行がノーオプかどうかで2人の意見が割れるのは、デフォルトについて意見が割れているのであり、それは議論ではなく、そのスキルを実行してみることで決着する。

モデル相対的であるということは、**ノーオプはモデルが上がるたびに新しく生まれる** ということでもある — 書かれた時点では振る舞いを変えていた行が、次のモデルではデフォルトに追い越される。最も追い越されやすい層は、自己検証と自己修正の指示である(「答えを再確認する」「自明でないタスクには最終検証ステップを含める」「サブエージェントに検証させる」)。これらは、モデルがすでにそうするようになった時点でノーオプに変わるだけでなく、過剰な検証を招いて重ねた分以上のコストを生む。**verification gate(検証ゲート)** — 二値の合否が出るコマンド — とは区別される: ゲートはモデルのデフォルトではなくリポジトリの契約なので、モデルが上がっても追い越されない。乗り換えのたびに、この層を狩り直す。

_避ける表現_: redundant instruction, restating the obvious, belaboring
