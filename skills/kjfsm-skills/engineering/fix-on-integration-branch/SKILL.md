# 一覧を統合ブランチで直す

役は2つある。**実装役**(`fix-implementer`)は PR を1本作る。**まとめ役**(このスキルを読んでいる側)は割り方を決め、**関門** — 差分を読み、統合ブランチに重ねて検証し、入れる — を1本ずつ持つ。実装は並列、関門は直列である。

既定ブランチへは入れない。人が読むのは最後の1本で、そこに「自分で決めたこと」と「テストで確かめられないこと」が全部載っている — それがこの進行の成果物である。

項目が数件ならここは要らない(そのまま直す)。設計から決め直す項目は割り当てに入れず、イシューにして `launch-implementation-session` スキルへ回す。一覧がまだ無いなら、先に `review-codebase` スキルである。

## 手順1 — 始める前に、決めてもらう

始めたら最後まで止まらないので、ユーザーに聞けるのはここだけである。既に言われているものは聞かない。残りを1回でまとめて聞き、答えを待つ。

- **直す項目と、触らない項目**(一覧の ID で)
- **統合ブランチへのマージを、まとめ役がしてよいか。** これがこの進行の前提である。許可が無ければ始めず、項目ごとに `launch-implementation-session` で進める形を提案する
- **迷ったときに、まとめ役が決めてよいか。** よいなら、決めたことの一覧が報告の中心になる。だめなら、迷った項目は直さずに残す
- 統合ブランチの名前(既にあるものを使うのか、新しく切るのか)

次のものは、ユーザーが名指しで入れない限り割り当てから外し、最後の報告に並べる: スキーマ変更やマイグレーションが要る項目、記録された設計判断を覆す項目、本番のデータを見ないと直し方が決まらない項目。本番のデータは、読み取りであっても許可の後にだけ見る。

完了: 直す ID・触らない ID・統合ブランチの名前が決まり、マージと判断の許可について答えがある。

## 手順2 — 台帳を置く

作業ツリーの外(`mktemp -d`)に台帳ファイルを1つ置き、状態が変わるたびに書き換える。**文脈が要約されたら、まず台帳を読む** — 長い進行では何度か要約が入り、順番と「自分で決めたこと」はそこにしか残らない。

```markdown
# 台帳

依頼: <統合ブランチ、許可されたこと、同時に走らせる数、止まる地点>

## 済み

- #<PR> <題>(<ID の列>)— マージ済み <SHA>
  - 報告に書く: <自分で決めたこと・戻す単位・テストで確かめていない変更・書いた文言>

## 実行中

- <ブランチ名>(<モデル>)<ID の列>

## これから(順)

## 触らない

## 最後の報告に書くこと
```

## 手順3 — 統合ブランチを切り、PR に割る

`git fetch` し、最新の `origin/<既定ブランチ>` から統合ブランチを切って push する。

PR は **重さや区分ではなく、触るファイルの重なり** で割る。

- 同じファイルを触る項目は、同じ PR に寄せる
- それでも重なる PR は順番を決めて直列にし、前の PR が統合ブランチに入ってから次を切らせる。`gh-stack` で積まない — ここの PR は統合ブランチに入った時点で役目を終え、層として残して人が読むものではない
- 多くのファイルに薄く触る項目(コメントや文書の直し、重複の共通化)は最後の PR に回す
- PR ごとに **触らないファイル** — 同時に走る別の PR が触るもの — を書き出す

一覧に `probes/`(再現に使った一時テスト)が付いていれば、項目ごとに対応するファイルを控える。実装役の赤いテストの元になる。

完了: 直す項目のすべてがちょうど1本の PR に入り、同時に走らせる PR 同士は触るファイルが重ならず、割り当てと順番が台帳にある。

## 手順4 — 実装役を立てる

**`fix-implementer` サブエージェントを、PR ごとに worktree を隔離して起動する。** 手順・約束・最終報告の形はそちらが1部だけ持つ — **ここには写さない。**

渡すのは、その PR でしか決まらないものだけである: 統合ブランチの名前、作るブランチの名前、項目(ID、`file:line`、起きること、直し方の案、再現テストの元のパス)、触らないファイル、先に読む文書、絞った検証のコマンド。

- **同時に走らせるのは2体まで。** 実装役ごとに依存の実体とテストのプロセスを持つので、増やすとメモリが尽きる。関門の検証もその横で走る
- **モデル** — 画面・解析・スクリプトだけの PR は Sonnet に下げる。サーバー、状態を持つもの、並行、設計の判断を含む PR は既定のままにする
- **実装役を途中で止めると、worktree ごと作業が消え、push 済みのブランチだけが残る。** 使用量の上限などで止めるなら、先に途中を push させるか、やり直す前提で止めて台帳に「出し直し」と書く

完了: 起動のたびに、台帳の「実行中」にブランチ名・モデル・ID がある。

## 手順5 — 関門: 読んで、重ねて、検証して、入れる

実装役が PR を返すたびに、**1本ずつ、順番に** 通す。2本を同時に検証して入れると、どちらが統合ブランチを壊したのか分からなくなる。

1. **差分を読む**(`gh pr diff <番号>`)。渡した項目とファイルの外に出ていないか、実装役の約束に反するものが無いかを見る。時間のしきい値で合否を決めるテストは通さず、挙動で言い直させる
2. **最新の統合ブランチに重ねる**

   ```bash
   git fetch origin
   git switch --detach origin/<統合ブランチ>
   git merge --no-ff --no-edit origin/<PR のブランチ>
   ```

3. **`verification-loop` スキルでクリーンランを取る。** 絞った検証ではなく、ゲートの全部である。実装役は自分の PR 単体でしか確かめていない
4. **緑なら入れる**

   ```bash
   gh pr merge <番号> --merge
   git push origin --delete <PR のブランチ>
   ```

   `--delete-branch` を付けないのは、detach 中だとローカルの後始末で落ち、マージは通っているのに失敗に見えるからである。

5. 台帳を書き換える: 「済み」へ移し、実装役の報告から **判断してほしい点・書いた文言・テストで確かめていない変更** を写す

赤のとき:

- **「不安定」で片付けて回し直さない。** 並走の負荷で初めて落ちるテストは、落ちた理由が本物のことがある。落ちたテストが言っていることを先に確かめる
- 直しが小さければ自分で PR のブランチに積み、そうでなければ同じ実装役へ、落ちたゲートと最初の失敗を添えて戻す。どちらでも 1. からやり直す

既定ブランチが進んでいたら(2. の `git fetch` で分かる)、統合ブランチへ取り込み、ゲートを通し直してから次の PR に進む。

最初の1本を入れたら、統合ブランチから既定ブランチへの PR を **draft で** 作り、以後は入れるたびに本文へ1行足す。途中で止まっても、どこまで進んだかがユーザーの見える場所に残る。

完了: 統合ブランチに入った PR のすべてについて、重ねた状態のクリーンランがあり、台帳の「済み」に報告へ書くことが写っている。

## 手順6 — 文書とコードの食い違いを決める

「文書はこう言い、コードとテストはこうしている」という項目は、どちらに合わせるかの判断を含む。直させる前に経緯を調べる — どのコミットで何が入り、何が残ったのか(`git log -S`、該当の PR とイシュー)。

経緯から答えが出て、ユーザーが判断を任せているなら決めて、台帳の「最後の報告に書くこと」に、決めた向き・根拠にしたコミットや文書・戻す単位を書く。出なければ直さずに残す。

## 手順7 — 最後の PR を仕上げて止まる

統合ブランチで `verification-loop` のクリーンランを取り直し、draft を外す。本文は `where-to-write-what` スキルで書き、台帳から次を載せる。

- **入れた PR を目的別に束ねたもの** — 番号順ではなく、何を直すための束かで
- **気をつけるところ**
  - テストで確かめられない変更と、既定ブランチへ入れる前に見る場所(本番のホスト構成に依る検査なら、プレビューで実際に通ることを見る、など)
  - **自分で決めたことの全部** — 決めた値や挙動、理由、戻す単位(PR かコミット)
  - 利用者の目に入る文言を足した・変えた箇所
- **直さなかった項目** — ID と理由(外した・実装役が直せなかった・判断がつかなかった)

**既定ブランチへはマージしない。** PR の番号と、上の3つをそのまま最後の報告にして止まる。残った項目を続けるかは、ユーザーが決める。

完了: 最後の PR の本文に、台帳の「最後の報告に書くこと」が1つ残らず載っている。
