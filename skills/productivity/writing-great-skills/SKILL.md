# 良いスキルを書く

スキルは、確率的なシステムから決定性を絞り出すために存在する。**予測可能性(Predictability)** — エージェントが毎回同じ出力を生むのではなく、毎回同じ _プロセス_ を取ること — が根本的な美徳であり、以下のすべてのレバーはそれに仕える。

このファイルが持つのは **判断** — 何を、どの順で決めるか — である。**太字の用語** の定義は [`GLOSSARY.md`](GLOSSARY.md)、公式が定める **数値上限・frontmatter の仕様・名指しのアンチパターン** は [`OFFICIAL.md`](OFFICIAL.md) にある。用語の意味が要るなら前者を、仕様を確定させるなら後者を開く。

**`OFFICIAL.md` の項目に従って設計や手順を決めるときは、その項目の引用元まで開く。** あそこの1〜2行は思い出すためのものであって、決めるためには足りない — 落ちているのは「いつ効かないか」「どの順で適用するか」であり、判断を左右するのはたいていそこである。

## 1. 呼び出し方式を決める

**モデル呼び出し型** と **ユーザー呼び出し型** は、異なる負荷を天秤にかける。モデル呼び出し型は **context load** を毎ターン支払い、その見返りにエージェントと他のスキルからの到達可能性を得る。ユーザー呼び出し型はそれをゼロにする代わりに **cognitive load** を消費する — それが存在することを覚えている索引は _あなた_ である。

判定: **エージェントが自力でそのスキルに到達しなければならないか、他のスキルが到達しなければならないか。** どちらでもなく、手で発火する以外に使われないなら、ユーザー呼び出し型にして負荷を支払わない。

ユーザー呼び出し型が覚えきれないほど増えたら、積み上がった認知負荷は **ルータースキル** で治療する。

## 2. description を書く

モデル呼び出し型の **description** は2つの仕事をする — そのスキルが何であるかを述べ、それを発火させるべき **分岐** を列挙する。すべての単語が context load を増やすので、本文よりさらに厳しい刈り込みに値する。

- **スキルの先導語を前面に出す。** description は、その呼び出しの仕事をする場所である。
- **分岐ごとに1つのトリガー。** 単一の分岐を言い換えただけの同義語は **重複** である — 「TDD で機能を構築する…テストファーストの開発を求める」は、1つの分岐が2度書かれたものである。畳み込み、本当に別個の分岐だけを残す。
- **すでに本文にある固有の説明は削る。** トリガーと、「他のスキルが…を必要とするとき」という到達節だけに留める。
- **2つの仕事は1つのフィールドに収める。** トリガーを別フィールドへ分けると、標準しか読まないハーネスで丸ごと落ちる。

ユーザー呼び出し型の description は宛先が **人間** に変わる — スラッシュコマンドの一覧を眺める人が読む1行。トリガーのリストは誰にも読まれないので取り除く。フィールド自体は消さない(標準の必須フィールドである)。

## 3. 中身をどこに置くか

**information hierarchy(情報階層)** は、エージェントがどれだけ即座にそれを必要とするかで順位付けされた1つの階段である。

1. **スキル内のステップ** — 何を、どの順で行うか。各ステップは **completion criterion(完了基準)** で終わる。
2. **スキル内のリファレンス** — 必要に応じて参照される定義・ルール・事実。
3. **開示されたリファレンス** — 別ファイルに押し出され、**context pointer** が発火したときだけ読まれる。

**押し下げが少なすぎると上部が肥大化し、押し下げすぎると必要な資料が隠れる。その緊張こそが決定のすべてである。** 判定は **分岐** が与える: すべての分岐が必要とするものはインラインにし、一部の分岐しか到達しないものはポインタの裏へ。ポインタの _文言_ が、その対象ではなく、いつ・どれだけ確実に到達するかを決める。

完了基準は2つの軸を持つ。**明確さ**(完了と未完了を見分けられるか)は **premature completion** に抵抗し、**要求度**(「変更リストを作る」ではなく「変更されたすべてのモデルを漏れなく確認する」)は **legwork** を駆動する。要求度はステップに縛られない — 「すべてのルールが適用された」がフラットなリファレンスを縛るのは、「すべてのステップが完了した」が手順を縛るのとまったく同じである。

同じ見出しの下に定義・ルール・注意点をまとめる(**co-location**)。一部を読めば隣接部分もついてくる。

## 4. いつ分割するか

**granularity(粒度)** の切り分けは、必ず2種類の負荷のどちらかを消費する。見合うときだけ分割する。2つの切り口:

- **呼び出し方式による分割** — それ自体を発火させるべき明確な **先導語** があるか、他のスキルが到達しなければならないとき。新しい description の context load に見合う到達可能性が要る。
- **手順による分割** — 先にあるステップ(**post-completion steps**)が目の前のステップを急がせる誘惑になるとき。視界から外すと legwork が増える。

## 5. 散文か、保証か

スキルの散文は勧告である — エージェントの注意を通って効くので、確率的に守られる。ハーネスのフックは **guarantee(保証)** である — ハーネスが実行するので、注意を通らない。

判定: それは **毎回、例外なく** 起きなければならないか? そうならフックであり、スキルの行ではない。

これで **no-op** の処方が2つになる。デフォルトで守られている行は **削除** する。守られなければ困るのに散文では守りきれない行は **フックへ移す** — 行はスキルから消えるが、振る舞いは残る。

フックより手前に、もう1段ある: frontmatter の `disallowed-tools` はツールをモデルの手札から外す。「ここでは実装しない」といった脱線の禁止は、散文で頼むよりこの1行の方が固い。ただし2つの制約がある。

- **ターン全体にかかる。** そのスキルを _呼ぶ側_ が外されたツールを必要とする場合は使えない。
- **次のユーザーメッセージで切れる。** `allowed-tools` の権限付与も同じで、**効くのは呼び出したその1ターンだけ** — 本文がコンテキストに残り続けるのとは寿命が違う。

2つ目が効くのは **対話を往復するスキル** である。ユーザーの返答を待つ設計(インタビュー、確認を挟む手順)では、最初の返答が来た時点でガードは消えている。往復のあいだ守りたいなら、これは保証ではない。

## 6. 散文か、コードか

**executable(実行可能物)** は、散文が苦手な2つの仕事を引き受ける。**決定的である** — 散文の手続きは実行のたびに書き直され、そのたびにぶれる。**安い** — 実行されたコードはコンテキストに一度も乗らない。

判定: エージェントが **毎回ほぼ同じコードを書いている** なら、それは同梱物になりたがっている。

同梱物の読まれ方は2つあり、どちらを意図しているかは **context pointer** の文言が決める。**実行させる**(「`${CLAUDE_SKILL_DIR}/scripts/check.sh` で差分を検査する」)が既定で、中身は読まれない。**読ませる**(写して埋めるひな形、やり方を示す作例)なら、それはコードの形をした **リファレンス** である。

パスは `${CLAUDE_SKILL_DIR}` で書く。`allowed-tools` に同じ文字列を書けば権限プロンプトなしで走る(→ `OFFICIAL.md` §2)。

## 7. 先導語へ畳み込む

**leading word(先導語)** とは、モデルの事前学習にすでに存在する、コンパクトな概念である(例: _lesson_、_fog of war_、_tracer bullets_)。予測可能性に二重に貢献する — 本文の中では _実行_ を束ね、description の中では _呼び出し_ を束ねる。

リファクタリングの機会を狩る。3か所で綴られた三つ組(**重複**)、1つの考えに1文を費やす description — それぞれが1つのトークンへ **畳み込まれる** ことを求めている。

- 「速く、決定的で、オーバーヘッドが低い」 → _tight_ — フェーズ全体で言い換えられていた1つの性質を、1つの事前学習済みの言葉へ。
- 「信頼できるループ」 → _red_ — 曖昧なゲートを、二値の観測可能な状態へ(そのループはバグに対して _red_ になるか、ならないか)。

すべてのスキルは、先導語が退役させられる言い換えを抱えていると想定する。

## 8. 刈り込む

各意味を **single source of truth** に保つ。1つの権威ある場所に置き、振る舞いの変更が1か所の編集で済むようにする。

すべての行に **relevance** を問う。それはいまだにそのスキルの動作に関わっているか?

それから、行単位ではなく **文単位** で **no-op** を狩る。各文を単独で取り出して判定し、失敗したら単語を削るのではなく文全体を削除する。積極的であること — 判定に失敗した散文のほとんどは、書き直すのではなく削除すべきである。

**長さそのものが上限を持つ。** 本文は500行以内、かつ5,000トークン以内(→ `OFFICIAL.md` §2)。日本語では行数より先にトークン側を踏む。しかも圧縮を挟むと、コンテキストに戻るのは **各スキルの先頭5,000トークンだけ** である — 超過分は消えるのではなく、_圧縮後に黙って消える_。効かせたい指示ほど前方に置く。

## 失敗モードから逆に診断する

ユーザーがそのスキルで抱えている問題は、たいていこのどれかである。定義は `GLOSSARY.md`、ここにあるのは治療法だけ。

| 症状                                 | 失敗モード               | 治療                                                                                                                                 |
| ------------------------------------ | ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| ステップを本当に終える前に切り上げる | **premature completion** | まず完了基準を研ぎ澄ます(安価で局所的)。どうしても曖昧で、実際に急いでいると観測できたときだけ、手順を分割して完了後のステップを隠す |
| 同じことが何度も書いてある           | **duplication**          | 1つの **single source of truth** へ畳む。**先導語** に畳み込めることが多い                                                           |
| 古い層が積み上がっている             | **sediment**             | **relevance** で1行ずつ問う                                                                                                          |
| 全部が有効なのに、単純に長い         | **sprawl**               | 階段を下げる — リファレンスをポインタの裏へ、分岐や手順で分割する                                                                    |
| 書いてあるのに何も変わらない         | **no-op**                | 削除するか、**保証** へ移す。弱い先導語(_be thorough_)はより強い言葉(_relentless_)へ                                                 |
| 禁止したのに、むしろやる             | **negation**             | **肯定形** で言い直す。禁止は肯定形にできないガードレールのときだけ残し、代わりの行動と対にする                                      |

**no-op はモデル相対的なので、モデルが上がるたびに新しく生まれる。** 真っ先に追い越されるのは自己検証と自己修正の指示である。乗り換えのたびに狩り直す。

## 走らせて測る

原則は下書きまでしか連れて行かない。そこから先は、代表的なタスクで実際に走らせ、どこで詰まるかを観測して直す。測るものは2つ、そして **直す対象が違う**:

- **invocation(呼び出し)** — 発火すべきときに発火し、そうでないとき黙っていたか。外れているなら直すのは **description** であり、本文をどれだけ磨いても動かない。
- **predictability(予測可能性)** — 何度走らせても同じ経路を取ったか。ばらけるなら直すのは **完了基準** の明確さか、**context pointer** の文言である。

どの行が **no-op** かで意見が割れたときも、決着をつけるのは議論ではなく実行である — 割れているのはその行についてではなく、モデルのデフォルトについてだからである。eval の回し方は `OFFICIAL.md` §8、ハーネスの `skill-creator` がその観測を回せる。
