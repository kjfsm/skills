# Diagnosing Bugs

手強いバグのための規律。フェーズを飛ばすのは明示的に正当化できる場合のみ。

コードベースを探索するときは、(存在すれば)`CONTEXT.md` を読んで関連するモジュールの明快なメンタルモデルを得て、触れている領域の ADR を確認する。

## 伏せ字にする

このスキルは、コマンド・出力・取得した成果物を見せることを要求する。**見せる前に、秘密はすべて伏せ字にする**: その場所に `<REDACTED>` と書く。ループは環境変数に対して組み、認証情報が見せるものの中ではなく環境の側に残るようにする。取得した成果物は認証ヘッダを抱えている — シグナルを運んでいる行だけを引用する。

伏せ字にした出力ではバグを診断できないなら、そう言ってユーザーに尋ねる。

## フェーズ1 — フィードバックループを構築する

**これがこのスキルの核心である。** 他はすべて機械的な作業にすぎない。そのバグに対する **タイトな** 合格/不合格のシグナル — _この_ バグでレッドになるもの — を持っていれば、原因は見つかる。二分探索、仮説検証、計測はすべてそれを消費するだけである。持っていなければ、どれだけコードを見つめても救われない。

ここに不釣り合いなほどの労力をかける。**攻撃的であれ。創造的であれ。決してあきらめるな。**

### 構築する方法 — おおよそこの順で試す

1. バグに届くどんなシームでもよいので、**失敗するテスト** — ユニット、統合、e2e。
2. 動いている開発サーバーに対する **curl / HTTP スクリプト**。
3. フィクスチャ入力を使った **CLI 呼び出し**。既知の正しいスナップショットと stdout を diff する。
4. **ヘッドレスブラウザスクリプト**(Playwright / Puppeteer) — UI を駆動し、DOM/コンソール/ネットワークに対してアサートする。
5. **記録済みトレースの再生。** 実際のネットワークリクエスト/ペイロード/イベントログをディスクに保存し、それを単体でコードパスに通して再生する。
6. **使い捨てのハーネス。** システムの最小限の部分集合(1つのサービス、モックされた依存)を立ち上げ、1回の関数呼び出しでバグのコードパスを実行する。
7. **プロパティ/ファズループ。** バグが「時々おかしな出力になる」というものなら、1000個のランダムな入力を実行し、失敗モードを探す。
8. **二分探索ハーネス。** バグが2つの既知の状態(コミット、データセット、バージョン)の間に現れたなら、「状態 X で起動、確認、繰り返し」を自動化し、`git bisect run` にかけられるようにする。
9. **差分ループ。** 同じ入力を旧バージョンと新バージョン(または2つの設定)の両方に通し、出力を diff する。
10. **HITL bash スクリプト。** 最後の手段。人間がクリックしなければならないなら、`${CLAUDE_SKILL_DIR}/scripts/hitl-loop.template.sh` を **写して手順を埋め**、そのスクリプトでその人間 _を_ 駆動し、ループが構造化されたままにする。取得された出力があなたにフィードバックされる。

正しいフィードバックループを構築すれば、バグは9割直ったも同然である。

### ループを締め上げる

ループを1つの製品として扱う。 _ある_ ループができたら、それを **締め上げる**:

- もっと速くできないか?(セットアップをキャッシュする、無関係な初期化をスキップする、テストの範囲を狭める)
- シグナルをもっと鋭くできないか?(「クラッシュしなかった」ではなく、特定の症状に対してアサートする)
- もっと決定的にできないか?(時刻を固定する、乱数を種で固定する、ファイルシステムを隔離する、ネットワークを凍結する)

30秒かかるフレーキーなループは、ループがないのとほとんど変わらない。2秒で決定的なループはタイトである — デバッグの必殺技である。

### 非決定的なバグ

目標はきれいな再現ではなく、**より高い再現率** である。トリガーを100回ループさせる、並列化する、負荷をかける、タイミングウィンドウを狭める、sleep を注入する。50%でフレークするバグはデバッグ可能だが、1%はそうではない — デバッグ可能になるまで率を上げ続ける。

### 本当にループを構築できないとき

立ち止まり、それを明示的に伝える。試したことを列挙する。ユーザーに次を求める: (a) それが再現する環境へのアクセス、(b) 伏せ字にした取得済みの成果物(HAR ファイル、ログのダンプ、コアダンプ、タイムスタンプ付きの画面録画)、または (c) 一時的な本番計測を追加する許可。ループなしで仮説立てに進んでは **ならない**。

### 完了基準 — レッドになるタイトなループ

フェーズ1が完了するのは、ループが **タイト** かつ **レッドになれる** ときである: **1つのコマンド** — スクリプトのパス、テストの呼び出し、curl など — を名指しでき、それを **すでに少なくとも一度実行しており**(その呼び出しと出力を、伏せ字にしたうえで見せる)、それが次を満たすとき:

- [ ] **レッドになれる** — 実際のバグのコードパスを駆動し、**ユーザーの正確な症状** に対してアサートするので、このバグでレッドになり、直ればグリーンになれる。「エラーなく動く」ではなく、_この特定のバグを捕まえられる_ ものでなければならない。
- [ ] **決定的である** — 毎回同じ判定になる(フレーキーなバグの場合は、上記の通り固定された高い再現率)。
- [ ] **速い** — 分ではなく秒。
- [ ] **エージェントが実行できる** — 見守りなしで実行できる。ループの中の人間は `hitl-loop.template.sh` を通してのみ。

このコマンドができる前にコードを読んで理論を組み立てようとしていることに気づいたら、**止まること — 仮説にいきなり飛びつくことこそ、このスキルが防ごうとしている失敗そのものである。** レッドになれるコマンドなくして、フェーズ2なし。

## フェーズ2 — 再現+最小化

ループを実行する。レッドになるのを見届ける — バグが現れる。

確認する:

- [ ] ループが生み出す失敗モードは、**ユーザー** が説明したものであること — たまたま近くにある別の失敗ではない。バグを取り違えれば、直す対象も間違う。
- [ ] その失敗は複数回の実行で再現可能であること(非決定的なバグの場合は、それに対してデバッグできる十分に高い率で再現可能であること)。
- [ ] 正確な症状(エラーメッセージ、誤った出力、遅いタイミング)を取得済みであること。後のフェーズで、修正が実際にそれに対応しているか検証できるように。

### 最小化する

レッドになったら、再現手順を **それでもレッドになる最小のシナリオ** まで縮める。入力、呼び出し元、設定、データ、手順を **1つずつ** 削り、削るたびにループを再実行する — 失敗にとって本質的なものだけを残す。

なぜそうするのか: 最小の再現手順は、フェーズ3の仮説空間を縮め(疑うべき可動部分が減る)、フェーズ5でそのままきれいなリグレッションテストになる。

**残っているすべての要素が本質的である**とき完了である — どれか1つでも取り除くとループがグリーンになる状態。

再現 **かつ** 最小化が終わるまで先に進まない。

## フェーズ3 — 仮説を立てる

どれかをテストする前に、**3〜5個の順位付けされた仮説** を生成する。単一の仮説だけを生成すると、最初にもっともらしく見えたアイデアに引きずられる。

各仮説は **反証可能** でなければならない: それが立てる予測を述べる。

> フォーマット:「もし <X> が原因なら、<Y を変えると> バグは消えるはずだ/<Z を変えると> 悪化するはずだ。」

その予測を述べられないなら、その仮説は単なる勘にすぎない — 捨てるか、研ぎ澄ます。

**テストする前に、その順位付けされたリストをユーザーに見せる。** ユーザーはしばしば、それを瞬時に並べ替えるドメイン知識を持っている(「#3 にはついさっき変更をデプロイしたばかりだ」)、あるいはすでに除外済みの仮説を知っている。安価なチェックポイントで、大きな時間の節約になる。これに阻まれてはいけない — ユーザーが離席中なら、自分の順位付けのまま進める。

## フェーズ4 — 計測する

各プローブは、フェーズ3の具体的な予測に対応していなければならない。**一度に1つの変数だけを変える。**

ツールの優先順位:

1. 環境が対応していれば **デバッガ/REPL による調査**。1つのブレークポイントは10個のログに勝る。
2. 仮説を切り分ける境界に置く **狙いを定めたログ**。
3. 「すべてをログに出して grep する」は絶対にしない。

**すべてのデバッグログに** ユニークな接頭辞、例えば `[DEBUG-a4f2]` を **タグ付けする**。最後の後片付けが1回の grep で済むようになる。タグのないログは生き残り、タグ付きのログは消える。

**パフォーマンス分岐。** パフォーマンスのリグレッションでは、ログは大抵あてにならない。代わりに: ベースラインの計測(計測用ハーネス、`performance.now()`、プロファイラ、クエリプラン)を確立し、それから二分探索する。まず計測し、それから直す。

## フェーズ5 — 修正+リグレッションテスト

**正しいシーム** がある場合に限り、修正の **前に** リグレッションテストを書く。

正しいシームとは、呼び出し箇所で実際に起きる **本物のバグのパターン** をテストが行使できるシームのことである。使えるシームが浅すぎる場合(バグが複数の呼び出し元を必要とするのに単一の呼び出し元のテストしかない、バグを引き起こした連鎖を再現できないユニットテストしかない)、そこでのリグレッションテストは誤った安心感を与えてしまう。

**正しいシームが存在しないなら、それ自体が発見である。** それを書き留める。コードベースのアーキテクチャが、このバグを封じ込めることを妨げている。これを次のフェーズに向けて指摘する。

正しいシームが存在する場合:

1. 最小化した再現手順を、そのシームでの失敗するテストに変える。
2. それが失敗するのを見届ける。
3. 修正を適用する。
4. それが通るのを見届ける。
5. 元の(最小化していない)シナリオに対してフェーズ1のフィードバックループを再実行する。

## フェーズ6 — 後片付け+事後検証

完了を宣言する前に必要なこと:

- [ ] 元の再現手順がもう再現しない(フェーズ1のループを再実行する)
- [ ] リグレッションテストが通る(またはシームがないことが文書化されている)
- [ ] すべての `[DEBUG-...]` 計測が取り除かれている(接頭辞を `grep` する)
- [ ] 使い捨てのプロトタイプが削除されている(または、明確にマークされたデバッグ用の場所に移されている)
- [ ] 正しいとわかった仮説がコミット/PR のメッセージに書かれている — 次にデバッグする人が学べるように

**そして問う: 何があればこのバグを防げたか?** 答えがアーキテクチャ上の変更(良いテストシームがない、絡み合った呼び出し元、隠れた結合)を含むなら、具体的な内容とともに `/improve-codebase-architecture` スキルに引き継ぐ。この提言は修正が入った **後** に行うこと。始めたときよりも今の方が多くの情報を持っている。
