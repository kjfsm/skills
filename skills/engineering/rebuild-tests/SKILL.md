# テストスイートを立て直す

`tdd` が「1 本のテストをどう書くか」なら、こちらは「すでにあるスイート全体をどう建て直すか」である。既存のスイートが重い・複雑・信用できないと感じたとき、直すべき対象がテストとは限らない — 多くの場合、テストの歪みはプロダクションコードの設計が漏れ出したものである。

## 設定の複雑さは症状であって病気ではない

テストランナーの設定が肥大していたら、まず **なぜプロジェクトが分かれているのか** を 1 つずつ言葉にする。分かれる正当な理由は **ランタイムが違うこと** だけである — 実行環境、プール、セットアップファイル。これらはプロジェクト単位でしか設定できないので、違えば分けるほかない。

正当でない理由は **モックの都合** である。「このファイル群は先にモジュールをモックしておきたいから別プロジェクト」は、設定の問題ではなく、そのモジュールが引数や context で渡されていないというシグナルである。設定を整理しても症状しか消えない。プロダクション側に **シーム**（外から差し替えられる境界）を入れて、モックの必要そのものを消す。

グローバルなアクセサ（`getEnv()` のような、どこからでも呼べる環境取得）が 1 つあるだけで、それを呼ぶモジュールすべてがテスト時にモックを要求する。1 か所を引数渡しに変えると、その連鎖ごと消えることがある。設定の行数ではなく **モックの本数** を減らす方向に投資する。

## 消す前に棚卸しする

スイートを作り直すと決めたら、消す前に **各テストが何を守っていたか** を 1 行ずつ書き出す。名前ではなく守っていた不変条件を書く — 「過去にこの事故があった」「この設計判断を固定していた」まで含める。

この表が作り直しのバックログになる。各行に「復元した」か「復元しない（理由）」が付くまでが完了である。表を作らずに消すと、何を失ったかを永久に知ることができない。テストの本数は復旧の目安にならない — 本数が戻っても、守っていたものが戻ったかは別の話である。

**復元の基点となるコミットを表に書いておく。** 消したコードは履歴に残っているので、`git show <基点>:<パス>` でいつでも読める。

## 書き直すより、履歴から復元して直す

作り直しというと全部書き直したくなるが、**旧テストの検証内容そのものは資産**である。捨てるべきは構造（重複・肥大）であって、内容ではない。

判断はディレクトリ単位で行う。

- **復元する** — 検証内容が具体的で、1 テスト 1 主張になっているもの。多くはデータ層・境界値・実挙動の確認。機械的な修正（import の付け替え、廃止したヘルパーの引数）だけで動くことが多い。
- **書き直す** — 同じ判定を何度もコピーしているもの。典型は、全エンドポイントに対して「権限が無ければ 403」を貼り付けた層。判定は最も内側で 1 回検証し、外側は配線だけを見る形に畳む。

復元してみて落ちたら、そこが現構成との差分である。落ちた理由を 1 つずつ言葉にすると、リファクタで何が変わったかの確認にもなる。

## 書いたテストは、壊して確かめる

**実装を意図的に壊して、テストが落ちることを 1 回は確かめる。** 通るだけのテストは、書いた本人に「守られている」という誤解だけを残す。壊し方は検証したい主張に合わせる — 境界の `>` と `>=`、分岐の順序、早期 return の削除、定数の値。

落ちなかったときが本番である。原因は 3 つのどれかで、対応が違う。

| 落ちない理由                                                 | 対応                                                     |
| ------------------------------------------------------------ | -------------------------------------------------------- |
| その分岐が冗長（他の判定と等価で、外しても挙動が変わらない） | テストではなくコードの事実。コメントで残すか、分岐を消す |
| アサーションが弱い                                           | テストを強くする                                         |
| 主張そのものが実態と違う                                     | テストの主張を実態に合わせて書き直す                     |

アサーションが弱い例は見つけにくい。オブジェクト全体を緩く比較する検証は、意図した変換が起きていなくても偶然通ることがある — 直列化した後を見る、変換前後を別々に見るなど、主張が成立しない形を具体的に潰す。

## カバレッジ比率をゲートにしない

カバレッジは計測して眺めるものであって、閾値で CI を止めるものではない。比率は無関係な変更で動く — 対象範囲の指定漏れで分母が変わる、リファクタで行数が変わる。閾値で落ちた回数のうち、コードの正しさに関係していたものが何回あったかを数えてみるとよい。ゼロに近いなら、そのゲートは注意を削るだけである。

守りたいのは比率ではなく **特定の不変条件** なので、棚卸し表の側で管理する。

## 一次情報の順序

ライブラリの API をテストから触るときは、思い出しで書かない。信頼度はこの順である。

1. **インストール済みの型定義** — 手元のバージョンそのものの事実。非推奨マークもここに出る
2. **公式リポジトリのサンプル/フィクスチャ** — 実際に動いているコード
3. **ドキュメントページ** — 説明は厚いが、更新が遅れることがある

型定義とドキュメントが食い違ったら型定義を採る。実例として、ある SDK ではドキュメントページに記載の無い非推奨が型定義には付いていて、公式サンプルも新しい API に移行済みだった。ドキュメントだけを見ていると、非推奨の API で書き始めてしまう。
